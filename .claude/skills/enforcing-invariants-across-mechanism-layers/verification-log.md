## 投票规则

本文件是本 skill 记录协议的**唯一权威**；SKILL.md 只定义断言，不复述规则。

- **一条断言被三次独立会话证实即毕业**（移到「已毕业」节）；**任何一次证伪都当场改 SKILL.md 正文**，并在这里写清改了什么。
- **数据不足也要写。** 长期观察不到说明验法选错了位置，那就**改验法，优先于改结论**。
- **改过本 skill 的会话不能投证实票。** 机械判据：`git log --oneline -5 -- .claude/skills/enforcing-invariants-across-mechanism-layers/` 里有你本会话的提交，或你这轮编辑过该目录 → 本轮只能记「数据不足」或「证伪」。
- **证伪票不受此限，而且格外可信**。
- 三次证实票须来自**三个未编辑过本 skill 的会话**。

## 关于「要不要升级成 always-on rule」

用户 2026-08-08 的裁决：**先写成 skill，等事情真实复现之后再据本 skill 向用户建议强化为 always-on rule。** 因此：

- **本 skill 自己不修改任何 rule 文件**，也不自动升级。它只在下面的条件满足时，**向用户提出建议**，由用户裁决。
- **建议升级的条件（三条全中才提，缺一条都不提）**：
  1. 下方记录里累计出现 **≥3 次独立会话的真实缺口实例**——即「一层守住、另一层独立制造同一违例」在不同的不变量、不同的机制维度上各自发生过，而不是同一个案例被记了三遍。
  2. 其中 **≥1 次是「缺口形成之前本 skill 未被召回」，且下方记录里该项明确记着「未召回」**。理由：升级到 always-on 解决的是**召回**问题，不是方法问题。**若某次是「已召回、方法照做了、仍漏了一层」，那不算升级理由——那是方法证伪，应当去改 SKILL.md 正文**（并在下方按证伪记一笔）。两种情形必须分开记，混为一谈会用加载层去补方法层的洞。
  3. 该形态**跨项目**成立，不是本仓特有的架构产物。
- **提建议时必须一并交出**：三个实例各自的不变量、缺口所在的机制维度、**每个实例是「未召回」还是「已召回仍漏」**、以及未召回那些的具体成因。没有最后一项，升级只会得到一条同样召不回的规则。
