# 跨机制层落实一条不变量

一条不变量被冻结之后，最常见的失败不是「有人违反了它」，而是**「它只被接线到了当时正在改的那一层」**。别的层照旧能产生同一个被禁止的可观察结果——而且它们**从来没有复述过这条不变量**，所以任何基于「搜这句话」的检查都看不见它们。

> **核心动作：先定义「被禁止的可观察结果」，再问「谁能产生这个结果」。不要问「谁提到了这条不变量」。**

## 什么时候用

只在下面这些**真实发生的事件**上触发，不要预防性地跑一遍：

- 你正要**冻结一条新的产品不变量**，或修改一条已冻结的。
- 你**发现了一处**「这一层守住了、那一层没有」，想知道还有没有第三处。
- 你准备**声称某条不变量已完整落实**（交付、评审、写进文档或规格）。
- **评审已经点名**某个旁路（config 默认值、后台 reaper、fallback 路径、迁移兼容层……）。

**不触发**：还没有不变量、只有一个需求的阶段；以及**满足下面全部三条**的局部缺陷——① 不涉及任何已冻结的不变量；② 你**不打算**做「已完整落实 / 已覆盖」这类完整性声称；③ 被禁结果与**所有已知 producer** 都封闭在同一个 helper 的合同之内（注意判据是「除了这个 helper 没有第二个东西能产生它」，**不是**「我修的地方在 helper 里」）。

**这条排除项是本 skill 最好用的逃生门，所以它自带两个闸**：

- **只要沾上冻结不变量、或要做完整性声称，就不得以「代码位置局部」为由排除。** 修复点在哪一层与 producer 有几个是两回事——一条产品不变量完全可能**恰好在某个 helper 里被发现**。
- **判定「适用排除」必须落成一句 triage 结论并写下来**（PR、交付说明、进度文件都行）：「不涉及冻结不变量 / 不做完整性声称 / 已知 producer 只有 X 一个」。**三句写不全就不适用排除。** 这不是仪式：它把一个心里的判断变成一个后来可被反驳的记录。

## 方法

### 第一步：把不变量改写成「被禁止的可观察结果」，并把它写成 inventory 的表头

不变量常写成命令式（「绝不 X」）。**先把它翻译成一句只描述**结果**的话**，因为「谁能产生这个结果」才是可枚举的。

- ❌ 「B2 只在上游确定性死亡时重发」——这是对某个组件的约束，只能查那个组件。
- ✅ 「**不存在**这样的情形：连接仍活、上游可能还在思考，而请求已被终止」——这是一个结果，任何能终止请求的东西都在嫌疑名单里。

**这一步必须留下可见产物，否则会被静默跳过**——它是本方法里唯一不产生表格的一步，也因此最容易只在脑子里过一遍：

> **把这句结果陈述写成 inventory 的表头**（「被禁结果：……」），并要求第三步里**每一个 producer 行都显式指回它**——那一行填的是「这个 producer 怎么产生**这句话描述的**结果」。表头缺失或 producer 行指不回它，本步即未遵守。

改写做对了的标志：**你能拿着这句话去问「谁能让它发生」，并得到一串互不相干的答案。** 得不到，说明还停在组件语言上——**这时不要往下走**，回来重写这句话。

### 第二步：建机制清单（开放式，不是勾选表）

**两张表，别混在一起**——它们回答的问题不同，字段也不同。混着填会得到一张自相矛盾的表（「operator 告警能否独立制造违例？」这个问题本身就没有意义）。

**但两张表不是互斥分类，同一个机制可以同时上两张表。** 判据是**角色**不是**归属**：问「它能不能直接产生被禁结果」（→ 表 A）和「它会不会让违例查不出来或被传播」（→ 表 B）**两个问题，各自独立回答**。典型的双角色：一个测试 fake 既遮蔽证据（表 B · oracle 忠实度），又可能被生产代码在某条降级路径上真的用上而直接产生被禁结果（表 A）；一份被调用方文档既传播错误用法（表 B · 契约传播），其**生成的默认配置**又能直接制造违例（表 A）。**一个机制只填了一张表，要能说出另一张为什么不适用**。

**表 A · producer（谁能直接产生被禁结果）**——只有这张表的行进第三步的五字段记账。**下面这些维度是起步提示，明确不是封闭枚举**；照着勾完不等于完整，它们的作用是打破「只想到自己刚改的那一层」：

| 维度 | 它怎么独立制造被禁结果 |
|---|---|
| runtime gate / 判定函数 | 你正在改的那一层。**最容易只有它被接线** |
| bundled 默认值 | 配置文件里的一个数字就能让被禁结果成为默认行为 |
| 用户 / per-model override | 即使默认值对了，覆盖表里一个值又打开它 |
| 后台 reaper / deadline / 定期维护 | 与主路径完全无关的时钟，谁都没想起它 |
| retry / fallback / recovery | 「救援」路径常常绕过主路径的门 |
| compat / migration 层 | 为兼容旧行为而保留的分支，正是被禁行为的旧形态 |
| schema / 生成的配置 | 生成物把被禁值写成合法甚至推荐 |

**表 B · 非 producer，但会让违例查不出来或被传播**——它们**不产生**被禁结果，所以不填「能否独立制造违例」；各有自己的可判字段：

| 类别 | 问题 | 可判字段 |
|---|---|---|
| 可观察性 | 违例发生时能不能被看见？ | 有没有一条**会真的触发**的日志/告警/指标；触发条件是什么；谁会看到 |
| oracle 忠实度 | 测试替身会不会把违例遮蔽掉？ | 该 fake/桩在这条不变量相关的行为上与真实依赖**是否一致**；不一致处列出来 |
| 契约传播 | 别人照文档写会不会正好违反它？ | 被调用方的 docstring / 类型注释 / 契约文档有没有把被禁做法写成可选甚至推荐（user-rule `check-dependency-contract-against-your-invariant`）；已按旧文档写成的调用点在哪 |

**两张表都只增不减。** 每发现一个新维度就补进去——`criteria-list-grows` 在这里同样成立：本轮想到的层数不代表全部。

### 第三步：表 A 的每一层逐条记账

**表头先写上第一步那句结果陈述**（「被禁结果：……」），然后每一层写**五个字段**，缺任何一个都不算记过：

| 字段 | 说明 |
|---|---|
| **producer** | 这一层里，具体是哪个东西能产生被禁结果（函数、配置键、定时器、表项） |
| **怎么产生表头那个结果** | 显式指回第一步的结果陈述，不是泛泛说「它有问题」 |
| **能否独立制造违例** | 不依赖其他层，它自己够不够？**这一栏是判据的核心**——「够」就是必须处理，「不够」要写清它依赖什么 |
| **disposition** | 本轮修 / 记 backlog（附理由）/ 判定不适用（附理由）。**不允许留空** |
| **正负 control** | 怎么证明这一层现在真的守住了：注入违例会不会红（负控）、正常样本会不会被误杀（正控）。**并写明这个 control 实际驱动的是什么**（见下面「不能证明什么」第 4 条） |

表 B 各类按它自己那栏的可判字段记，同样每条都要有 disposition。

**「一层都没发现」也要落到纸面**：写清扫了哪两张表的哪些维度、用了什么判据。「无发现」和「没扫」在纸面上必须可区分。

### 第四步：别用「grep 这条不变量」当覆盖证明

最常见的自欺：搜这条不变量的**措辞**（或它的关键词），命中的地方都改了，于是宣称完整落实。

**这个方法结构性地看不见最危险的那一层**——恰恰是那些**从未复述过这条不变量**的机制（一个配置默认值、一个后台定时器）最可能独立制造违例。文本搜索只能找到「谈论它的地方」，找不到「能违反它的地方」。

grep 仍然有用，但它的作用是**找到所有需要同步修订的复述**（守卫、注释、文档），不是证明覆盖面。

## 与既有 always-on 规则的关系（互补，不复制）

这些规则各自有正文，**本 skill 不复述它们，只说明分工**：

- user-rule `64-concurrency-and-refactor.md:14` `scoped-invariant-written-as-global` —— 讲「这条不变量其实只在某个作用域内成立」。**方向相反且互补**：那条问「它的适用范围是不是被写大了」，本 skill 问「它的落实范围是不是被写小了」。**两个方向都要过一遍。**
- user-rule `63-engineering-practice.md:52` `fix-at-the-shared-base-not-where-you-noticed` —— 讲修复点该放在哪一层。本 skill 是它的前置：**先知道有哪些层，才谈得上选层。**
- user-rule `63-engineering-practice.md:57` `check-dependency-contract-against-your-invariant` —— 讲被调用方的文档可能把你要禁止的事写成推荐做法。那是本 skill「文档 / 被调用方契约」这一维的展开。
- user-rule `63-engineering-practice.md:50` `new-checks-must-not-alter-existing-contracts` 与 `:67` `packaging-can-void-another-invariant` —— 讲你新加的东西会碰坏别的不变量。**是本 skill 的反向**：那边问「我这次改动碰坏了谁」，这边问「谁能碰坏我这条」。

## 历史实例（只作示范，状态以权威 docs 为准）

`never-false-kill-legit-thinking`：一条用户冻结的硬约束，禁止在「连接仍活、上游可能仍在思考」时终止请求。它当时被完整接线进了 B2 / B3 的判定路径——**而 bundled 配置里的四个 wall-clock terminator 仍在按正秒数终止活请求**。那四个键从未提到过这条不变量，所以任何基于措辞的检查都扫不到它们；缺口是在一次**合并态审计**里才撞出来的。

这个实例的价值在于形态，不在于数字：**判定层做对了，而默认值层独立地制造着同一个被禁结果。** 完整的裁决原文、涉及哪些键、当前是什么状态，一律去读权威 docs（`docs/plan/2026-07-23-upstream-silence-recovery/README.md` 的 Global Constraints 节、`docs/DESIGN.md` 的活架构现状表）——**本 skill 不复制当前的配置/告警/测试清单**，那些会变。

## 这条方法**不**能证明什么

- 它**不能**证明清单完整。它只能证明「你按结果而不是按措辞去枚举过」，并留下可被下一个人接着补的记账。
- 逐层都绿**不等于**层与层之间没有缝（`gaps-between-criteria-not-within`）。想找缝，得去造一个「每层单看都对、合起来仍产生被禁结果」的场景。
- **一个 control 只证明它实际驱动到的那个 witness**，不证明生产接线，也不证明输入完备性。两种典型失真：control 打在 fake / helper 上（逐层全绿，而**真实入口根本没读那个机制**），或 control 只覆盖了这一层的部分输入形态（另一半输入下它照样违例）。所以记账里那一栏要写**这个 control 实际驱动的是什么**；凡是要做「已完整落实」声称的层，control 必须**从真实入口驱动**，并用**独立 oracle** 校准。
- 它**不产生授权**。发现某层能制造违例之后要不要改、怎么改，仍受既有裁决约束——若那条不变量是用户冻结的，放宽它需要新的用户裁决。

## 自验：本 skill 需要实战检验的断言

以下断言写作时无法自证，只能靠**未来会话在正常使用中顺手观察**证伪。观察到一条就往 [`verification-log.md`](verification-log.md) 追加一行（记录协议以该文件为准）。**本 skill 的作者不能给自己投证实票。**

**升级为 always-on rule 的条件写在 verification-log 里，且只由用户裁决**——本 skill 自己不修改任何 rule 文件。

| # | 断言 | 证实长什么样 | 证伪长什么样 |
|---|---|---|---|
| V1 | 四个触发事件够具体，真的会被认出来 | 在四个事件之一上自发想到它 | 事后（缺口已暴露）才想起来；或被人点名才用 |
| V2 | 「结果语言而非组件语言」这一步可执行，且**留下了产物** | inventory 表头上真的有那句结果陈述，且 producer 行指得回它 | 表头缺失、或直接开始填层名；改写出来的仍是对某个组件的约束 |
| V3 | 起步维度表**没有**被当成封闭勾选表 | 有人补进了表 A 或表 B 上没有的维度 | 有人勾完现有几行就宣称完整落实 |
| V4 | 「grep 措辞不算覆盖证明」这条挡得住 | 有人明确放弃了「搜关键词全命中=已覆盖」的论证 | 又一次用 grep 命中数当作覆盖面证据 |
| V5 | 五字段记账真的被填满（尤其「能否独立制造违例」与 disposition） | 落盘的表里五栏齐全 | 只列了层名；或 disposition 留空 |
| V6 | producer 与非-producer 两张表**没有被混填，也没有被当成互斥分类** | 表 B 的项按各自字段记；双角色机制同时出现在两张表，或写出了「另一张为什么不适用」 | 给 operator 告警填「能否独立制造违例」；或把一个双角色机制只归进一张表而说不出理由 |
