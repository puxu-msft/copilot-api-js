# 分层迭代交付

## 核心原则

迭代交付同时承担两项证明义务：

1. **当前批是终态。** 它边界清楚、内部自洽、可独立产生价值，并通过自己的验收门；编译中间态、缺腿实现或已知 correctness／数据完整性／合并安全缺陷都不是一批。
2. **完整范围没有消失。** 不阻断当前批的正确事项进入后续批，但每项都必须可发现、可复议、可验收；不能靠改状态、缩窄“核心范围”或无限写“下批再排”让它退出父项目。

这不是“小步优先”，而是“每步完整，完整范围持续可达”。批次大小由依赖和验收接缝决定，不由行数、日期或方便程度决定。

## 何时拆批

观察到以下任一信号就建立批次台账，而不是继续维护一张无限增长的任务清单：

- 工作需要多个语义 commit 或跨阶段依赖。
- 当前批已能独立验收，但实施中继续发现新的长期正确事项。
- 新发现依赖尚未到达的外部事件、数据规模或另一阶段产物。
- 团队在“全部塞进本轮”与“先交付，剩下以后再说”之间摇摆。
- 父项目准备关闭，但仍有 deferred／follow-up／todo。

单一语义、一次成型且没有后续发现的工作不需要此流程。

## 工作流

### 1．冻结当前批契约

动手前或发现范围扩张时，写下：

| 字段 | 必须回答 |
|---|---|
| 独立价值 | 这一批单独交付后，谁能得到什么真实价值？ |
| 边界 | 明确包含和不包含哪些能力？ |
| 不变量 | correctness、数据完整性、兼容迁移与合并安全必须满足什么？ |
| 验收 | 哪些命令或观测证明这一批可独立运行？ |
| 正控 | 注入哪个目标缺陷会使门精确变红？正确样本能否保持绿？ |
| 依赖 | 哪些前置已经满足，哪些尚未满足？ |

多步骤计划先用 `superpowers:writing-plans`；实现遵循 `superpowers:test-driven-development`。高风险 correctness gate 用 `positive-control-your-tests` 验证鉴别力。

### 2．每个新发现当场分流

按对当前批契约的影响分类，不按“修起来要多久”分类：

| 分类 | 判据 | 动作 |
|---|---|---|
| 当前批 blocker | 不做就违反当前批已冻结的不变量、验收、数据完整性或合并安全 | 留在当前批，闭合后才能交付 |
| 后续批 | 长期正确，但当前批不依赖它也完整、可用、可验收 | 当场写入后续项载体，然后继续当前批 |
| 需裁决 | 是否仍正确、是否属于父项或是否已被替代没有客观答案 | 记录证据与分歧，交用户或未卷入方裁决；作者不能靠改标签自行消项 |

“演示能过”“主流程能跑”“已经投入很多时间”都不能把 blocker 变成后续项。反过来，“这是正确改进”也不能把不阻断当前批的工作强塞回当前批。

### 3．所有受治理对象使用完整记录契约

批次、阶段、父项目和后续项都必须独立记录同一状态 schema；对象不适用的业务字段写 `N/A` 并说明理由，不能省略状态条件集合。缺字段时写 `TBD`，不能静默省略。`TBD` 只证明缺口被捕获，不代表记录完整；每个 TBD 固定附五项：`source_context`（支撑该缺口的原始证据或发现上下文；没有证据文件时至少记录发现者、发现动作和原载体）、`unknown_reason`、`owner`、`resolution_trigger`（强制补齐的可观察事件）、`state_gate`（补齐前禁止进入的状态）：

```markdown
- ID／目标：
- 为什么仍然正确：
- 与当前批的关系：不阻断的具体依据
- 依赖：
- 事件型复议触发点：
- 验收判据：
- 证伪方式：
- 正确样本／目标缺陷正控：
- applicable_conditions：该对象全部适用条件 ID 的唯一集合
- closed_conditions：已闭合条件 ID 与证据
- open_conditions：未闭合条件 ID、责任人和触发点
- 状态：pending／ready／in progress／ready to deliver／blocked／needs adjudication／done／superseded／retired／transferred
- 决策权：谁能继续排期或重新裁决
- 父项／计划入口：
```

**事件型复议触发点是必填项，不能裸写 `TBD`。** 使用可观察事件，例如“供应商 API v3 发布”“数据达到 10TB”“依赖批合并”“下一阶段启动”“父项目申请关闭”。日历日期只能作提醒，不能单独充当触发点；日期可以被反复顺延，而事件会迫使重新判断。

对每个对象先验证集合分区：条件 ID 在 `applicable_conditions` 中唯一；`closed_conditions` 与 `open_conditions` 不相交，二者并集必须精确等于 applicable 集。缺失、重复或同时落两侧时转 `needs adjudication`，不得先判状态。

对全部非终态对象检查依赖与触发的组合图，不能靠改状态标签逃逸。按以下**从上到下的互斥优先级**派生唯一状态，命中后不再匹配后项：

1. `needs adjudication`：存在待裁决的正确性、归属或依赖结构命题，或依赖／触发图出现环、自依赖、无外部入口的封闭分量。open 集必须记录命题、合格裁决者和已经发生的立即复议原因；裁决前禁止开工、继续等待或进入其它终态。
2. `blocked`：不存在待裁决命题，但至少一个真实外部依赖未满足；每个依赖必须可追溯到独立事件或可启动根项。存在外部阻塞时不得标 `pending／ready／in progress`。
3. `pending`：没有外部阻塞或待裁决命题，但分类、信息或排期尚未闭合；open 集记录补齐责任与可达触发，且实施尚未开始。
4. `in progress`：全部启动前置已闭合，实施或验收 ID 正在闭合；不得同时存在待裁决命题或未满足外部依赖。
5. `ready`：全部启动前置已闭合，实施尚未开始，open 集只含尚未启动的实施、验收和交付 ID；现在即可开工。
6. `ready to deliver`：边界、不变量、依赖、实施和验收 ID 均 closed，只有交付 ID 仍 open。此状态执行交付；交付证据落盘后把交付 ID 移到 closed，再转 `done`，不得先标 `done`。

终态同样唯一。记录一个 `terminal_outcome` 条件组；`done／superseded／retired／transferred` 候选若同时超过一个成立，先转 `needs adjudication`，不得按方便选择标签。只有一个 outcome 的全部条件 closed、其余候选明确“不适用”、且 open 集为空时，才派生对应终态：

- `done`：交付已完成且证据落盘，全部适用实施／验收／交付 ID closed。
- `superseded`：具名替代对象、覆盖原目标与验收的证据、合格裁决 ID closed；原实施／验收／交付 ID 由该裁决原子处置为“不再适用”。
- `retired`：原需求或价值不再成立的证据、影响记录、合格裁决 ID closed；不得用“已有替代”冒充需求失效，原执行 ID 由退休裁决原子处置。
- `transferred`：真实转移的全部条件及接收证据 ID closed；源项所有责任 ID 由转移 ID 显式关闭，接收父项以同一事项 ID 建立自己的条件集合。合作方缺失或转移条件未闭合时仍属非终态。

任何终态都不得残留未处置的 open ID。长期没排期、连续延期或清空看板意图都不是终态证据。

载体位置遵循项目文档路由；需要决定 plan／backlog／todo 放置时使用 `organizing-project-docs`。不要另建与现有状态真相源平行的台账。

### 4．当前批验收一绿就进入交付

当前批除交付外的契约全部闭合后，标 `ready to deliver`，立即提交、集成或发布这一批，不等待不阻断它的后续项。交付成功及证据落盘后关闭交付 ID，再标 `done`。交付报告同时给出：

- 当前批已满足的契约与证据。
- 未完成后续项的完整清单与入口。
- 下一事件型复议触发点。
- 父项目当前状态。

“后续项未完成”不否定当前批完成；“当前批完成”也不等于父项目完成。

### 5．批次、阶段与父项目是三道不同的门

每次批次／阶段收尾以及父项目申请关闭时，机械枚举对应状态真相源中的全部组成批次与未完成后续项。

- **批次完成：** 只需当前批契约闭合，允许后续批仍未完成。
- **阶段完成：** 阶段内每个批次都达到各自的完成态或授权终态，阶段级集成／验收门也闭合；一个批次完成不能替代阶段完成。
- **父项目完成：** 三组条件必须同时闭合：全部必需组成批次／阶段达到完成态或授权终态；父项目级集成／验收门通过；所有正确后续项为 `done`、由用户／未卷入方依据证据判为 `superseded／retired`，或完成真实转移。没有 follow-up 只满足第三组，不能掩盖未完成阶段或项目级验收。
- **真实转移：** 接收父项必须存在且处于活动状态、有具名 owner，并在自己的状态真相源中以同一 ID 接收目标、验收、依赖、触发点、当前状态和关闭责任；源／目标双向链接，转移关系无自环或父项间循环。全部条件原子成立后，源项才标 `transferred`；只移动链接、复制标题或单方面声明不算转移。
- **部分完成：** 核心批已交付但所在阶段或父项目仍有正确后续项时，分别写“当前批已完成／阶段进行中／父项目部分完成”，不要追溯性缩窄“核心范围”来宣布上层完成。

父项目关闭点的未完成正确事项必须由用户或**未卷入方**逐项明确决定：继续排入后续批、依据证据 `superseded／retired`，或完成真实转移；没有裁决就不能关闭父项。这里“未卷入”是机械资格：没有参与该事项的提出、实现、既有处置，也没有发起或执行本次关闭申请；具名、有治理授权、现任 owner 都不自动满足。若没有满足资格的项目方，交用户裁决；用户未裁决时父项保持开放。既有已批准批次内部的普通排序仍可由具名治理 owner 处理，但它不能替代关闭点裁决。当作者既提出后续项又想在关闭时消项，属于自我裁决；记录理由与级别，使用 `adopting-agent-findings` 的独立 adjudication 流程。沉默不是裁决。

阶段结束时使用 `session-closeout`，把未完成项枚举与父项状态纳入独立核验。

上述外部 skill 是流程委托，不是本 skill 状态判据的隐藏实现。目标缺失或 frontmatter 身份不符时停止并报告依赖错误，不回退为手写平行流程；目标 skill 可正常演进，故只校验身份与可达性，不锁定全文 hash。

## 快速参考

| 现场问题 | 正确动作 |
|---|---|
| 当前批已自洽，新发现不阻断 | 记录完整后续项，立即交付当前批 |
| 新发现破坏当前批 correctness | 留在当前批，不能用 backlog 降级 |
| 后续项依赖尚未发生的事件 | 记录依赖与事件型触发点，不提前实现 |
| 多轮只写“下批再排” | 触发复议；补依赖、事件与明确裁决 |
| 核心上线但阶段／父项仍有正确后续项 | 当前批完成，阶段进行中，父项部分完成 |
| 想把事项批量改成 Not Planned | 停止；要求证据与用户／未卷入方裁决 |
| 想把事项转给另一个父项 | 先验证接收方 active、具名 owner、完整原子接收、双向链接与无环 |

## 示例

日志存储批次 A 的读取 API 已独立验收；批次 B 的压缩优化只有在生产数据达到 10TB 后才能设计，当前为 600GB。

```markdown
父项目：部分完成
当前批 A：done；读取 API 已交付，回归、迁移兼容与独立验收均通过
后续项 B：
  ID／目标：B／基于真实分布设计压缩与迁移
  为什么仍然正确：降低达到规模后的存储成本
  与 A 的关系：不影响读取 API correctness、兼容或交付
  依赖：生产样本达到 10TB
  事件型复议触发点：容量监控首次达到 10TB
  验收：冻结样本上比较压缩率、读取延迟、CPU、迁移与回滚
  证伪：收益不足或迁移／回滚不满足冻结阈值
  正控：已知可压缩样本应显示收益；高熵样本不应被误判
  applicable_conditions：[B-RECORDED, B-DATA-10TB, B-IMPLEMENT, B-ACCEPT, B-DELIVER]
  closed_conditions：
    - B-RECORDED：目标、价值和与 A 的不阻断关系已记录
  open_conditions：
    - B-DATA-10TB：owner=容量监控负责人；trigger=生产样本首次达到 10TB
    - B-IMPLEMENT：owner=B 实施负责人；trigger=B-DATA-10TB closed
    - B-ACCEPT：owner=B 验收负责人；trigger=B-IMPLEMENT closed
    - B-DELIVER：owner=B 交付负责人；trigger=B-ACCEPT closed
  状态：blocked
  决策权：用户或未卷入的项目负责人
  父项／计划入口：日志存储父项目／后续批次 B
```

A 立即交付；B 不提前实现也不删除；B 未被重新裁决前，父项目不能标为完成。

## 常见错误与合理化

| 说法 | 实际问题 |
|---|---|
| “正确事项绝不能丢，所以全部塞进本轮” | 保存范围不等于阻塞交付；完整记录后续项即可保留范围 |
| “核心已经上线，剩下都改成 Not Planned” | 追溯性缩窄父项；未证明事项失效，也绕过了独立裁决 |
| “每月看一次就算有复议点” | 日期可无限顺延；缺少必须重新判断的事件 |
| “主流程通过，恢复／错误路径放下一批” | 若错误路径属于当前批故障模型，就是 blocker |
| “todo 还在，所以没有丢范围” | 存在性不保证可达；没有依赖、事件触发和关闭门仍可永久冻结 |
| “字段都写了 TBD，所以记录完整” | 只捕获了缺口；没有补齐责任、触发和状态门，接手者仍无法行动 |
| “转进另一个父项，就能关闭原项目” | 单方面改标签不转移责任；接收必须完整、双向、原子且无环 |
| “当前批完成，所以阶段／项目完成” | 混淆批次门、阶段门与父项目门 |

## 红旗——停止并重新分类

- 当前批仍有已知不变量反例，却准备标完成。
- 后续项只有标题、负责人或日期，没有事件型复议触发点。
- 依赖／触发组合图存在环、自依赖或没有外部入口的封闭分量。
- 同一个事项连续两次被写成“下批再排”，却没有产生新裁决。
- 阶段或父项目关闭动作没有先枚举全部组成批次与未完成后续项。
- `transferred` 没有接收父项的活动状态、具名 owner、完整接收记录、双向链接或无环证据。
- 用 `Not Planned`、`Won't Do`、`Out of Scope` 批量清空仍然正确的事项。
- 关闭方也是事项作者，且没有用户或未卷入方裁决。
- 用“核心范围”替换原父项范围，却没有更高权威的明确重裁。

这些信号意味着迭代正在退化为无限扩张、无限延期或静默删范围。先修台账与裁决，再继续关闭动作。

## 自验

本 skill 的静态自洽不证明未来模型会按它执行。正常使用时把观测追加到 [verification-log.md](verification-log.md)：

| ID | 待验证断言 | 顺手观察 | 证伪形态 |
|---|---|---|---|
| V1 | description 能在 scope creep、all-in-one、deferred follow-up 与父项关闭场景触发 | 记录实际触发来源 | 用户点名后才加载，或关闭父项时未触发 |
| V2 | 三道门能阻止“批次完成＝阶段／父项完成” | 记录阶段或父项仍有后续项时的实际状态 | skill 使用后仍追溯缩窄范围并标上层完成 |
| V3 | 事件型触发点能阻止无限写“下批再排” | 后续项第二次复议时记录是否由事件触发并产生裁决 | 只更新日期、没有新裁决 |
| V4 | 分类不会 false-red 地强迫 all-in-one | 记录合法外部依赖项是否留在后续批 | 为显得彻底而提前实施，或阻塞已自洽当前批 |
