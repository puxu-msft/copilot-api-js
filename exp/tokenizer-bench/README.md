# tokenizer 选型实测（2026-08-11）

## 它回答的问题

主线程被 token 计数阻塞数秒（活服务 `/health` p90 2027ms、max 3113ms）。换一个 tokenizer 实现能不能消除这个病态？

## 结论：不能。二次行为是 BPE 的固有性质，不是某个库的缺陷

`o200k_base`，同一台机器，warmup 后计时。**三者 token 数完全一致**（12601 / 19205 / 160 / 480 / 960），故互换不改变行为。

| 输入 | gpt-tokenizer（现用） | tiktoken 1.0.22 (Rust/WASM) | js-tiktoken 1.0.21 |
| --- | --- | --- | --- |
| 英文 60KB | **9 ms** | 64 ms | 11 ms |
| JSON 60KB | **28 ms** | 43 ms | — |
| 空格 20KB | 424 ms | 396 ms | **74792 ms** |
| 空格 60KB | 3514 ms | **3269 ms** | — |
| `=` 分隔线 60KB | 3452 ms | **2841 ms** | — |

- **换库最多省 7%**（病态用例），代价是正常英文慢 7 倍（tiktoken）。现用的 `gpt-tokenizer` 已是三者最优。
- `js-tiktoken` 在病态输入上差 **176 倍**，直接排除。
- 病态形态是**同字符长游程**：尺寸翻倍耗时约 4 倍 → O(n²)。裸 `encode` 与经我方包装层的耗时一致，故缺陷不在包装层。

## 附带发现：游程的 token 数是精确线性的

空格 20KB→160、60KB→480、120KB→960，**恰好 128 字节/token**；`=` 是 60KB→960，即 64 字节/token。

所以同字符游程的 token 贡献**可按 (字符, 长度) 精确计算，无需送进 BPE**——这是消除病态的算法解，且结果精确而非近似。

## 后续实测（2026-08-12）：换库不行，但「换线程 + 短路游程」两件都做了

两件事互补，任一单独都不够：

- **搬出主线程**（`src/lib/models/tokenizer-worker.ts`）。用 5 ms 的 interval 定时器量事件循环是否还活着，同一段 ~1.9 MB 英文：**主线程内 205 ms，定时器触发 0 次**（`Math.max` 拿到空数组，所以探针打印 `-Infinity`——那不是异常值，是「一次都没触发」）；**走 Worker 183 ms，触发 31 次，最大停顿 14.2 ms**。这解决的是「计数期间整个进程失聪」，包括收不到 `SIGUSR2`。
- **游程短路**（`src/lib/models/run-collapse.ts`）。空格 60 KB 3514 → 1 ms，120 KB 17407 → 1 ms，`a` 60 KB 7911 → 17 ms；普通英文 18 → 21 ms（多出来的是游程扫描）。**搬了线程仍需要它**：Worker 只有一条线程，一次 17 秒的病态计数会把其后所有计数排在它后面。

比例不是硬编码的，按 (编码, 字符) 用短探针学一次并缓存，且**只在「长度翻倍则 token 翻倍」成立时才采信**，否则退回真实编码——正因为下面「只测了一种编码」这条限制。

## 它没有证明什么

- **只测了 `o200k_base` 一种编码**。项目还用 `cl100k_base`/`p50k_*`/`r50k_base`，未验证它们的游程常数是否相同（几乎可以肯定不同，需逐编码器实测后再硬编码任何比例）。
- **只测了单字符游程**。未测「短周期重复」（如 `ab` 重复、缩进模式 `\n    `），它们是否同样二次、是否同样线性可算，**未知**。
- **未测真实生产 payload**。语料是合成的；真实 Claude Code 请求里游程的长度分布未采样。
- **未测多编码器共存下的内存占用**，也未测 WASM 编码器在 Worker 中的加载成本。
- **Worker 的往返开销未单独标定**。上面 183 ms vs 205 ms 是端到端，其中 postMessage 的 structured clone 成本没有单独测；小 payload 上这笔固定开销占比更高，未测。
- **未测并发**。全部是单请求串行；多请求同时计数时单条 Worker 线程会排队，排队延迟未测。
- 单次运行、单机、未控 CPU 频率与并发；数量级可信，个位数百分比不可信。

## 复现

```bash
cd exp/tokenizer-bench
bun add tiktoken js-tiktoken        # gpt-tokenizer 取自项目 node_modules
bun run bench-one.ts gpt            # 也可传 wasm / js
bun run equivalence-check.ts        # 游程短路 vs 真实编码器，逐用例比对
bun run event-loop-blocking.ts      # 主线程 vs Worker：计数期间定时器还跳不跳
```

`event-loop-blocking.ts` 里的路径是写死的绝对路径（探针不是产品代码，换树时改那一行）。它产出的对照是 README 上面那组「0 次 vs 31 次」的来源；常驻守卫只覆盖 Worker 那一侧，主线程对照只有这里有。
