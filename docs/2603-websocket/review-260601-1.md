# WebSocket 模块全面审查报告

> 审查日期：2026-06-01
> 审查范围：代理↔上游 + 客户端↔代理 + 历史 WS + 集成 + 配置
> 审查者：独立 subagent

## 总体评价

整个 WebSocket 子系统已经处于「上线就绪」的成熟度。代理↔上游层（`src/lib/openai/upstream-ws.ts` + `upstream-ws-connection.ts`）的状态机设计严谨：连接复用键（`previousResponseId` → `conversationId`）层次清晰、半开恢复窗口的「至多两轮」语义在代码与注释中明确互证、`handleClose` 的幂等保护、`send`/`parse` 失败时主动撕掉连接以防止协议状态污染——这些都是经过实战打磨的痕迹。客户端↔代理层（`src/routes/responses/ws.ts`）以 `WeakMap` 串行化同一 socket 的 `response.create`，并以共享 pipeline 复用 HTTP 路径的全部清洗/重试逻辑，避免了 WS/HTTP 双实现漂移。`src/lib/shutdown.ts` 对 upstream WS 做了 Phase 1 `stopNew` + Phase 4 + `finalize` 三道关，覆盖比一般实现更全面。

主要遗留问题集中在两类：(1) 配置面/文档「实现已超前、文档未跟上」漂移（`fix_stream_ids`、`client_websocket_keep_open`、`max_connections` 都没在 `config.example.yaml` 出现）；(2) 一处真实 shutdown 时序竞态——`manager.create()` 在 `stopNew()` 后抛错时绕过 fallback，直接冒泡。其余多为可读性/可观测性优化。

## 严重度分级

- 🔴 CRITICAL — 真实 bug 或安全问题，必须立即修
- 🟠 HIGH — 真实 bug 或显著健壮性问题
- 🟡 MEDIUM — 设计/可维护性问题
- 🟢 LOW — 风格/小优化

## CRITICAL

（无）

## HIGH

### H1. shutdown 时 `manager.create()` 抛错未走 fallback

`src/lib/openai/responses-client.ts:119-121`

```ts
const connection =
  reusable
  ?? (await manager.create({ headers: prepared.headers, model: wire.model, conversationId: opts?.conversationId }))
```

`await manager.create(...)` 写在 `??` 表达式内，整段处于 try/catch 之外。`canUseUpstreamWebSocket()`（responses-client.ts:93-96 检查 `!manager.stopped`）与 `manager.create()` 之间存在 TOCTOU 窗口；shutdown 在该窗口内调用 `stopNew()` 后，`create()` 直接抛 `"Upstream WebSocket manager is not accepting new work"`（upstream-ws.ts:134），**冒泡到 `createResponses()` 调用方**，既没 `recordFallback()` 也没走 HTTP fallback——客户端会看到内部错误。

**修复方向**：把 `manager.create()` 调用纳入 try/catch；或把「拿连接 + connect + first event」原子化为一个 helper，统一把所有「首帧前」失败都转成 `{ kind: "fallback" }`。

**影响**：shutdown 时边缘请求会出 500 而非降级到 HTTP。频率不高但属正确性问题。

### H2. `config.example.yaml` 缺失 `fix_stream_ids` 与 `client_websocket_keep_open`

`config.example.yaml:283-288`

实现已经支持但用户无从知晓的两个开关：
- `openai-responses.fix_stream_ids`（默认 `true`，影响 `@ai-sdk/openai` 兼容性）
- `openai-responses.client_websocket_keep_open`（默认 `false`，启用客户端长连接 WS）

两者均挂在 `state.ts:284-301` 与 `config.ts:307-310`，但 yaml 示例完全没提。

**修复方向**：在 `openai-responses` 段补齐示例与默认值，解释 `client_websocket_keep_open=true` 时一次连接多次 `response.create` + 服务端 `WeakMap` 串行化的行为。

## MEDIUM

### M1. DESIGN.md 引用不存在的文件

`docs/DESIGN.md` 在 `lib/history/` 列表中写着 `ws.ts # WebSocket 实时推送`，实际该文件不存在——历史 WS 已迁移到 `src/lib/ws/broadcast.ts`（topic-aware 总线）。

**修复方向**：把条目改为指向 `lib/ws/broadcast.ts`，并加一句「历史/状态/请求事件统一通过共享 WS 总线广播」。

### M2. Phase 1 同步关闭浏览器 WS 客户端，导致 `shutdown_phase_changed` 事件丢失

`src/lib/shutdown.ts:249-253` 在 Phase 1 同步执行 `closeWsClients()`，用 1001 顶掉所有 `/ws` 浏览器客户端。`setPhase("phase1")`（shutdown.ts:232）的 `notifyShutdownPhaseChanged` 是 synchronous broadcast，但帧可能还没出栈、客户端就被踢掉了。后续 phase2/3/4 的广播帧没人能收到。

**修复方向**：要么先 broadcast、await 一个 microtask 再 close；要么不在 Phase 1 关 WS 观察者客户端（它们不是业务流量），留到 Phase 4 force close，前端能看到进度。

### M3. `finalize()` 中 `setPhase("finalized")` 后立刻清理，前端永远收不到 finalized 帧

`src/lib/shutdown.ts:346-358` —— 同 M2 同类设计问题。

### M4. `recordFallback` 在禁用窗口内计数器单调递增

`src/lib/openai/upstream-ws.ts:177-198` 处于禁用窗口内的 `recordFallback()` 早早 `return` 是为了避免「无限延长禁用」（正确），但 `consecutiveFallbacks` 计数器**永远不复位**（只有 `recordSuccessfulStart()` 复位）。`/api/status` 暴露的 `consecutive_fallbacks` 在长期间歇失败下会变成无意义的大数字。

**修复方向**：窗口内的 `recordFallback` 也跳过自增；或暴露「最近一次成功时间」作为辅助指标。

### M5. `findReusable` 是「首个命中」而非 LRU/MRU

`src/lib/openai/upstream-ws.ts:97-130` `for...of connections` 按插入顺序遍历首匹配返回。在 `conversationId` 退化匹配下可能复用一个「久未使用、TCP 状态较旧」的连接。`lastUsedAt` 已经记录但没被用作选择依据。

**修复方向**：按 `lastUsedAt` 倒序选最近用过的；或在 `conversationId` 多命中时倾向已设 `statefulMarker` 的连接。

### M6. WS 客户端帧没有 size 上限

`src/routes/responses/ws.ts:298-307` 和 `src/lib/ws/broadcast.ts:329-347` 直接 `JSON.parse(event.data)`，无任何大小检查。Bun/Node WS 默认上限 16MB~100MB，恶意巨型 `response.create` 帧能直接占满 V8 堆。公网部署时是 DoS 表面。

**修复方向**：`onMessage` 入口加 `raw.length > MAX_WS_FRAME_BYTES` 守卫，默认 1MB。

### M7. `clientWebsocketKeepOpen=true` 没有客户端侧 idle 关闭

`src/routes/responses/ws.ts:251-253` 开启 keep-open 后，socket 在终结后保留。客户端如果再不发帧也不关闭，socket 永远占着 FD 与 `WSContext`。upstream 侧有 `DEFAULT_IDLE_TIMEOUT_MS=5min`，客户端侧没有对等机制。

**修复方向**：加客户端 idle timeout，`onOpen` 起定时器、每次 `onMessage` 重置。

## LOW

- **L1**：`upstream-ws-connection.ts:155-194` `socket = ws` 赋值发生在 await 之前。逻辑正确但读起来需追三处回调，可考虑握手成功后再赋值给模块级 `socket`。
- **L2**：`upstream-ws-connection.ts:122-126` `handleError` 当 `!busy` 时静默忽略。idle 状态下 socket 报错应主动 `socket?.close()` 把连接踢出池，目前等 close 事件兜底。
- **L3**：`responses-client.ts:237-261` `logHeaderReuseDiff` 每次都构造两个 Map 只为查 4 个 invariant。改成大小写不敏感的 `getHeader` 调用更轻量。
- **L4**：`routes/responses/ws.ts:286` 的 `WeakMap` 锁注释假设 hono/bun 串行化 onMessage；切到 node-ws 时假设不成立，但有 WeakMap 兜底。建议补一个非 Bun runtime 的并发测试 case。
- **L5**：`broadcast.ts:152-161` 在 `for...of clients` 迭代中删除条目合法但易困惑，可改为收集后批量删除。
- **L6**：`routes/responses/ws.ts:201-202` 与 `handler.ts:201` 的 SSE iterator cast 重复，可抽 `iterateSseEvents()` 助手。

## 配置评价

`openai-responses` 段当前只有两条注释，远不够。建议补齐：

```yaml
openai-responses:
  normalize_call_ids: true
  upstream_websocket: false           # 启用代理↔上游 WS
  fix_stream_ids: true                # 修复 @ai-sdk/openai 期望的 ID 一致性
  client_websocket_keep_open: false   # 客户端长连接 WS（默认每次 1000 关闭）
  # max_upstream_connections: 32      # 连接池软上限（达到后驱逐 idle）
```

默认值评价：所有当前默认值（`upstream_websocket=false`、`fix_stream_ids=true`、`client_websocket_keep_open=false`）均合理。32 连接池上限对大多数部署够用，但应暴露为可配置项以应对高并发。

## 测试覆盖盲区

1. **H1 描述的 shutdown 时序竞态**——`canUseUpstreamWebSocket` 通过后、`create` 之前 `stopNew` 触发的窗口。
2. **`client_websocket_keep_open=true` 下的 idle 行为**——长连接客户端 X 分钟不发帧。
3. **`onMessage` 巨型 payload 防护**——无 DoS 边界测试。
4. **非 Bun runtime 下的 WeakMap 并发锁**——`tests/ws/responses-ws.test.ts` 仅 hono/bun。
5. **`closeAllClients` 与 `notifyShutdownPhaseChanged` 顺序**（M2 场景）无测试。
6. **`logHeaderReuseDiff` drift 路径**——是否真正打印、大小写处理正确性。
7. **`recordFallback` 禁用窗口内计数器行为**——已测「不延长窗口」，未测计数器递增预期。
8. **`handleMessage` parse error 后 socket 必关闭**——connection 测试中缺该 case。

## 优势

- **`handleClose` 幂等保护 + 注释明确**（`upstream-ws-connection.ts:127-146`）是教科书级防御代码。
- **`recordFallback` 半开窗口的两轮限制**（`upstream-ws.ts:177-198`）注释比代码长——避免了「间歇失败永久禁用 WS」反模式。
- **`finishRequest` / `failRequest` 严格分离**——终结清理 vs 失败清理两条路径状态切换干净。
- **`evictOneIdleIfNeeded` 在所有连接都 busy 时打 warn 但允许超额**（`upstream-ws.ts:78-87`）——避免「池满 → fallback 计数 → 禁用 WS」的雪崩。
- **shutdown 三道关清理 upstream WS**（Phase 1 `stopNew` / Phase 4 `closeAll` / `finalize` `closeAll`），`finalize()` 注释明确解释了「graceful drained 路径也要清理」的动机。
- **HTTP/WS 客户端 handler 共享 `createResponsesAdapter` 与 `createResponsesStrategies`**（`routes/responses/pipeline.ts`）——避免双实现漂移。

## 建议优先级

按 ROI 排序：

1. **H2**（配置文档补齐）——改一个 yaml 文件，可发现性 ROI 最高。
2. **H1**（shutdown 时 create 抛错路径）——几行代码，闭合真实正确性边界。
3. **M6**（WS 帧大小上限）——一行守卫，闭合 DoS 表面。
4. **M1**（DESIGN.md 修正 `history/ws.ts` 引用）——文档勘误。
5. **M7**（client keep-open idle 关闭）——启用该特性的部署防资源泄漏。
6. **M2/M3**（shutdown 广播顺序）——UI 侧需要展示 shutdown 进度时重要。
7. **M4/M5**（fallback 计数器观感、复用选择策略）——长跑可观测性优化。
8. **L1–L6**——按需进入下一轮维护。
