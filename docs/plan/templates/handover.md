# HANDOVER / KICKOFF 骨架

user-level skill `writing-handover-docs` 的配套模板（本仓专用，含本仓路径）。判定纪律在那个 skill 的正文，这里只放可照抄的结构——**空着的槽位要显眼**，因为最易漏的几条（证据等级与口径、**结论的适用问题**、**与冻结 spec 的对账**、验收判据+证伪方式、自己犯过的错**及其复发点**）正是靠槽位空着才会被发现。

**两份的归属契约由 user-level skill `writing-handover-docs` 权威定义，本模板按执行者语境完整复述其可直接使用的形状。** HANDOVER 维护交接事实与状态，KICKOFF 是带 HANDOVER 小节引用的启动投影；两份都可完整写出读者完成任务所需的内容。下面槽位与 §6 冲突时以 §6 为准，并在本轮同步修正模板。

## `HANDOVER.md` 骨架

```markdown
# <主题> 交接

> **状态**：**草稿·未评审** / 进行中 / 已被接手（<会话或分支>）/ 已完成（落地 `<sha>`）/ 已失效（<原因>）
> —— 「草稿·未评审」是「上下文将满」紧急路径的合法状态，**过完评审闭环后必须改成正式状态**；从目录外一眼可辨。
> **核验基线**：`<sha>`（<YYYY-MM-DD HH:MM>）——晚于此且触及相关路径／契约／测试基础设施的 peer 提交可能影响下面的结论；无关 HEAD 前进本身不使证据失效
> **工作区**：分支 `<branch>` / worktree `<path>`；未提交改动 `<列表或“无”>`；未追踪 `<列表或“无”>`
> **已跑门禁**：`<命令>` → `<结果>`（<日期>）；未跑的写“未跑”，别留空

## 0. 入口指引

先读什么 → 再读什么。每份材料标明「什么时机才需要读」，避免接手方一上来读完全部。

## 1. 背景与本轮做了什么

已落地的改动，逐条给 `<sha>` 或 `file:line`。

## 2. 已确证的硬事实（**别再重新推导**）

| # | 事实 | 证据等级 | 证据 | 适用问题 / 边界 |
|---|------|----------|------|-----------------|
| 1 | … | 实测 / 源码读证 / 推断 | 命令与输出、`file:line`、探针路径 | 仅审计/计数/否定/完备性结论必填，其余填 `—` |

「推断」级的必须写明还差什么才能升到「实测」。**计数事实在证据栏写全对象、集合边界、基线与生成命令**（「N 个文件」≠「N 个调用点」）。**最后一列的触发词**：结论里出现「全部、只剩、无、N 个、完整、能通过」就必须填它回答的是哪个问题、集合边界与排除项——换个问题问，同一批事实的答案会不一样。

## 2.5 与冻结上游文档的对账（**有冲突必填；声称「无」要附检索证据**）

- **候选上游文档**（CLAUDE.md 文档路由 + 现有 plan 的引用 + DESIGN 活路径 + backlog 条目；`rg` 只做补漏）：`<逐份列出 + 每份的 disposition>`
- **检索词与范围**：`<当前术语 + 旧术语/关键 symbol + 搜了哪些目录>` —— 单关键词空结果**不能**支持「无冲突」。
- 若与本轮方向相左，写三句：上游当时判死的**依据** → 本轮哪几步在拆那个依据（**前提变了 ≠ 推翻裁断**）→ 落地后要同步哪几处（**同时列进 §3 当一条正式待办**）。

不写这一节，接手方会撞上两个互相矛盾的权威，正确动作只剩「停下来问人」。

## 3. 待办

每条固定五栏，缺一栏就不算写完：

### T<n> <标题>　【用户已批准 / 已裁决 / **待用户裁决** / 我的建议】

- **要做什么**：
- **验收判据**：什么现象出现才算成立（可跑的命令 / 可观测的输出）。
- **鉴别力正控**：要引入什么变异让这条判据变红；**已跑就附命令与输出，没跑写「待执行期正控」**。（写了一句变异 ≠ 鉴别力已验证。）
- **证伪方式**：什么现象出现说明这条路走不通——没有证伪方式的待办等于没有判据。
- **已知约束**：踩过的坑、不能碰的东西、依赖的前置。

## 4. 我犯过的错与成因

只列结论的交接会让接手会话**重犯产出这些结论的错误**。逐条写：我当时下了什么结论 → 错在哪 → 根因是哪种方法论失误 → 现在正确的说法是什么 → **复发点：T<n> 的哪个具体动作**。绑不上复发点的那条是纯自我检讨，压成一行或删掉。

## 5. 产物清单

| 产物 | 路径 | 已提交? | 它**没有**证明什么 |
|------|------|---------|--------------------|

探针/实验产物**就地**留在 `exp/<topic>/`（不迁走），README 必含「它没有证明什么」。

## 6. 环境与禁区

测试门禁现状（**标核验日期**）、本机跑不起来的命令、用户明确推迟的、绝对不能碰的。
```

## `KICKOFF.md` 骨架

```markdown
# 新会话 kick-off 提示词

复制下面整段作为新会话的第一条消息。

---

接手 <项目> 上一轮未完的工作。[HANDOVER.md](./HANDOVER.md) 是交接事实与状态的权威来源；本 KICKOFF 已完整带出启动所需的 gate、第一步与批准状态，并逐项引用对应小节。先读 HANDOVER §0，再按下面步骤启动。

## 硬性工作方式

<代码改动去哪、文档改动去哪、合并前要不要查 peer——完整写出启动前必须遵守的 gate 与动作，每条配一个 HANDOVER 小节指针。若第一步执行必须知道具体命令或参数，在此完整复述并沿用 HANDOVER 的核验基线；高 churn 细节可只留精确指针。>

## 待办与优先级

<按 HANDOVER 待办节的 T1–Tn 写批准状态、建议顺序和执行第一步所需的完整摘要；每条链接对应 T<n>。未裁决的明确写「需用户先定」。不要复制无法可靠同步的长证据链。>

## 这一轮反复踩的坑

三到五条，每条一行，指向 HANDOVER §4 的完整版。

## 测试与门禁（**核验于 <日期> / `<sha>`；先信任该证据，出现具体信号才复验**）

<完整写出接手第一步必须知道的 gate：哪个命令在本机跑不起来、哪些是用户已推迟不要顺手修、绝不碰的东西，并引用 HANDOVER §6。复验信号必须完整列出：真实失败、矛盾证据、基线后相关路径／契约／测试基础设施变化、异常 merge／integration 结果、会改变结论真假的环境／版本／运行实例等条件已陈旧，或用户明确要求核验。无关 HEAD 前进不触发重复全量验证。>
```

## 落盘顺序（顺序本身是纪律）

**正常路径是个闭环，不是一条直线**——评审前就提交、评审后不再提交，会留下「已提交的是评审前版本」的假完成：

1. **先把交接要引用的既有产物提交**：`git add -- <精确路径> && git commit -F <msgfile> -- <精确路径>`。只 `git add` 会把文件留在共享 index，被 peer 的无-pathspec 提交卷走。
2. **查 peer**：`git log --oneline ..master -- <相关路径>` + `git log -S<被改动那行的字面量>`，按 `writing-handover-docs` 的「写之前先查 peer」节处理命中。
3. **查冻结的上游结论**：候选文档逐份 disposition，填 §2.5（含检索证据）。
4. **起草 HANDOVER**（把第 2 步的 `<sha>` 填进头部核验基线）**+ KICKOFF + `docs/` 权威入口**——**入口也是产物，必须一起进评审**（它可能链错路径、复制状态事实、把错主题标成 `[wip]`，而 reviewer 看不到就等于没审）。
5. **过评审闭环**（视角定义见 `writing-handover-docs` 的「交接的默认两视角」节）：两视角的输入 = HANDOVER + KICKOFF + **入口 diff**；整改 → **回查 KICKOFF** → 恢复原 reviewer 复审 → 直到各视角均无 BLOCKER/MAJOR。
6. **最终一次提交**：放行后的 HANDOVER + KICKOFF + 各轮评审报告 + `docs/` 入口，**精确 pathspec 一起提交**。

**「上下文将满」的例外路径**（别和正常路径共用一套顺序）：先把头部状态标成 **「草稿·未评审」** 的 HANDOVER/KICKOFF 提交落盘保住可恢复性，把「过评审闭环 + 建 docs 入口 + 改回正式状态」写成 HANDOVER 里的一条待办。**交接是唯一不可重做的产物，未评审的草稿也远好过没有**——但它必须自报未评审，否则接手方会当成已核验的档案。
