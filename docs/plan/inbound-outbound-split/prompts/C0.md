## 背景 + 为什么

正在做一个大型 byte-critical 重构（把散布的「(clientFormat × targetEndpoint) cell 需要什么」知识收敛到集中化 2D 装配器 `CellAssembly`）。这是**纯结构重构**——现状 6 格 + 前向 + 反向翻译腿的**客户端可见字节 / oracle 必须全程不变**。要证明「不变」，先得有 golden 把当前行为**锁死在改动前的 HEAD 上**。

第二轮对抗 review 实测发现三条最高风险路径**当前没有逐字节硬证**：
- **(a) keepalive-ON 的 live anchored direct 流式**：唯一的 HTTP-app 逐字节 golden `tests/anthropic/direct-stream-golden-phase4.http.test.ts` 实测**关了心跳**（`streamKeepalivePingSec=0`, `streamCommitAfterSec=0`，见其 `:19` 注释），所以 **anchor 注入 + reconcile（commit 时关闭 anchor block@0 + 真实块 remap +1）的字节序列从没被锁**。现有 live anchor HTTP 测试（`live-post-commit-anchor-closeoff` / `live-pump-terminal-anchor-closeoff` / `keepalive-e2e` / `keepalive-buffered-anchor-e2e`）全是**结构/存在性断言**（`.some(s => s.index===0)` / `frameTypesInOrder` / `.toContain`），**不是逐字节** `.toBe(exact)`。唯一逐字节 anchor golden `tests/pipeline/buffered-anchor-golden.test.ts` 是 **driver 层 + buffered 路径**，不覆盖 HTTP-app 的 **live** 路径。
- **(b) reverse @messages 转发逐帧字节**：`tests/openai/reverse-cc-messages.it.test.ts` 用 `driver.inspectRequest`（dry-run wire）+ CC 累加器 oracle 证往返，**没有经 HTTP app 的转发 SSE 逐帧 byte golden**——即 cc/responses/gemini 客户端 `@messages` 反向腿：上游 Anthropic SSE → codec 逐帧翻译回客户端格式 → 转发的字节流没被逐字节锁。
- **(c) responses-ws + gemini 两跳终帧**：responses WS（`tests/responses/responses-ws.http.test.ts`）与 gemini via-responses 两跳（`tests/gemini/gemini-v4.http.test.ts:242`）的**终帧字节**没被逐字节锁（现有断言是结构/`frameTypesInOrder`/presence）。

C2（迁 /v1/messages 腿、动 direct anthropic 的 prepareWire + 反向供料）、C4（迁 /responses+ws、动 CC→Responses wire）会触达这三条路径。**不补这 3 条 byte golden，C2/C4 的「逐字节等价」就是空头承诺**——没有 oracle 能抓到 anchor reconcile 字节漂移 / 反向逐帧翻译漂移 / ws-两跳终帧漂移。

**关键纪律（golden 预捕获，`large-refactor` §4）**：golden 必须在**改动前的当前 HEAD** 上跑通 = 它锁的是**现状行为**。一个只在重构后才存在/才通过的 golden 什么都证明不了。C0 只加测试文件、**零生产代码改动**。

## 目标：补 3 条 byte golden（新增 3 个测试文件，零生产代码改动）

命名建议放 `tests/pipeline/` 或各自 vendor 目录，文件名前缀 `c0-`（便于识别是本重构的预捕获）。每条都要**逐字节** `.toBe(exact string)` 或 `.toEqual([exact frame array])`，**不是** `frameTypesInOrder` / `.toContain` / `.some`（那些是结构断言，抓不到字节漂移）。

### golden (a) —— keepalive-ON live anchored direct 流式（HTTP app）
- 文件建议 `tests/anthropic/c0-live-anchored-direct-stream-golden.http.test.ts`。
- 场景：direct `/v1/messages` 流式，`streamKeepalivePingSec>0` + `streamCommitAfterSec>0` + `FakeClock`；上游先 gated park（silent stall）→ `clock.advance` 越过 cadence → **live anchor 注入**（synthetic message_start? / anchor `content_block_start@0{text:""}` / empty `text_delta@0`）→ 释放 gate、上游续帧 + 终帧 → **commit reconcile**（anchor `content_block_stop@0` 关闭 + 真实块 remap +1）。
- **逐字节锁**转发给客户端的完整 SSE 文本（`res.text()`）——精确到 anchor 帧的 `event:`/`data:` 字节、真实块的 remap 索引、终帧。用 `FakeClock` 保证 cadence 触发时序确定（连跑 25× 无 flake）。
- 也保留 `direct-stream-golden-phase4` 的 `assertEventLineInvariant`（每合成帧带可辨识 `event:` 行，否则 @anthropic-ai/sdk SSEDecoder 静默丢帧）。
- **你要先跑一次、把实际转发字节 dump 出来，再把它 freeze 进断言**（golden 预捕获 = 锁现状，别凭想象手写期望值）。若发现 live 路径当前不注入 anchor（配置/时序没触发），调整 stall/cadence 直到确实走 anchor 注入+reconcile 分支（这正是要锁的分支）。

### golden (b) —— reverse @messages 转发逐帧字节（HTTP app）
- 文件建议 `tests/openai/c0-reverse-cc-messages-forward-golden.http.test.ts`（以及可选 responses/gemini 反向各一，若字节路径不同）。
- 场景：cc 客户端 `POST /chat/completions`，`model:"<claude-model>@messages"`, `stream:true`；fetch mock 返回上游 **Anthropic** SSE（text + tool_use + 终帧）；断言转发给客户端的 **CC** SSE 文本逐字节（`res.text()` `.toBe`）——证明 Anthropic→CC 逐帧翻译的转发字节被锁。
- 至少覆盖 cc→messages；若 responses→messages / gemini→messages 的转发字节路径不同（render 目标格式不同：Responses SSE / Gemini SSE），各补一条。**先 dump 再 freeze**。
- keepalive OFF（`streamKeepalivePingSec:0`, `streamCommitAfterSec:0`）让转发字节流确定（心跳不掺入）——这条锁的是**翻译逐帧**字节，不是 anchor。

### golden (c) —— responses-ws + gemini 两跳终帧逐字节
- 文件建议 `tests/responses/c0-ws-terminal-golden.http.test.ts` + `tests/gemini/c0-via-responses-terminal-golden.http.test.ts`（或合一）。
- responses WS：升级 WS → 转发上游帧 → **终帧**（`response.completed`/`failed`/`incomplete`/`error`）的字节 + 「终帧后一帧不转发」（`stopAfterFrame`）逐字节锁。参考 `responses-ws.http.test.ts:265/327`。
- gemini via-responses 两跳（Gemini 客户端 → CC → Responses 上游 → Responses→CC→Gemini render）：终帧的 Gemini SSE 字节逐字节锁。参考 `gemini-v4.http.test.ts:242`。
- **先 dump 再 freeze**。
