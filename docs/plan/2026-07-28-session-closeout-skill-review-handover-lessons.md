# session-closeout skill 交接教训回写评审

## 总判

**这批改动的经验内核值得进入 skill，但当前版本不应原样提交。** 它确实把一次真实交接中反复发生的五类失误固化成了会改变行为的动作：评审前分视角、计数写口径与命令、与冻结文档对账、新 oracle 写鉴别力正控、错误绑定本任务复发点。问题不在方向，而在三处执行契约尚未闭合：评审与提交顺序互相打架；“KICKOFF 绝不复述”同时又给出复述例外；V8/V9/V10 中只有 V10 接近可验，V8 测错了量，V9 把“写了一句变异”误当成鉴别力证据。

建议结论：**保留核心规则，修完下列 MAJOR 后再进 skill；删掉案例叙事与重复方法论，预计可收回本轮新增篇幅的一半左右，而不损失行为约束。**

## 发现

### [MAJOR] `.claude/skills/session-closeout/handover.md:105-113`、`.claude/skills/session-closeout/SKILL.md:9,15,29,79,83-88`——评审、提交、评审报告入库形成了无法按当前顺序完整执行的环

**不改会导致什么**：模板要求第 6 步先提交 HANDOVER/KICKOFF，第 7 步才评审，第 8 步再整改并重查 KICKOFF；但整改后的 HANDOVER/KICKOFF 没有再次提交这一步，第 7 步产生的评审报告也没有明确的提交点。正常照做会得到“评审前版本已提交、评审后版本与评审报告仍未提交”的假完成。与此同时，SKILL §1 要求“交付前”评审，§6 又要求被引用产物先提交再写交接；若交接要引用自己的评审报告，报告只有交接写完后才存在，当前顺序无法成立。

**具体修法**：把正常路径写成一个闭环，而不是线性九步：① 先提交交接引用的既有产物；② 起草 HANDOVER/KICKOFF；③ 两视角评审；④ 整改并重查 KICKOFF；⑤ 双方放行后，把最终 HANDOVER/KICKOFF、评审报告、`docs/` 入口一起用精确 pathspec 提交。为“上下文将满”单列例外：先提交明确标为“未评审”的可恢复草稿，评审与最终提交进入 HANDOVER 待办。不要让正常路径和紧急路径共用一套互相矛盾的顺序。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:17-29`——从一次 HANDOVER 实测直接推广成所有“交接 / spec / plan”的固定双视角，范围超出证据

**会改变的行为**：这段会让未来评审者不再泛泛地“各读一遍”，而是一个查判据鉴别力、一个按接手方动作走查；这是本轮最有价值的新增之一。

**不改会导致什么**：当前表把“接手方”与“数字算术”写成所有文档类产物的固定分工。HANDOVER 有明确接手者和执行步骤，plan 通常也有；spec 的使用者和失败形态不同，未必存在逐步接手动作，判据证伪也不只等于“数字对不对”。此外，“不要做另一个视角的事”会让 reviewer 遇到跨视角的同一 BLOCKER 时主动不报，错把降低报告重叠率置于完整性之上。

**具体修法**：§1 只保留通则：“派活前按产物失败面写出正交视角、每个视角的证据义务和主责；主责用于保证覆盖，不得禁止顺手上报跨视角 BLOCKER。”把这张经实测的双视角表移到 §6，明确标题为“HANDOVER/KICKOFF 默认双视角”。若要覆盖 plan/spec，把第二视角改成可替换槽位“实际执行方/使用方第一人称走查”，不要声称本轮已验证所有文档类型。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:24,114`——V8 用“发现交集大小”测正交性，测量对象错误且不可稳定复现

**不改会导致什么**：两个真正正交的 reviewer 可能从不同路径发现同一个致命问题，交集高反而说明问题稳健；两个低质量 reviewer 也可能各报一堆互不相干的 MINOR，交集为零却没有覆盖关键失败面。发现如何归并成“同一条”也没有规则，“重叠过半”缺分母定义，正常收尾时无法机械判断。

**具体修法**：V8 改测分工是否产生**增量覆盖**，而不是追求零重叠。顺手可观察的记录应为：① 每个视角是否完成其 prompt 指定的检查动作；② 各自发现的独有 BLOCKER/MAJOR 数；③ 任一视角若省略，是否会漏掉会改变执行动作的发现。证伪形态写成“某视角未执行其指定方法，或连续多次没有任何独有且会改变动作的发现”；重叠只记数据，不设“过半即失败”。删掉正文“零重叠”作为质量目标，可把它留在经验来源报告中。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:65,81,96`、`.claude/skills/session-closeout/handover.md:4,82-98`——“KICKOFF 绝不复述”与“实在要写的只写动作”不是同一契约

**不改会导致什么**：`SKILL.md:65` 写“其余一律指向……绝不复述内容”，`:81` 又允许复述动作；`:96` 明令 KICKOFF 放工作方式、批准状态、坑、测试门禁，这些内容通常已经存在于 HANDOVER。模板也直接给了这些槽位。模型无法同时满足“绝不复述”与“在这些槽里写具体动作”，最后只能自行解释例外，正是规则要消灭的漂移来源。

**具体修法**：改成正向输出契约，不再使用绝对禁令：HANDOVER 保存事实、理由、证据和完整步骤；KICKOFF 只保存启动前 gate、第一步动作、批准状态与 HANDOVER 指针。允许逐字重复一个**执行 gate**，但同一 gate 的理由、命令细节、数字和后续步骤只在 HANDOVER。同步把 V6 的检查对象从“有没有任何复述”改成“有没有重复事实、理由、数字、命令或完整步骤；允许的 gate 是否逐字且带指针”。这样“只写动作不写理由”才成为可判定例外。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:75,115`、`.claude/skills/session-closeout/handover.md:50-53`——V9 只能证明写了变异描述，不能证明判据有鉴别力；且与专门记忆重复

**会改变的行为**：模板给每条待办增加“什么变异能让它红”的强制槽位，会阻止作者只写“这个 oracle 专门咬 X”这一类纯意图声明。这个结构性槽位值得保留。

**不改会导致什么**：正文称“鉴别力本身是实验性主张”，但模板和 V9 只要求写一句假想变异，没有要求观察该变异真的使判据变红。作者完全可以再写一条听起来合理但同样错误的变异说明，V9 仍计为合规。更严重的是，V9 的断言是“写的时候真会被问一遍”，验法却在交接落盘后检查产物，无法观察问题发生的时点。相同方法已在 `docs/memory/methodology-new-oracle-discriminating-power-is-experimental.md:7-18` 完整说明，当前三处并存会漂移。

**具体修法**：分清两层。模板只增加结构槽：“**鉴别力正控**：要引入什么目标变异；实际跑过则附命令/输出，未跑写‘待执行期正控’。”SKILL 只保留一条动作规则并指向该方法论记忆，不复制“意图不是能力”等解释。V9 改测输出与执行证据：新建 detector/oracle 的待办是否明确了目标变异；若本轮已经实现该 oracle，是否记录了红的观测；若尚未实现，是否明确留作执行期 gate。不要把“写了一句”计为鉴别力已验证。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:76`、`.claude/skills/session-closeout/handover.md:28-32`——“适用问题”被强制加到每条硬事实，作用域过宽，会制造填充文本

**会改变的行为**：它会迫使作者区分“哪些边成环”和“还剩哪些跨界出边”，直接堵住本次交接最晚才暴露的 BLOCKER；这条经验值得保留。

**不改会导致什么**：模板把“本行结论只对哪个问题成立”加到所有硬事实。路径存在、commit 已落地、命令输出等事实并不依赖提问角度；强迫每行填写只会产生“本任务”“通用”之类无信息文字，增加表宽并掩埋真正需要限定范围的审计结论。正文自己也承认列形态越具体越容易失效，却仍将它无条件铺到整表。

**具体修法**：把列名改为“**适用问题/边界（仅审计、计数、否定或完备性结论必填）**”，普通事实填 `—`。正文触发条件写死：凡结论含“全部、只剩、无、N 个、完整、可迁移、能通过”等范围词，必须写它回答的问题、集合边界与排除项。这样槽位只在真实高危结论上改变行为。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:74,116`、`.claude/skills/session-closeout/handover.md:34-42,107`——V10 的正常流程可观察，但单关键词 `rg` 不能建立“没有冲突”的可信结论

**会改变的行为**：新增 §2.5 会迫使交接作者在冻结 spec/ADR/backlog 与新方向相左时写出旧依据、前提变化和后续 doc-sync；它直接解决了真实接手方会面对两个权威而停工的问题，应保留。

**不改会导致什么**：模板要求“没有则写无”，但唯一发现机制是 `rg -l '<主题关键词>'`。主题可能改名、旧文档可能只出现旧方案术语，单词空结果会把“没搜到”伪装成“无既有结论”。V10 的证伪条件只有“有而没写”，却没有办法在检查漏搜时知道“有”。这会制造一个新的空结果假绿。

**具体修法**：§2.5 增加一行检索证据：已读的已知上游文档、搜索目录、至少一个当前术语与一个旧术语/关键 symbol。优先从 CLAUDE.md 文档路由、现有 plan 的引用、DESIGN 活路径和 backlog 条目建立候选集，`rg` 只做补漏。V10 记录“候选上游文档是否逐份 disposition；搜索词和范围是否落盘”，证伪写成“已引用/已命中的上游文档未对账，或声称‘无’却没有检索证据”。这仍可在正常写交接时顺手观察，不需要额外实验。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:98`、`.claude/skills/session-closeout/handover.md:113`——要求 DESIGN、backlog、spec“各一条指针”违反按内容路由与同一事实单一源

**会改变的行为**：它会给活交接建立 discoverability 入口，避免接手方从 DESIGN→spec→backlog 一路走进旧方案；这条改动有明确行为收益。

**不改会导致什么**：不是每个交接都同时有相关 spec 和 backlog；无条件三处落指针会鼓励为了合规改不相关文档，并在三处复制 `[wip]` 状态。状态变化后要同步三处，正好制造新的漂移面，也与项目“同一事实只写一处”冲突。

**具体修法**：要求“至少一个由项目文档路由决定的 live 入口”，优先更新该主题已经存在的权威条目；其它相关文档只放指向权威入口的短指针，不复制状态与事实。模板第 9 步改成条件式清单：DESIGN 活架构现状、相关 backlog、相关 spec 中**实际存在且会把接手者导向旧路线的那些**必须更新；不存在的不得新造占位。

### [MINOR] `.claude/skills/session-closeout/SKILL.md:24-29,79,81,98`——案例叙事使 §1 与 §6 变成长段证明，增加跳读概率

**不改会导致什么**：本轮 SKILL 从 99 行/695 个 `wc -w` token 增至 126 行/923 个，约增加 33%；§6 从 32 行/211 增至 41 行/302，约增加 43%。新增不是单纯行数问题：多段都采用“2026-07-28 本轮发生了什么”的叙事，执行动作藏在段尾。每次收尾读取时，模型更可能扫描粗体结论而跳过真正的条件与步骤。

**具体修法**：SKILL 只保留触发条件、动作、完成判据；把以下内容留在两份 review 或方法论记忆，不在正文复述：`:24` 的零重叠战果、`:28` 的第二轮三条 MAJOR、`:79` 的“五个提交后十字路口”、`:81` 的三次漂移枚举、`:98` 的三次领域剥离故事。模板保留槽位与落盘顺序，不再解释完整事故。建议把 §6 的 HANDOVER 必含项改成六行 checklist，每行最多一个动作和一个缺失后果。

### [MINOR] `.claude/skills/session-closeout/SKILL.md:29,79`、`.claude/skills/session-closeout/handover.md:111`——“多轮直到双方都放行”重复三次，且没有定义整改后的复审边界

**不改会导致什么**：重复本身不增加执行力；“双方都放行”未说明每轮是全量重审还是只复核整改及其邻接影响，模型可能每轮从头重做，或只看原发现而漏掉整改引入的新缺陷。

**具体修法**：单一源放 §1：“整改后恢复原 reviewer；复核原发现、整改 diff、受影响的相邻契约，直到两个视角均无 BLOCKER/MAJOR。”§6 和模板只写“按 §1 评审闭环”，不复述轮次规则。

### [MINOR] `.claude/skills/session-closeout/SKILL.md:29,83-88`、`.claude/skills/session-closeout/handover.md:111`——评审报告入库有行为收益，但“为什么保存”与既有产物纪律重复

**这处该压缩因为它不再改变行为**：SKILL §6 已有“subagent 结论落进产物文件”，§1 又解释原始措辞价值，模板再解释一次。三处同时保留会漂移。

**具体修法**：§1 只写“每个视角维护一份可追加的评审报告；复审追加轮次；最终与交接一起提交”。§6 的通用产物纪律保留对 return-only 的禁令；模板只留提交槽位，不再写理由。

## V8/V9/V10 可验性结论

| 项 | 当前是否可验 | 结论 |
|---|---|---|
| V8 | **不可可靠验证** | 正常流程能看到两份报告，但“发现交集/过半”没有稳定归并单位，且不是正交性的正确代理。应改测指定方法是否执行、各视角是否带来独有且改变动作的 BLOCKER/MAJOR。 |
| V9 | **只能验形式合规，不能验主张** | 能数“写了几句变异”，不能据此判断 oracle 有鉴别力，也不能证明作者“写的时候问过”。应区分未实现阶段的变异计划与已实现阶段的红色观测。 |
| V10 | **方向可验，检索器不充分** | 查上游文档本来就是正常交接动作，符合“顺手观察”；但单关键词空结果不能支持“无冲突”。补候选文档清单、搜索范围/术语和逐份 disposition 后可验。 |

## 模板与正文同步结论

- **已覆盖**：计数口径与命令（HANDOVER §2 证据栏）、结论适用问题（新列）、冻结文档对账（§2.5）、判据变异（§3）、错误复发点（§4）、交接评审与 KICKOFF 回查（落盘顺序）、`docs/` 入口（落盘顺序）。
- **缺失的闭环槽位**：评审整改完成后的“最终提交”步骤；评审报告的最终提交归属；紧急“上下文将满”路径的“草稿未评审”状态。
- **正文有纪律、模板形状过宽**：“适用问题”只应约束审计/计数/否定/完备性结论，模板却约束每条事实。
- **模板有动作、正文契约矛盾**：KICKOFF 模板要求写具体 gate、坑与门禁，正文同时写“绝不复述”；必须先统一分工定义。
- **§2.5 尚缺证据槽**：模板能写对账结果，却没有记录“查了哪些上游文档、用什么术语查”的位置，无法证实“无”。

## 建议保留、压缩、删除清单

### 保留并加固

1. 交接默认使用“判据证伪 + 接手方第一人称走查”两个视角，但限定为 HANDOVER/KICKOFF，且主责分工不得禁止上报跨视角 BLOCKER。
2. 计数事实必须写对象、集合边界、基线和生成命令。
3. 冻结 spec/ADR/backlog 冲突对账，并把落地后的 doc-sync 作为正式待办。
4. 新 detector/oracle 必须写鉴别力正控；已经实现的必须记录实际红色观测。
5. 审计、计数、否定和完备性结论必须写“回答哪个问题/集合边界”。
6. 每条错误绑定 T<n> 的具体复发动作。
7. HANDOVER 每轮整改后重查 KICKOFF；评审报告落盘提交；live docs 有可发现入口。

**不改会导致什么**：`git status --porcelain` 只能观察工作区/index 是否相对 HEAD 干净，不能回答某路径是否包含在“该提交”里。遗漏某份评审报告时，只要它此前已被单独提交、被误删后工作区干净，或检查路径集合本身漏了它，第二时点仍可绿。“两次 status 取交集”也没有对应的集合语义：两个时点检查的是不同产物集合，不应求交集。这是一条典型的“文字声称机械，命令没有鉴别力”的新 oracle。

**具体修法**：V7 明确两套不同检查：

1. 起草前：对“将被引用的既有产物清单”运行 `git status --porcelain -- <精确路径...>`，输出必须为空；另用 `git ls-files --error-unmatch -- <路径>` 确认不是未追踪漏检。
2. 最终提交后：用 `git diff-tree --no-commit-id --name-only -r HEAD -- <闭环产物路径...>`（或 `git show --name-only --format= HEAD -- ...`）确认 HANDOVER、KICKOFF、每份本轮评审报告和 docs 入口**都在最终 commit 的路径集合中**；再用 `git status --porcelain -- <这些路径>` 确认没有提交后残留。

### [MAJOR] `.claude/skills/session-closeout/SKILL.md:112`——V7 第一时点仍把“status 空”误当成“路径已提交”

**实测正样本对照**：
