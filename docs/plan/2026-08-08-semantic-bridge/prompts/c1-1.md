# C1.1 —— ledger 类型契约与 declare/delta reducer

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**本片新增纯状态机模块，不接 wire、不写 sink、无生产调用者。**

## 背景

现有六个 translator 各自维护自己的 lifecycle 状态：A→R stream 有 `sequence`/`started`/`flushed`/block→index 映射/text buffer/reasoning buffer/signature buffer/tool arguments/usage/stop；R→A stream 有另一套；两个 non-stream 又各有一套。**同一领域事实在六处分别裁决**，于是多 reasoning 被压扁、encrypted-only 被丢、无 delta 的 function call 变空。

RFC §4 用一个 keyed item ledger 取代它们：每个 reasoning/text/tool item 有独立 identity、ordinal、authoritative final value 与 lifecycle；nested part（reasoning-summary / reasoning-content / text）各有自己的 declare→delta→done。

本片落类型契约与 declare/delta 累积。**terminal 是 C1.2，snapshot/fork 是 C1.3，别越界。**

## 必读

RFC §4「核心类型契约」全节。**类型逐字对齐，不得自行增删字段。** 冲突时改代码不改 RFC —— RFC 已过五轮对抗评审收口，你在实现中发现的「更好的字段」极可能是被评审否决过的。真觉得有问题，停下回报，不要自行改契约。

## 产出接口

```ts
createSemanticLedger(): SemanticLedger
// SemanticLedger.apply(update: LedgerUpdate): void
```

`LedgerUpdate` 的 declare/delta 分支（RFC §4）：`declare-item`、`declare-part`、`append-part-text`、`append-arguments`、`append-result-output`、`set-final-arguments`、`set-final-result-output`、`set-reasoning-metadata`。

## 本片要落的不变量

逐条来自 RFC §4「Ledger invariants」，**每条一个拒绝路径 + 一条单测**：

1. 每个 item key 与 part key **只 declare 一次**。
2. part 只能引用**已 declare** 的所属 item。
3. `sourceIndex` 在同 item ／同 kind 内唯一。
4. **declare 期 metadata 互斥**：call kind 只允许 `call`、result kind 只允许 `result`，其它 kind 两者都不得带。错配 **fail-closed**。
5. `CallMetadata` 在 call declare 时即完整存在；缺 `callId` 或 `name` 的 call **不进入 emitter**。
6. `ResultMetadata` 在 result declare 时即冻结关联 ID、error 与 source payload。
7. part delta 可多次；`.done` text 是权威值（本片只落累积与权威值写入，**冲突产生 observation 的部分留到 C3.1**，此处先留结构位）。
8. **reasoning visible 的唯一 owner** 是各 part 的 authoritative text 加 `reasoningVisibleKind`。ledger **不得并存第二份可独立写入的 summary** —— 这正是 A-5/A-6 单槽压扁的根因，别把它换个位置重现。
