# C3.4 —— 共享 JSON-value validator

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**纯新增模块，无生产调用者。**

## 背景

RFC §6.1（carrier canonical JSON）与 §8.1（structured output schema 序列化）**各自**要求同一件事：

> 先用共享 JSON-value validator 拒绝非法值，再调用项目已锁定的 `safe-stable-stringify@2.5.0`。

为什么不能省掉 validator 直接调库 —— **实测该库不会拒绝非法输入，它会静默有损地接受**：

| 输入 | 库的行为 |
|---|---|
| `Infinity` / `-Infinity` / `NaN` | 变成 `null` |
| `undefined` | 直接省略该键 |
| `bigint` | 数值化 |
| 循环引用 | 写成 `"[Circular]"` |

这些都不报错。对 carrier 来说，这意味着一段被悄悄改写的 opaque state 会被当成合法值编码进 wire；对 schema hash 来说，意味着两个语义不同的 schema 可能得到同一个 hash。

## 为什么这一片单列、且必须在 C4–C7 分叉之前

计划初稿把 validator 放在 C6.1 里创建、让 C7.1 复用，同时又要求 C7 先合并 —— **这是自相矛盾的**：C7 的实施者从 C3 拉分支时该文件还不存在，要么 typecheck 不绿（违反 G1），要么自己造第二份。

而**两份 validator 必然漂移**，且 C7.1 自己的 mutation（只测 prefix↔kind 联合校验）**抓不到这种分叉**。所以它前移为四组并行的共同前置。

## 产出接口

```ts
assertPlainJsonValue(value: unknown): asserts value is JsonValue
```

fail-closed，抛 typed error（**稳定 error code，不要让调用方解析英文 message**）。

**C6.1 与 C7.1 都 import 这一个。** 它们不得各自再写一份。

## 步骤

1. 递归校验。六类一律 fail-closed：**bigint、function、symbol、undefined、cycle、非有限数字（`Infinity` / `-Infinity` / `NaN`）**。
2. 六类逐条正控（每类一个用例，断言抛出且 error code 正确）。
3. 正样本对照：合法的嵌套对象／数组／字符串／有限数字／`null` 全部通过。**只测拒绝不测通过，会让一个「什么都拒绝」的实现照样全绿。**
4. **唯一性结构守卫**：断言全仓只存在一处 JSON-value 校验实现（冻结命中集合）。这条守卫防的是 C6/C7 并行时各造一份 —— 没有它，漂移发生时不会有任何测试变红。

## 验收

- `bun run typecheck` 绿。
- `bun test tests/pipeline/semantic/json-value-validator.unit.test.ts tests/architecture/json-value-validator-uniqueness.unit.test.ts` 全绿。
- **无生产调用者**：`rg 'json-value-validator' src/ | rg -v '^src/lib/pipeline/semantic/'` 为空。
- `bun run test:backend` 无回归。
- **G2 wire 字节 golden 对账**（C0.2 锁的那组）：本片纯新增，字节必须完全不变。

## Mutation（必做）

去掉 cycle 检测、直接把值交给 `safe-stable-stringify` → cycle 用例变红。

`[hard]` **核对失败信息来自 validator 缺位**，而不是「库输出的 `"[Circular]"` 恰好不等于期望值」—— 后者是旁路断言代咬，它会让你以为门还在，其实已经失效。

撤销用 exact reverse patch（先有 patch、再有变异；`git apply --reverse --check` 失败就停下问用户）。
