# C2.2 —— candidate lineage 与 policy resolver

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**仍不改变 production writer：lineage 只被记录、不被消费。**

## 背景

RFC §6 的 `CandidateTranslationLineage` 要把「谁是谁的后代、因何而生、用哪份 policy」显式化。现有代码里这些信息散落在 coordinator 的 settle 语义中，没有统一载体。

## 关键事实：三个 boundary 点性质不同

`src/lib/pipeline/generation/coordinator.ts`（**开工先复核行号，会漂移**）：

| 锚点 | 当前语义 | RFC 对应 |
|---|---|---|
| `:182` `runRecovery`（`:197` 父 `settle({verdict:"failed"})`） | **父失败、子重开** | fallback 性质。父无可保留输出时走 discard |
| `:215` `runContinuation`（`:221-222` 父 `settleDispatch({verdict:"continued"})` + `settle({verdict:"continued"})`） | **父已部分交付、子续接** | continuation 性质。父的 committed prefix 在客户端 wire 上，**不清空** |
| `:234` `raceReadyCandidates` | 多候选竞争的**赢家判定** | 不是 segment 新建点，是「哪个段成为权威」的判定点 |

`[hard]` **`runRecovery` 与 `runContinuation` 不得共用同一个 segment 构造函数。** 它们的父段处置方式相反：前者父段作废，后者父段是已交付前缀。用一个函数处理会把这个差别抹掉，而抹掉之后测试仍会绿——直到某次 continuation 把父段的已交付内容又发了一遍。

## 产出接口

RFC §6 的 `PairTranslationPolicy` 与 `CandidateTranslationLineage`，逐字对齐。

```ts
resolvePairPolicy(snapshot: TranslationConfigSnapshot, source: ModelIdentity, target: ModelIdentity): PairTranslationPolicy
```

## 要落的不变量

1. 每个 candidate 在 **final route 确定后**，从**同一** ingress snapshot 按完整 source／target `ModelIdentity` 解析**一次** policy。
2. candidate 改变 route → 生成**新的** candidate／dispatch／segment 和 policy；**祖先 policy 不变**。
3. retry、hedge、fallback、continuation **都创建 candidate-local ledger**，不得共享可变 item state。要复用已冻结的请求语义，只能从 immutable ingress baseline 或已提交 segment snapshot **fork**（C1.3 的 `fork()`）。
4. **未命中 rule 时用全局安全默认**（RFC §6.2）：unknown carrier `reject`、structured output `strict`、context management `reject`。
5. 命中有效 rule 但省略可选字段时**也用这些公开默认**；**命中失效 rule 不等于未命中**（失效 rule 的处理在 C6.2，本片只需把「失效」这个状态表达出来，不要让它静默回落成默认 policy）。

## 步骤

1. 写 policy resolver 与 lineage 类型。
2. 在 coordinator 三个点接线：`runRecovery` 建 fallback 性质的新 segment，`runContinuation` 建 continuation 性质的新 segment（**继承父 ledger 的已提交前缀**），`raceReadyCandidates` 只标记权威归属。
3. 单测覆盖上述五条。
4. **回归保护**：跑既有的 retry／hedge／continuation e2e，证明现有行为字节不变。
