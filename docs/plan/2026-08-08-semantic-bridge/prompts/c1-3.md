# C1.3 —— immutable snapshot、fork 与 property tests

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**仍无生产调用者。这是 C1 的收口片。**

## 背景

RFC §3.2 要求 stream 与 non-stream **强制消费同一 semantic model**：stream emitter 消费有序 `LedgerTransition`，non-stream emitter 消费 finalized `LedgerSnapshot`。「parity 是结构属性，不是两份实现靠 fixture 维持的愿望」——本片提供那个结构。

RFC §4 还要求 `fork()` 可结构共享 immutable history、但后续状态隔离；ledger 只存活于 candidate／dispatch／segment，**不得跨 retry 或 hedge candidate 共享可变实例**。

## 产出接口

```ts

snapshot(): LedgerSnapshot        // immutable，结构共享

```

## 步骤

1. **immutable snapshot**，结构共享（不是深拷贝——深拷贝会破坏 RFC §13 的复杂度要求）。
2. **fork 写时隔离**：fork 后任一侧的写入都不影响另一侧。
3. **Property 1 —— 多 reasoning 不串槽**：任意交错的多 reasoning item declare/delta/done 序列，各 item 的 visible 与 opaque 永不互串。这条直接对治 A-5/A-6 的单槽压扁。
4. **Property 2 —— function args authoritative done**：三类输入（无 delta／有 delta 且与 done 一致／delta 与 done 冲突），最终 snapshot **一律取 authoritative value**。冲突时产生 observation —— observation 类型在 C3.1 才落地，本片**先留结构位**（如返回一个待填的冲突记录），不要自己发明 observation 类型。
5. **复杂度守护**：时间 O(events + items)；ledger 内存 request/candidate-local O(items + delta bytes)，**不得 process-wide 累积**。加一条断言：跑完一个 ledger 生命周期后，模块级不残留引用。
