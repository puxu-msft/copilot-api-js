# C0.3 —— mutation registry

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**本片零生产改动，纯文档。**

## 背景

RFC §12 的验收矩阵有十七行，C0.2 又建了九类缺陷断言。这些判据横跨 C1–C11 十余个 commit、多个 implementer。如果不把「每条判据的 exact mutation」制度化，实际会发生的是：每片各自口头声称「我做了 mutation 对照」，而没人能复核那次 mutation 到底改了什么、失败是不是来自目标机制。

**变异对照证明的是「已写的那条判据在错误实现下会红」，它证明不了「判据覆盖了该覆盖的面」。** 本片建立的 registry 让后者也可被审计。

## 目标

建立一张表，把每条阻断式判据映射到一个**可执行的** mutation 描述。

## 改动锚点

- Create `tests/openai/semantic-bridge/mutation-registry.md`

（进度文件约定已由 `docs/plan/2026-08-08-semantic-bridge/progress/README.md` 提供，本片不再新建。）

## 表结构

| 列 | 要求 |
|---|---|
| 判据 ID | 对应 RFC §12 矩阵行，或 C0.2 的 KNOWN-LOSS 编号 |
| 目标机制 | 这条判据到底在守什么。一句话，具体到函数 |
| mutation | **改哪个文件的哪个函数的哪一行，改成什么**。不接受「注释掉相关代码」这类不可执行描述 |
| 期望变红的用例 | 精确到用例名 |
| 失败来自目标机制？ | 是/否/未验。**核对过失败信息确实来自该门、而非旁路断言或另一条路径**才填「是」 |
| 落实于 | 哪个片负责跑这条 |

## 步骤

1. RFC §12 矩阵十七行逐行登记。
2. C0.2 的九类 KNOWN-LOSS 逐条登记。
3. 每条的 mutation 列写成**别人照着能复现**的粒度。
4. 表头注明三条纪律（下面这段直接写进文件，它是给后续 implementer 看的）：

> **mutation 不变红有三解**：①测试没咬住 ②mutation 没生效 ③fixture 造不出被测状态。排除前两条后，**先写探针问「这个状态真的存在吗」**，别改断言凑绿。
>
> **变异注入与撤销**：先构造只描述该变异的 exact patch → `git apply` 注入 → `git apply --reverse` 同一份冻结件撤销。`--reverse --check` 失败或与当前改动重叠就停下问用户。**绝不整文件 `git checkout`**。
>
> **registry 是明细 SSOT，任何汇总是派生视图**。别在别处另维护一份计数。

## 验收

- registry 行数 ≥ RFC §12 矩阵行数 + C0.2 的 KNOWN-LOSS 条数，且**逐行可追溯到来源**。
- 交叉验证用两种不同原理的方法数行数（如 `rg -c '^\|' ` 与人工数矩阵行），不一致就挖到解释得通为止。
- 每行的 mutation 列都能被另一个人照着执行。自查判据：把这一列念给一个没读过代码的人，他知道该打开哪个文件吗？
