# C2.1 —— ingress config snapshot

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**本片开始碰生产文件，但仍不改变 production writer。**

## 背景

RFC §6 要求：ingress 在**任何 route／candidate 分叉前**捕获一次 `TranslationConfigSnapshot`，并把它的 identity 冻结到 `RequestEnvelope`。此后每个 candidate 只能从这份**共同** snapshot 解析 policy；热重载只影响后续 ingress。

为什么必须这样：fallback 会改变 target identity，continuation 会创建新 candidate。如果后代 candidate 各自重读热配置，同一个请求的不同 segment 就会按不同配置翻译，而 History 里看不出来。

## 现有可复用的模式（先读）

`src/lib/pipeline/envelope.ts` 已有一个**同类字段**：`requestState`。它的语义是「request-lifecycle-STABLE 的 outbound-leg 供给，由 InboundCodec 的 `parse` 捕获一次，经 `with()` **按引用保留**，与 replace 语义的 per-attempt `prepareHints` 刻意分开」。

**照抄这个模式。** `translationConfigSnapshot` 与 `requestState` 的生命周期完全一致：ingress 捕获、后代只读、retry 不得覆盖。

## 改动锚点

- Create `src/lib/pipeline/semantic/config-snapshot.ts`
- Modify `src/lib/pipeline/envelope.ts` —— 新增 `readonly translationConfigSnapshot?`，**不进 `with()` 的 patch 集**（与 `requestState` 同待遇，见该文件 `with()` 签名的注释）
- Modify inbound codec 的 `parse`（与 `requestState` 同一捕获点）
- Create `tests/pipeline/semantic/config-snapshot.unit.test.ts`

## 产出接口

```ts
type TranslationConfigSnapshot = Readonly<{
  snapshotId: string
  // 冻结的 model_translation 视图
}>
captureTranslationConfigSnapshot(): TranslationConfigSnapshot
```

`snapshotId` 进 History（C3.2 消费），所以要稳定且可比较。

## 步骤

1. 在 ingress 捕获一次，冻结进 envelope。
2. **只捕获与读取，不加任何消费者** —— 本片不改变任何翻译行为。
3. **热重载隔离测试**：起一个在飞请求 → 改配置 → 断言该请求的 snapshot 不变 → 下一次 ingress 的 snapshot 才变。

⚠️ 注意 `config.yaml` 每请求会覆盖 `setStateForTests` 的 config-managed 键。写测试时若发现「同一 policy 一半听测试一半听配置」，那是这个已知陷阱，不是你的 bug——用配置注入而非 `setStateForTests` 钉这些键。

## 验收

- `bun run typecheck` 绿。
- 既有 config 热重载测试全绿（`bun test tests/config/`）。
- `bun run test:backend` 无回归。
- snapshot 无消费者：`rg 'translationConfigSnapshot' src/` 只出现在捕获点与类型定义。

## Mutation（必做）

让后代 candidate 重新读热配置（而非用 envelope 上的 snapshot）→ 热重载隔离用例变红。
