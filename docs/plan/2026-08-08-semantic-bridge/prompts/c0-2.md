# C0.2 —— 缺陷语料与现状锁定

> 开场先读 [README.md](README.md) 的通用红线与必读清单。**本片零生产改动，纯测试。**

## 背景

RFC §1 列出九类**已复核确认**的缺陷。本片为每一类建立 fixture，**在改动前的旧码上跑通**，并显式标注「当前是已知有损」。这些断言是后续 C8–C10 逐条转绿的对照物。

这是 golden 预捕获（skill `large-refactor` §4）：一个只在重构**之后**才存在的 golden 什么都证明不了，它只是编码了新代码的行为。必须先在旧码上锁住现状。

## 九类缺陷（逐条覆盖，缺一即本片未完成）

对照 RFC §1，每条都已复核到 `file:line`（见 [../plan.md](../plan.md) 锚点表 A 段，**开工先复核行号**）：

1. **官方 OpenAI SDK 无法消费部分 A→R 流式事件** —— 用 C0.1 的 `finalResponseOf` 驱动。
2. **两向 request translator 重排 text/tool 顺序** —— A-1 `:217-255` 的 `unshift`；A-4 `:148-277` 的 `foldInputItems` 三槽位重组。
3. **server-tool 四格均未闭合** —— A-1 `:243-245`、A-2 `:132-136`、A-3 `:287-291` 的 drop。
4. **Scenario B 只接 response renderer**（request consumer 漏接）。
5. **多个 reasoning item 被单槽压扁** —— A-5 `:163-173`、A-6 `:129-139` 只有一个 `reasoningEncrypted`。
6. **non-stream encrypted-only reasoning 被丢** —— A-5 `:213-222` 只有 text 非空才生成 thinking。
7. **无 arguments delta 的 function call 变成空 input** —— A-3 `:258-271` 不读 start block 的完整 input，flush 靠 `argumentParts.join("")`。
8. **incomplete payload 仍发 completed event** —— A-3 `:482-501` 无条件发 `response.completed`，只把 status 填成 incomplete。
9. **顶层 capability 静默裁剪** —— A-1 `:150-155`（`context_management`／stop sequences／`top_k`）、A-4 `:122-128`（`previous_response_id`／context management／truncation）。

## ⚠️ fixture 清单按「旧码可否表达」二分

RFC §11 的 C0 清单里有一部分**在旧码上根本无从表达** —— 例如「child part 开放时提前 finish item／response 的拒绝正控」，它需要 part／item／response 三层 terminal，而那要到 C1.2 才存在。本片是**零生产改动**的片，若把这类断言塞进来，你会撞上一道过不去的门，唯一出路就是弱化或删断言，**那会让整道门失效**。

- **本片只做旧码可表达的**：上面九类 KNOWN-LOSS、nested parts 与 multi-reasoning 的**现状**、encrypted-only 的**现状**、`.done.arguments` 三类的**现状**、server-tool 四格现状、Scenario A/B 四腿、同模型原样回送、G2 wire golden。
- **需要 C1.2 之后才能表达的**（三层 terminal 的拒绝正控、response terminal provenance 合成）→ **不在本片**，已移到 C1.2 的验收。
- **正样本跑出来是红的怎么办**：`[hard]` **不要改断言**。那说明你发现了第十类缺陷 —— 登记进 KNOWN-LOSS 并回报，这是发现不是障碍。

## Mutation（必做，三条，各自指名期望变红的用例）

1. **encrypted-only**：翻转 `src/lib/openai/translate/responses-to-anthropic.ts:213` 的 `if (reasoningText.length > 0)` 条件（改成 `>= 0`）→ encrypted-only 那条 KNOWN-LOSS 变红。
   ⚠️ **不要用「把 `reasoningEncrypted` 改成数组」当这条的 mutation**：该字段的基数与 `:213` 这道门**无关**，改它**不可能**让 encrypted-only 变红（本计划初稿就是这么写的，是错的）；而且改成数组会先撞 `buildSyntheticReasoningSignature` 的签名，patch 本身跑不通。
2. **multi-reasoning**：把 `:172` 的覆盖赋值（`reasoningEncrypted = item.encrypted_content`）改成累加 → multi-reasoning 那条 KNOWN-LOSS 变红。
3. `[hard]` **wire golden 的灵敏度对照**：改动 production wire 的**一个字节**（例如改 `anthropic-to-responses-stream.ts` 某个 `event:` 名，或改一个 usage 字段值）→ **至少一条 wire golden 变红**。

   **这条不做，你交付的整组 golden 就没有判别力。** 它是 C2.1–C8.3 十余片 G2 的唯一机械判据 —— 若你的捕获点取浅（捕在 translator 输出而非**真实客户端字节**）或归一化过度，后续每一片的对账都是空转，而且**不会有任何信号提示**。把这条的结论写进 C0.3 的 registry。

⚠️ **变异的注入与撤销方式是强制的**，因为这是一个你没有提交的生产文件：

1. **先构造一份只描述该变异的 exact patch**，用 `git apply` 注入它。顺序是「先有 patch、再有变异」。
2. 撤销时对**同一份冻结的 patch** 执行 `git apply --reverse`。先跑 `git apply --reverse --check`，失败或与当前改动重叠就**停下问用户**，不要强推。
3. **绝不用整文件 `git checkout` / `restore` 撤销** —— 共享树里那个文件可能同时含主会话或同伴的未提交 WIP，整文件回退会连它们一起抹掉。

反面做法（别做）：在注入变异前跑 `git diff <file> > /tmp/x.patch` 当基线。那一刻变异还没注入，这份 diff 捕获的是**真实实现或同伴的 WIP**，反向应用它等于把这些改动删掉。

做完 `git diff` 复核：出现不属于该 patch 的改动就停手。
