## 与 RFC §6 的四处偏离（均已同步改 RFC 正文）

写 RFC 时这些字段是按语义命名的抽象名字；对着**真正铸造这些 id 的代码**逐条核，四条站不住：

1. **`candidateId`／`dispatchId` 不再是裸 `string`，改用既有 branded handle。** `beginCandidate`（`dispatch-scheduler.ts:50`）铸的 `CandidateHandle` 已被 History V3 投影为 `candidateId`（`projection.ts:281`）。裸 `string` 会让 dispatchId／segmentId／candidateId 互相顶替而无诊断——换成 branded 后 typecheck **当场逼出 5 个传裸字符串的站点**，这就是 brand 有判别力的正样本证据。
2. **删掉 `cause: "retry"`。** retry 是同一 candidate 下的新 **dispatch**（`dispatch-scheduler.ts` 在 `for(;;)` 里对同一 candidate 反复 `beginDispatch`），不创建 candidate；其对应概念是低一层的 `DispatchReason`。
3. **`CandidateTranslationLineage` 删掉 `dispatchId`。** 该记录随 candidate 出生，那一刻没有任何 dispatch；而一个 candidate 之后拥有 *N* 个 dispatch。钉一个 dispatch 对每个重试过的 candidate 都是假话，却仍以权威语气呈现。RFC 自身结构佐证了这个分界：`TranslationObservation`／`AuthorityIdentity`／`CandidateHistoryDiagnostic` 都是**在 dispatch 已存在之后**铸造的，各自带自己的 `dispatchId`。
4. **`cause` 与 `CandidateRole` 三值重合、两端分歧，必须显式换算。** `fallback` **宽于** `recovery`：`runRecovery`（`coordinator.ts:212`）丢弃父 upstream 并 settle `failed`，客户端未收到任何字节，那只是 pre-commit fallback；**post-commit fallback（已发不可撤回字节后切模型）今天没有任何 candidate role**，coordinator 唯一能表达的 post-commit 交接是 `runContinuation`。**这个缺口归 C2.3。**

### 一次被自己证伪的中间结论

第 4 条我一度写成「`fallback` 就是 `recovery` 的重命名」，并把 `LineageCause` 改成 `CandidateRole` 的别名。提交前去查 RFC 里 `fallback` 的全部出现（`fallbackId`、`provenance: "fallback"`、pre/post-commit 两相，几十处）才发现它是承重概念、且 RFC 明确要求 post-commit fallback 与 continuation 并存。**该等式未经提交即被撤回。** 记在这里是因为它正是本仓反复踩的形态：把「看起来对应」当成「就是同一个」。

## 三个设计选择及理由

- **接线点在 driver 的 `createCandidate`，不在 generation coordinator。** coordinator 是协议中立组件、对 translation policy 一无所知；为了搬运数据而教会它 bridge 的词汇，正是 lineage 记录本身（复用既有 handle 而非另立 id）在避免的抽象泄漏。
- **registry 按 `RequestContext` 身份索引的侧表，不做成 `RequestScope`／`RequestContext` 的字段。** 两种都能work，`RequestScope.translationConfigSnapshot` 是后者的先例；但 `src/lib/context/` 目前**没有任何指向 `~/lib/pipeline` 的 import 边**，加字段会新开一条。选 ctx 而非 coordinator 作键，是因为 lineage 是 per-**请求**：continuation 腿会对同一 ctx 开新 coordinator，两截属于同一条记录。
- **segment 由 candidate 派生，不另设计数器。** RFC §6 让 fallback／continuation boundary 在同一动作里创建新 candidate **与**新 ledger segment，且禁止两个 hedge candidate 共享可变 ledger——今天二者 1:1。若将来 boundary 需要在**不开 candidate** 的情况下落地，这条派生就是会断的地方，而且断得很响（同一 candidate 内两个 boundary 会撞同一个 id，不会静默交错）。

## 接线暴露的一个既有缺陷（已在本片修掉）

`createDriverRecordingPort` 的兼容路径用**每个 recording port 一个计数器**铸 `compat-candidate:N`，而 port 是**每个 coordinator** 建一个、一个请求却可能建多个（continuation 腿开新 coordinator，ctx 不变）。于是第二个 coordinator 重新铸出 `compat-candidate:1`——**同一请求内两个不同 candidate 共用一个 id**。

- 显性化方式：本片按 `CandidateHandle` 建 per-request 表，`register` 撞重直接抛错，`driver.unit.test.ts` 的多策略遥测用例因此变红。
- 修法：修**命名空间本身**（句柄按 port 加判别前缀），不是教 registry 容忍重复——后者会把 RFC §6「祖先 policy 永不被改写」这条不变量拆掉。
- 作用域：**explicit 路径从未受影响**（其句柄来自请求作用域的 recorder）。全仓无任何测试断言该字面量。
