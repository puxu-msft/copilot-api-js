## 为什么这样实现

registry 以三个来源清单为入口：RFC §12 每一行、C0.2 九条 KNOWN-LOSS、C0.1／C0.2 实际执行 mutation。每一项使用全局唯一 ID，Registry 第一列必须与三个来源清单 ID 并集精确相等。这样验收输出直接给出缺失项与多余项，避免行数门被重复行或整类漏项绕过。

RFC 与 KNOWN-LOSS 的目标机制登记为长期 gate；尚未执行的计划 mutation 明确写“未验”。实际 mutation 单独以 `ACT-*` 登记，即使它与某条 LOSS mutation patch 相同也不合并，因为第三来源要求保留“本片真实做过什么、是否咬住”的历史事实。

## 来源枚举与交叉验证

- RFC §12：从 `git show plan-semantic-bridge:docs/rfc/2026-08-08-anthropic-responses-semantic-bridge.md` 的表格逐行读取，并与 kickoff 声明的矩阵规模及 registry `RFC-*` ID 清单交叉对账。
- KNOWN-LOSS：用 Bun JUnit reporter 运行时枚举 `known-defects.unit.test.ts` 的 testcase name，再映射到九个 `LOSS-*` ID；不用源码文本计数。
- 实际 mutation：从 `progress/c0-2.md`、C0.1 提取提交与本会话 frozen patch／失败输出逐条还原；包含一次未咬住的 reasoning-before-fixture 探测、四次 `test.skip` 删除负控、header/status 三维 digest 正控，以及 encrypted-only／redacted 缺陷字节正控。

## 已作废的路

不采用“registry 行数不少于来源计数”：重复一条即可掩盖另一条缺失，且无法指出缺失 ID。不把实际 mutation 折叠到 RFC／LOSS 行：折叠会丢失已执行 patch、失败机制和“fixture 当时不含 reasoning”的关键反例。

## 下一步与验收

后续实现者执行某行 mutation 后，应只更新该行“失败来自目标机制？”与可执行 patch 描述，不另建汇总。C0.3 收口要求用解析脚本对来源清单与 Registry 第一列做双向差集；实测 `source - registry = []`、`registry - source = []`。该集合由 RFC 17 个、KNOWN-LOSS 9 个、实际 mutation 20 个 ID 组成；这些值只是本次实测说明，权威仍是明细集合，未来必须重跑双向差集而非比较数字。独立评审还需复核每行描述能否被未读代码的人执行。
