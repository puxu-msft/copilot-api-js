## 为什么这样实现

registry 的 RFC 行以 RFC §12“性质”原文作 join key；一条 RFC 性质可拆成多个独立 mutation 臂，但每个臂有独立 ID。Scenario A／B 拆成两方向各自的 on/off 腿，pre-commit retain 拆成 wire effect／空 segment／flush failure，observation 拆成 single-stage／wire ACK／空 segment 归属／semantic effect；前向三点 seam 与双向 cutover 也逐点拆开，避免一条描述里的多个 patch 无法独立执行与裁决。

KNOWN-LOSS 的 join key 是 Bun 注册的完整 testcase name，必须一一对应。实际执行记录继续以 `ACT-*` 独立保留，即使 patch 与 LOSS 行相同也不合并，因为它们记录的是“本片确实做过什么、失败是否来自目标机制”的历史事实。

## 外部来源锚定

`tests/openai/semantic-bridge/mutation-registry-coverage.unit.test.ts` 建立两条外部机械门：

- RFC：直接解析 `docs/rfc/2026-08-08-anthropic-responses-semantic-bridge.md` §12 的表格首列，要求每个登记 join key 都存在且每条 RFC 性质至少被一个 mutation 臂覆盖；允许一条性质拆成多个独立臂。
- KNOWN-LOSS：guard 在临时目录生成 JUnit report，实际执行 `known-defects.unit.test.ts` 后从运行时 testcase 集合提取完整 `KNOWN-LOSS：...` 名称，要求与 `LOSS-*` join key 一一对应；不读取源码文本计数，避免注释、helper 或参数化命名污染。
- `ACT-*`：C0.1／C0.2 没有独立机器可枚举的外部来源，明确保留人工复核门；对照对象是 C0.1／C0.2 进度、冻结 exact patch 与失败输出。

## 已作废的路

不采用同文件手写“来源清单”和 registry 再做双向差集：两边同时漏项时仍会假绿。不采用行数门：重复一行即可掩盖缺失。不把多条独立 mutation 臂压成一行：那会让 implementer 自选改哪一臂，无法形成 exact patch。
