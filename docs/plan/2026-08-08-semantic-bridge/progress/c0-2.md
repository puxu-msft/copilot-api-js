## 为什么这样实现

九类 KNOWN-LOSS 直接调用六个现有 translator，断言当前有损结果；修复这些缺陷时，旧结果断言会变红，迫使 C8–C10 显式更新。G4 守护走同模型 Anthropic request rewrite，并构造完整的 thinking／redacted_thinking／text／tool_use 加配对 tool_result 回合，避免 orphan-tool 清理把不合法 fixture 的失败误判为 G4 回归。

G2 wire golden 使用官方 SDK 的 custom `fetch` 访问 `serveInProcess()`，在 localhost HTTP `Response` 到达 SDK、但尚未被 SDK 解析前 clone 并读取完整实体字节。十六条 golden 覆盖两方向 × stream／non-stream × retry／no-retry，并额外分别覆盖两方向的 stream reasoning、stream 工具、non-stream reasoning 与错误腿。Bun snapshot 可被 `bun test -u` 静默重写，因此测试文件内另有固定 byteLength／SHA-256 权威表；digest 只能随对应 C9／C10 cutover 在同一个经评审的 commit 更新。

## 试过但不成立的路

最初用 wire mutation 改 `response.reasoning_summary_text.delta`，八条基础 golden 仍绿。按“mutation 不红有三解：测试没咬住／mutation 没生效／fixture 造不出状态”排查：patch 已实际生效，测试捕获点也在真实客户端边界，最终确认 fixture 完全没有 reasoning，属于第三解。没有调整 golden 迁就 mutation，而是先用基础 fixture 必经的 text event 完成 wire 判别力正控，再新增专门携带 summary 与 encrypted content 的 reasoning golden，并对 reasoning event 单独重跑正控。

reasoning golden 的 mutation 将 `response.reasoning_summary_text.delta` 改一个字节为 `response.reasoning_summary_text.deltb`；目标用例变红，SDK 可见 summary 由 `reasoning summary golden` 变为空，证明该内容域已被 wire gate 覆盖。

六条均以 frozen exact patch 做过灵敏度对照：工具参数 delta（两方向）、non-stream reasoning 文本／summary（两方向）、共享 503 rate-limit body（两方向错误腿）各自变红；撤销前均先通过 `git apply --reverse --check`。

## 下一步与验收

C0.2 无剩余实现项。后续 C0.3 把九类 KNOWN-LOSS 与本片 mutation 结果登记进 registry；验收时应复跑 `bun test tests/openai/semantic-bridge/`，并把 golden fixture 的内容类型覆盖面本身作为审计对象：某类内容未出现在 fixture 中，则整组 byte golden 对该类完全失明，本片发现的 reasoning 缺口即实例。

补充实证：golden 覆盖面必须按翻译方向分别盘点，不能只问“整组有没有 reasoning”。本轮连续漏了两次：第一次八条基础 golden 两方向均无 reasoning；第二次补了 R→A reasoning 后，A→R 的 Anthropic `thinking`／`signature_delta` 仍为零。现在测试内用正向覆盖守卫要求 A→R 与 R→A 各有方向对应 marker，并用两方向纯 text wire 作负控，防止再次靠人眼漏盘。

守卫若与被守护对象直接调用同一批 capture helper，它审的是 helper 能否产生 marker，不是 golden 集合是否仍含该用例。机械判据是“跳过一条被守护的 golden，集合审计会不会红”；因此每条 golden 在 digest 断言成功后登记覆盖事实，末尾只审已登记集合。A→R 与 R→A 的 reasoning golden 各自用 `test.skip` frozen patch 做过删除负控，集合审计均变红。
