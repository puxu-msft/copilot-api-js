## 架构

### 运行时兼容（Bun-first / Node-compatible）

项目同时支持 Bun 与 Node 两个运行时，但**优先级不对称**：

- **Bun 是一等公民**——默认/推荐运行时。所有开发与运行命令（`dev` / `start` / `test:*`）都走 `bun`；后端测试分档：默认 `test`=fast(unit+http)、`test:backend`=全后端(unit+it+http)、`test:ci`=backend+pty+e2e（后缀=真相域、tier=脚本组合，见 [coding-conventions.md](coding-conventions.md)「测试组织」）。
- **Node 仅是有意维护的兼容目标**——分流路径靠运行时逻辑保证，但实测覆盖弱于 Bun（Node 专属分支在 `bun test` 下走不到，例如 driver.ts 的 `nodeFactory()`）。

所有运行时差异都收敛到单一判别点 `typeof globalThis.Bun !== "undefined"`，分流出独立实现：

| 子系统 | Bun 路径 | Node 路径 | 文件 |

#### 依赖选型原则：bun-first

> **决策记录**：[decisions/2026-07-05-dependency-selection-bun-first.md](decisions/2026-07-05-dependency-selection-bun-first.md)——这是真正的用户决策，是本原则的权威源（含背景/备选方案/后果）；下文为实现分流细节。

所选外部库本身**必须能在 Bun 下原生工作**——判据是"Bun 热路径上的库 Bun 原生可跑"，而非"禁止任何 node-only 依赖"：

- **拒绝 node-gyp 原生绑定（`binding.gyp`）**——Bun 兼容性最大的雷区。标杆实例：driver.ts 刻意不用 `better-sqlite3`（Bun 1.3 加载时直接拒绝 "not yet supported in Bun"），改用两端各自的内建 SQLite，避免用户在安装时被迫二选一。
- **node-only 库可作兼容路径，但不得进 Bun 热路径**——`@hono/node-server`、`@hono/node-ws` 只在 Node 分支被动态 `import()`。**上游 https 热路径走内建 `node:http2`**（`transport/http2-client.ts`）：Bun 的 undici HTTP 解析层对 GHC h2 端点的 chunked HTTP/1.1 响应永久挂（裸 `node:tls` 收齐字节、Node 同码 0.4s、curl 0.4s——是 undici-on-Bun 的解析 bug），而所有 https 上游皆 h2-native，故改走 node:http2（h2 + `createConnection` 上 `setKeepAlive`，`ss` 实证 idle socket 带 keepalive timer）。**`undici` 经 `undici/index.js` 子路径仅留给明文 `http://`**（本地 SearXNG）——纯 JS、无 node-gyp；走子路径是因为 Bun 把裸 `undici` 替换为内建 shim 会静默丢弃 dispatcher。pin undici 7（8 的 index.js 在 Bun 崩）。详见 skill `debugging-ghc-api-upstream-transport` 与 [spec/upstream-http2-transport.md](spec/upstream-http2-transport.md)。
- **审计手段（实测，非推断）**：`find node_modules -name binding.gyp` 应为空（零 node-gyp 依赖）；`find node_modules -name "*.node"` 命中的 `@rollup` / `@rolldown` / `@oxc-*` 都是**构建工具**预编译产物，只在构建期用、不进运行时 dist，不算违反。

### 请求流程

v4 管线：路由按前缀选 **codec**（每格式一个）+ 构建 per-request **driver**，由 driver 编排七阶段（S1–S7）。详见 [v4 设计文档](v4/01-architecture.md) 与 [03-spec/](v4/03-spec/)。

1. 请求进入 `src/routes/` 中的 Hono 路由（`route.ts` 薄包装：try/catch + forwardError，直调 v4 handler）。
2. handler 按接入格式选 codec（`lib/codec/`：`anthropic` / `openai-cc` / `openai-responses` / `gemini`）+ 构建 driver（`createPipelineDriver`，consume codec + transport + retry strategies + rewrite registry），调 `driver.runRequest` / `driver.runResponse`。
3. driver 编排**七阶段**（`lib/pipeline/driver.ts`，详见 [03-spec/envelope-driver.md](v4/03-spec/envelope-driver.md)）：
   - **S1 parse** — `codec.parse(raw)` → `RequestEnvelope`（model 解析、body 提取、建 RequestContext）
   - **S2 route/translate** — `decideRoute`（`pipeline/router.ts` **自由函数**，非 codec 方法：透传/翻译/拒绝，统一 4 格式判断、唯一读 model 能力，2026-07-11 ADR 从 FormatCodec 拆出）+ 出站腿 `translateOut`（经 `resolveCellAssembly` 的 `OUTBOUND_LEGS`；透传=identity）
   - **S3 rewrite-in** — `runRewriteIn`：请求改写链（registry 按 format+config+order 装配）。Anthropic 由 codec 经 `deps.requestRewrites` 供 per-request `RequestRewrite`（`codec/anthropic/request-rewrite-adapter.ts`：sanitize 链 + pipelineInfo/messageMapping/thinking 记录，**Stage A A0** 从 `codec.parse` 迁入；闭包 over 路由产的 `preprocessInfo`，故走 codec-provided 而非 module-global `BUILTIN_REQUEST_REWRITES`）
   - **S4 exchange** — `runExchange`：错误驱动重试循环（`codec.prepareWire` → `transport.send` → 失败时首个匹配 strategy 改写 env 重试；429 由 generation dispatch scheduler 经 `UpstreamAdmissionController` 处理；其余分类与重试边界见 [request-pipeline.md](request-pipeline.md)）
   - **S5 rewrite-out** — 响应改写链（逐帧 `transform`：emit/suppress/buffer + 流末 `flushChain`，已进 `try/finally` 故异常路径也 drain registry buffer）。Anthropic 的 5 个 `ResponseRewrite` 定义在 `src/lib/codec/anthropic/response-rewrite-adapters.ts`（`ANTHROPIC_RESPONSE_REWRITES`），由 handler 作 `deps.responseRewrites` 传入 driver（module-global `BUILTIN_RESPONSE_REWRITES` 仍空）：recover-tool-call=100 / thinking-signature-compat=150 / tool-input-decode=200 / server-tool-filter=300 / recover-refusal=400，**Stage A A1** 从 handler pump 原子迁入，复用既有 factory 不重写算法核；order 编码硬序契约 recover<filter<refusal
   - **S6 render** — `codec.renderResponse` 翻回客户端协议（透传=identity）
   - **S7 forward** — handler 写回客户端（streamSSE / JSON / WS frame）
4. driver 在阶段边界采样原始数据 → observability bus → sinks（History/Ws/Telemetry/File）+ tui `TerminalUi`（终端渲染，P0 迁出 sinks/）：S1 入站、S4 per-attempt 双轨（effectiveSource/upstreamRequest + queueWaitMs）+ **上游原始 sseEvents**（循环顶逐帧，所有格式统一）+ **S5 前经 `runResponse` 的 `onUpstreamFrame` hook 把 raw 帧交回 handler 做 accumulate（→ per-attempt `upstreamResponse` 保上游原貌，Option A，Anthropic）/ repetition / progress / 诊断**；**客户端 forwarded（Stage B 起）由 driver-owned `ClientSink` 在写出点采样（`makeSseSink`/`makeWsSink` 的 `onForwarded`），全 5 格式经 `runResponseSink` 统一**（详见下文「活的架构现状」流式写出行 + [03-spec/envelope-driver.md §4](v4/03-spec/envelope-driver.md)）。
5. Anthropic 直连为 **bypass-direct**（`translateOut`/`renderResponse`=identity）；其 S5 响应改写链（recover/thinking/decode/filter/refusal）由 driver 逐帧应用后写进 sink（**A1 起非逐字透传** + **Stage B 起 driver owns-the-sink**——driver 跑改写 + 写客户端，handler 只供 `onUpstreamFrame` accumulate + 映射终态，不再二次 filter / 不再 handler 写出）。非 Anthropic vendor 模型在 S2 拒绝 400（无降级）。
6. **Azure**：`injectDeploymentModel` 从 URL path 注入 `azureModelOverride`，复用 CC/Responses 的 v4 handler（不新增 codec）。
7. **例外**（不进 driver）：`count_tokens`（Anthropic 端默认转发 GHC 上游 `/v1/messages/count_tokens`、本地 tokenizer 兜底；Gemini 端仍本地 tokenizer）与 embeddings 均不进 driver/管线，也不建 `RequestContext`；History V3 由统一 lightweight `ModelOperation` lifecycle 在旁路边界直接捕获，仍不写 V2 History。
8. 请求完成 / 失败时经 History V3 终端总线单写者落一条不可变 `ModelOperationRecord`（内容寻址 CAS + manifest；`v3/store.ts` 的 `enqueueModelOperation` + `drainV3Writer`，drain-before-close），否则仅更新内存 in-flight 映射并推送 WebSocket。

**响应腿数据模型（proxy-introduced failure 不污染上游腿；两条正交轴）**：持久化 `attempts[].upstreamResponse` 忠实反映**上游腿**，请求级客户端结局进 `entry.state` + `_index.derived.failureReason`——**attempt 成败**（`upstreamResponse.success`）与 **entry 客户端结局**（`state`）是两条独立轴、不再混用一套 inbound/outbound 命名。**上游成功、代理拒绝**（contentless refusal、unrepairable malformed tool_use）走 `ctx.fail(..., { upstreamSucceeded: true })`：该 attempt 的 `upstreamResponse.success=true`、无 `error`、保留上游 content，verdict 只进 `_index.derived.failureReason`；**真上游失败**（HTTP error、截断、H3、H2）仍 `success:false`+error（但**流式 H2/H3/截断失败腿保留中止前 `acc` 累积的 partial content** 到 `upstreamResponse.body`，与 refusal 分支同经 `fail()` 的 content 通道——richest-data-flow，供 thinking-block metrics 等观测中止前已吐内容〔含损坏双空 thinking 块〕；verdict 语义不变）。`_index.derived` 全部由 `attempts` 重算（三处同步不变量），经 V3 projection（`v3/projection.ts::recordToHistoryEntry`）产出。前端 DiagnosticBar/ResponseSegment 据此把请求 verdict 与上游腿分开呈现，避免"代理判定失败显示成上游腿 error"。**per-attempt 失败 body（H）**：retry-恢复请求的中途失败 attempt，其上游错误 body 现经生产者对齐（`fail()`/`abort()` 与 `complete()` 对称调 `setAttemptResponse`）为该失败 attempt 合成 `upstreamResponse`，随 `ModelOperationRecord` 落 V3 canonical store（每个 settled attempt 恒载裁决）——供事后核对反应式学习依据（richest-data-flow；此前只有终态失败的 body 存了）。**runtime vs 持久化命名**：live `RequestContext` 的 `response`/`forwardedResponse` getter、`Attempt.{effectiveRequest,wireRequest,response}` 保留旧名，仅持久化 `HistoryEntry` 采用 client/upstream 腿。

### 活的架构现状（v4 迁移态）

v4 driver（七阶段编排）正逐步取代各格式巨型 handler。下表定位"当前活的是哪条路径"——读具体模块前先在此对齐，别把旧路径当主路径。状态：`[done]` 已迁 driver / `[wip]` 仍 handler-side / `[bypass]` 设计上不进 driver / `[退役中]`。

**max_tokens continuation P0（[done]，Anthropic-only 观测层）**：`src/lib/pipeline/max-tokens-terminal-observer.ts` 在 Anthropic candidate session 的 rendered-frame 旁独立追踪最后 wire block 的 kind/闭合状态，`max-tokens-truncation-class.ts` 用它完成 A/A'/B/B-closed/C 分类，绝不读取 continuation ledger。正常 `max_tokens` terminal 在 `routes/messages/handler-v4.ts` 的 settle 前写入 `pipelineInfo.maxTokensContinuation`，Telemetry 以 `max_tokens_truncation` 维度计数；`max_tokens_continuation.enabled` 默认 false，P0 不请求续写、不抑制或改写客户端 terminal。CC/Responses 的 observer 与生产接线仍是 P3 Task 3.0a/3.0b 的显式前置。

### 类型架构（single-source-of-truth）

类型定义只在**产生/拥有方**定义一次，消费端只 re-export：后端拥有的类型在后端定义、前端经 `~backend/*` re-export（前端不重新声明）。原则：
- 类型应**覆盖已知的数据变体**；内联类型多处引用时提取为命名导出。
- 运行时数据可保持 `any`，同时**额外导出具体联合类型**供消费端按需使用（richest-data-flow：不为 DRY 收窄数据源）。
- 有示范价值的"死代码"（准确描述已知变体、或为未来消费者提供模板）可保留；纯无用/过时/误导的死代码删除。
- 前端从 `~backend/*` 引入的模块**必须是纯的**（不拖入 `~/lib/state`/`consola`/node 内建等后端运行时）——需要后端纯函数时抽到无依赖模块、后端 re-export；校验用 `bun run build:ui-v4`（当前活的 React History UI 是 `ui-v4/`；`build:ui` 是旧 Vue `ui/`——校验 ui-v4 的 `~backend/*` 纯度必须跑 `build:ui-v4`，别跑成 `build:ui`）（见 skill `debugging-frontend-tests`）。

反应式学习记录（negotiation）的 `LearnedSnapshot` / `LearnedEntryView` / `LearnedEntryMeta` / `NegotiationCategory` / `EntryStatus` 均**后端拥有**（`src/lib/anthropic/{feature-negotiation,negotiation-lifecycle}.ts`），ui-v4 `Learned` 页经 `ui-v4/src/types/index.ts` 的 `~backend/*` re-export 消费、绝不前端重定义。

运营遥测快照 `RequestTelemetrySnapshot`（`/api/status.requestTelemetry` payload）**后端拥有**（`packages/telemetry/src/request-telemetry.ts`），ui-v4 `status.ts` 经 `@hsupu/ghc-proxy-telemetry/types`（包的**纯类型 barrel**，图里零 value import，故即使打包器没消除 type-only import 也够不到后端运行时）的 `export type` re-export 消费（2026-07-14 从 frontend-loose `Record<string, unknown>` 收敛；2026-07-27 telemetry 抽包后从 `~backend/lib/request-telemetry` 改指包）——纯类型、`typecheck:ui-v4` + `build:ui-v4` 双验。

#### History 数据模型（client/upstream 双腿，SSOT = `src/lib/history/types.ts`）

`HistoryEntry` 的持久化数据模型是本项目最复杂的 SSOT 类型（2026-07-07 引入的 client/upstream 双腿形状，V3 projection 沿用；设计演进见 [归档 RFC](archive/2607-history-v2-removal/2026-07-07-history-data-model-restructure.md)）。核心形状——两条**正交轴**（attempt 成败 vs entry 客户端结局）、client/upstream 双腿 + 逐 attempt 上游轨：

- **entry 级两腿**（proxy ↔ client，per-entry）：`clientRequest`（客户端入站，`body`=SoT + 结构化投影）、`clientResponse`（转发给客户端的响应，**一等公民**——非 `attempts[final]` 投影，客户端结局看 `entry.state`）。
- **`model: { requested, resolved, multiplier? }`**：模型/计费归拢键（保住遥测「成功=规范名 / 失败=别名」拆分）。
- **per-attempt 上游轨**（proxy ↔ upstream，`attempts[]` 逐次保留）：`effectiveSource`（`env.body` 本尊 + 本轮 pipeline）、`upstreamRequest`（最终 wire + messages 投影）、`upstreamResponse`（每 settled attempt 恒载裁决，`success` = 上游完整 2xx 且协议正常终止）。
- **`_index.{derived,aux}`**：`derived` 是 `attempts` 的 recompute-only 投影（`responseSuccess`/`currentStrategy`/`failureReason`/`attemptCount`，**三处同步不变量**——`toHistoryEntry` + sink `onTerminal` 投影 + `updateEntry` allowlist，见 skill `persistence-async-invariants`）；`aux` 是自由投影空间。
- **命名分层**：**live `RequestContext` 保留旧名**（`response`/`forwardedResponse` getter、`Attempt.{effectiveRequest,wireRequest,response}`、`_httpHeaders` 捕获袋的 inbound/outbound）——**仅 `HistoryEntry` 持久化采用 client/upstream 腿**（V3 `projection.ts::recordToHistoryEntry` 从 `ModelOperationRecord` 投影时映射）。V3 是内容寻址 canonical store、无 legacy 行迁移负担（旧 V2 `entries_v2`/`entry_stages` 及其读适配 `adaptLegacyLegsInPlace` 已随 History V2 removal 2026-07-18 整体删除）。V3 存储/表结构见 skill `history-sqlite-schema` + [history.md](history.md)。
- **`UsageData` 有两个锁步拥有点**（**反直觉**，2026-07-12 ghc-usage-details）：canonical `UsageData`（`src/lib/history/types.ts`）与 `ResponseData.usage` 内联字面量（`src/lib/context/types.ts`）**不是共享引用**（context 刻意不 import history-store 类型），故任何 usage 字段变更必须**同一 commit 同步改两处**、逐字对齐——否则 context→`complete`/`fail`/`abort` 链静默丢新字段（`reasoning_tokens` 可选化更会致赋值 TS 报错）。`tests/usage-data-shape.unit.test.ts` 是编译期锁步守卫。GHC 升级 usage 的 `cache_write_tokens`（→`cache_creation_input_tokens`）+ 模态/prediction 分解经 `src/types/api/ghc-usage.ts`（自有类型、不 augment openai SDK）在**全部约 11 个 `usageFromTotalInput` 站点**捕获（4 腿含 Gemini 流式经 `GeminiStreamMeta.usage`），模态/prediction 为 **blob-only**（无 SQLite 列）。出向 `responses→cc` 翻译器转发 cache_write。spec [2026-07-12-ghc-usage-details.md](spec/2026-07-12-ghc-usage-details.md)。

### 前端子项目

```
ui/
├── package.json       # 前端自有依赖与脚本（独立包，**非** workspace 成员）
├── bun.lock           # 自有 lockfile（`cd ui && bun install`）
├── src/types/         # 类型定义（re-export 自 ~backend/lib/history/types）
└── tests/             # 前端测试（bun test）
```

路径别名：后端 `~/*` → `src/*`，前端 `@/*` → `ui/src/*`，前端引用后端 `~backend/*` → `../src/*`。
前端类型统一从后端 re-export，不重复定义。

**`ui/`（旧 Vue）与 `ui-v4/`（活的 React）接线方式不同**——2026-07-28 起 `ui/` 已整体脱离主编译链，见下表。`ui-v4/` 仍是 bun workspace 成员（根 `workspaces` 声明、单一根 `bun.lock` hoist、根脚本经 `bun run --filter copilot-api-ui-v4 <script>` 委派、被根 `eslint .` 覆盖）。

| 链路 | `ui-v4/`（活） | `ui/`（旧 Vue，退役中） |
|---|---|---|
| 依赖安装 | 根 workspace 成员，根 `bun install` 一并装 | **独立包**，须 `cd ui && bun install`（自有 `ui/bun.lock`） |
| 根脚本委派 | `bun run --filter copilot-api-ui-v4 …` | `cd ui && bun run …`（filter 已不能解析） |
| root `eslint .` | 覆盖（含 react-hooks/jsx-a11y 块） | **不覆盖**（`ui/**` 整体 ignore、不再 lint） |
| 根 tsconfig | 不在 `include`（自有 tsconfig） | 不在 `include`（自有 tsconfig） |
| 根 `build` / 测试档位 | 不链、不聚合（显式 `build:ui-v4`/`test:ui-v4`） | 不链、不聚合（显式 `build:ui`/`test:ui`） |

两者的 FE 运行时与构建测试 devDeps 都在各自 package.json 下，各自拥有 `build`/`dev`/`preview`/`typecheck`/`test` 脚本（cwd=自身，配置经 `import.meta.dirname` 自寻）。**两侧工具链并不对称**：`ui/` 用 `vue-tsc` 做类型检查、自带 `@playwright/test` 与 `test:e2e`（浏览器 e2e 在 `ui/tests/e2e/`）；`ui-v4/` 用 `tsc`、**没有** Playwright 也没有 `test:e2e`（其 `test` = bun + vitest 两腿）。`typescript` 两侧都不在自己的 package.json 里声明，但**解析来源不同**：`ui-v4/` 从根 `node_modules` 向上解析；`ui/` 因 `vue-tsc` 把 `typescript` 作为 peer 拉进来，实际用的是 `ui/node_modules/typescript`（2026-07-28 两边同为 5.9.3，但这是两条独立的解析链，根上调版本时 `ui/` 不会跟着动）。根 `build` 不链任何 UI（2026-07-22 UI 外置：主服务器不再服务/构建任何 UI，运维单独构建后自托管，见 README「Hosting the Web UI」）。仓库级 dev 工具（`typescript`/`eslint`/`tsdown`）仍在根；FE eslint 插件只剩 React 侧（Vue 三件套随 `ui/` 脱链一并移除）。

`ui/` 保留两条通往仓库的绳子。主要一条是 `~backend/*`（vite alias + tsconfig paths 解析后端源码）——**它没有机器护栏**：后端重构可以静默把它弄坏（2026-07-28 实测发现 telemetry/foundation 拆包与 `DecodeToolInputConfig.all` 删除都已经把它打断且无人知晓）。改后端后若想确认没打断它，只能显式跑 `bun run typecheck:ui` + `bun run test:ui`。次要一条是 `ui/bunfig.toml` 向上 preload 仓库的 `tests/helpers/sandbox-paths.ts`（测试期 fs 沙箱地板，刻意保留——沙箱比自足重要）。这两条也划定了「独立」的边界：`ui/` 的 `build`/`test` 在仓库外裸装裸跑可通过（沙箱 preload 随仓库文件一起在），`typecheck` 不行（后端源码的依赖装在仓库根）。代价与实测数据见 [vue-ui-retirement.md](vue-ui-retirement.md) §0。

### 配置加载层级

`loadConfig()` 在每次调用时产生**生效配置 = bundled defaults 深合并 user overrides**（user 优先）：

1. **Bundled 默认** — 包根目录的 [`config.yaml`](../config.yaml)（`PATHS.BUNDLED_CONFIG_YAML`），随 npm 包发布；项目推荐的默认配置。
2. **用户覆盖** — `$XDG_DATA_HOME/copilot-api/config.yaml`（默认 `~/.local/share/copilot-api/config.yaml`，对应 `PATHS.CONFIG_YAML`），稀疏覆盖文件；缺省键自动回退到 bundled。

合并规则：
- 顶层嵌套 section（`anthropic` / `history` / `shutdown` / `openai_responses` / `rate_limiter` / `retry` / `timeouts`）— 按字段合并
- 自由形式 map（`model_mappings`、`anthropic.effort_overrides` 等）— 按 key 合并
- 数组与标量 — user 整体替换

代码里残留的硬编码（`CONFIG_MANAGED_DEFAULTS` / `DEFAULT_MODEL_OVERRIDES`）仅作为 bundled config 无法读取时的安全兜底。

**新增 config 键的收尾清单（无守卫测试强制，靠纪律）**：新增任何 config 键（尤其 `anthropic.*`）必须同时出现在 `schema.ts` + `config.ts`(apply) + `state.ts`（3 处）+ **bundled `config.yaml`**（含双语注释：三档/取值/默认/docs 链接）+ 下节「运行时选项」表。bundled `config.yaml`（包根、随 npm 发布）是**默认 SSOT + 完整自文档化清单**——键只活在 `CONFIG_MANAGED_DEFAULTS` 兜底里 = 用户翻 config.yaml 发现不了该功能。两个要主动否决的错误先验：「兜底够用」（只看功能性、漏可发现性 + 一致性）、「peer 在改 config.yaml 故避让」（`concurrent-sessions-line-coexistence` 禁止的退让——并发只决定用哪种行级隔离技法、绝不决定改不改）。`config.example.yaml` 是精简样例（只列常用），opt-in 默认关键不加。

### Hot-reload 语义（统一约定）

`config.yaml` 的字段在 `applyConfigToState()` 中按合并后的 effective config 应用，并保留 retain-on-absence 兜底：

- **用户键存在** → 替换运行时值
- **用户键缺省 + bundled 有该键** → 使用 bundled 值（深合并已注入）
- **用户键缺省 + bundled 也无该键** → 保留上次运行时值（兜底，避免空 bundled fixture 下意外清空）
- **集合显式为空**（如 `disabled_models: []`、`model_mappings: {}`）→ 清空
- **回到内置默认** → 删除用户文件中的对应键即可；下次 reload 自动从 bundled 取值。`PUT /api/config/yaml` 仍调用 `resetConfigManagedState()` + 重新 apply 全表以保证幂等

不参与 hot-reload 的字段（修改需重启）：
- `proxy` — `initProxy()` 在 `start.ts` 启动期执行一次
- `ghc_api_base_url` — 在 `start.ts` 启动期读取一次；mid-flight 切换上游会让进行中的请求路由错位
- `rate_limiter.*` — `AdaptiveRateLimiter` 是 stateful singleton，启动期构造

完整字段覆盖由 [tests/config/config-hot-reload.it.test.ts](../tests/config/config-hot-reload.it.test.ts) 的表驱动测试 + 完整性守卫验证；新增字段未登记到测试矩阵或豁免清单会立刻 fail。

## UI 设计原则

### Console UI（日志）

- **使用固定宽度 ASCII 前缀**对齐日志，不用 emoji/图标（如 `[....]`、`[<-->]`、`[ OK ]`、`[FAIL]`、`[RETRY]`）
- **日志格式**：`[PREFIX] HH:MM:SS METHOD /path ...` — 状态前缀在前，时间戳在后
- **只显示相关信息**：非模型请求（如 `/health`）不应显示模型名、token 数或 "unknown"
- **流式指示器**：长时间运行的请求显示 `streaming...` 状态，使用 `[<-->]` 前缀
- **多行 diagnostic 与模型目录保真/色彩**：`system.diagnostic.message` 在 canonical event/NDJSON 中保持原值，Terminal 末端 `renderSystemLogLines` 仅给首物理行加 `[INFO]/[WARN]/… + time`，续行与空行保持结构并逐行清除 CR/ANSI/OSC/DCS 等控制序列。启动 `Available models` 不再伪装成 diagnostic 文本，而由 `system.model_catalog` 携完整模型数据：Terminal 按“一模型一行”投影，label 用 `string-width` 做最小列对齐，长 model id/vendor/`[disabled]` **完整保留、不为对齐截断**；disabled 整行灰色，enabled 模型的 context/prompt 原始 token 上限 **≥900k** 时对应 `ctx:`/`prp:` 字段黄色（disabled 灰色优先），`out:` 不参与。StructuredFile 写 `model-catalog` 记录保留完整语义；超终端宽度由日志自然换行而非上游丢信息。
- **footer 行宽感知 + 按模型分组**：底部 `[<-->]` 在途请求 footer 恒渲染为**单物理行**——由 `tui/render/footer.ts` 的 `buildActiveFooter`（`TerminalUi` 渲染，P0 从旧 `ConsoleSink` 抽出）单一收口保证（先 strip C0 控制字符防内嵌换行撑行，再 `truncateToWidth` 截到 `columns-1` 显示宽度，`columns` 每次渲染读活值故 resize 后 ≤100ms 自愈）。多请求时**按 resolvedModel 分组**为 `model ×N ↓sumBytes t1 t2 …` 段（未解析归 `(resolving)` 桶，count 降序），每段显示该组**最久的 N 个**请求 elapsed（降序=最老在前），N 随组数自适应 `timesPerGroup`（1 组→5 · 2 组→3 · 3+ 组→1，横向空间共享）；显示几组由终端宽度贪心驱动、溢出收进 `+K more`（替代旧的固定 `MAX_SHOWN=3`）。宽度原语由 `tui/render/width.ts` 单一拥有：纯文本按 grapheme cluster 截断，Region 的 ANSI 防御层保持 SGR/OSC 完整，并以 canonical `string-width` 后验守住 `≤ columns-1`；着色只在纯文本截断后于末端 `pc.dim` 一次
- **交互式 live 面板（P1，`src/lib/tui/`）**：真终端（`stdout.isTTY` + 显式注入 `stdin`）下由 `TerminalSession` 独占 raw/cooked，键盘驱动三态——**collapsed**（分组 footer + `space: expand` 提示）↔ **panel**（展开逐条请求表格，选中行反色）↔ **detail**（固定 header/keybar + 可滚 body，完整 per-attempt 明细）。键位：`space`/`tab` 展开收回、`↑↓`(`k`/`j`) 选中、`enter` 详情、`esc` 逐级返回、`?` help、`q`/`Ctrl-C`/`Ctrl-D` graceful shutdown、`Ctrl-Z` 真 job-control suspend。分层：`ActiveRequestStore.apply()` 是 request event→active projection/effect 的纯 reducer；`controller` 只存 `selectedRequestId/detailRequestId`，index 仅 render 派生；`render/detail` 拆 keyed document 与 viewport；`TerminalView` 拥有 Region/alt-screen 状态；`OutputArbiter` 是唯一 stdout side-effect owner；`TerminalUi` 当前 293 行，只作 bus/input 编排。
- **渲染模型：collapsed N=1 + detail 备用屏 + scroll-before-grow 防吞行（2026-07-11 重构，消除 DECSTBM 几何 churn）**：根因（用户真终端实测）——**任何 DECSTBM 滚动区几何变化都扰动日志流**（面板长大吃日志行、缩小留空行 gap、重建使 footer 泄漏进历史）；069c2293 只堵了「在途数变化」这一路，漏了**视图切换**（collapsed/panel/detail 高度天然不同）。方案（用户 2026-07-11 定：默认折叠 N=1、允许切换出空行、严禁吞行——早前的「恒定高度区」方案因默认常驻 2 空行被否决）：
   - **collapsed 默认 N=1 + scroll-before-grow 严禁吞行**（用户 2026-07-11 反转恒高取舍）：交互实例**始终**经 `Region.render`，但**默认/折叠只占 1 行**（`buildCollapsedLines` 返 1 行、不补空行；panel 仍 `MAX_PANEL_ROWS=3`）。视图切换**允许几何变**（滚动区高度 collapsed 1 ↔ panel 3）——**空行 gap 可容忍、吃日志行是唯一红线**。红线由 `Region.render` 的 **scroll-before-grow** 保证：面板长高时（`rows===prev.rows && panelHeight>prev.panelHeight`）先在旧滚动区底行发 `delta` 个换行，把新面板将占的日志行推进 scrollback 再重锚，绝不覆盖；shrink 方向不处理（留空行）。窄缝：resize 与视图切换同帧时（`rows` 也变）scroll-before-grow 退化、可能吞行（见 `docs/todo/deferred-backlog.md`）。**用 Bun.Terminal + `@xterm/headless` PTY 网格测试验证**（`tests/tui/pty/no-eaten-lines.pty.test.ts`：真 PTY 驱真 TerminalUi + scrollback 断言无吞；harness 红样本精确报告缺号）。**注意**：此设计**取代**了早前同日的「恒定高度区（collapsed 补空行到 3 行、`interactivePanelHeight`）」方案——该方案换零 churn 但默认常驻 2 空行，用户否决。
  - **fix A 自愈**（INV-4）：`Region.render` **每拍**重申明 DECSTBM（`DECSC`+`\x1b[1;<bottom>r`+`DECRC`，不移停泊光标）——任何未预期扰动下一拍自愈（真终端唯一 oracle `exp/tui-rawmode/log-coordination-regression.ts`）。
   - **detail 走备用屏幕**（不再当 panel 走 Region）：进入 `\x1b[?1049h`→`\x1b[r`→`\x1b[?6l`→清屏；退出 `\x1b[?1049l` 后重建区。`buildDetailDocument` 生成稳定 keyed document，`layoutDetailViewport` 固定 header/keybar 并滚动 body，rows 3/10/24 下 60 attempts 全可达。detail 期间日志由 `TerminalView` 的有界 replay queue 暂存；system diagnostics 的 durable truth 在 per-process NDJSON，request lifecycle 的 durable truth 在 History。view/selection 真值是 `detailRequestId/selectedRequestId`，兄弟/当前/末行终结均先 reconciliation 再 render。
  - **输出协调三态**（INV-3，`terminal-coordinator.ts` 纯叶子单例）：所有对受控终端流的写都经 region 感知的 `emergencyWrite`——`region`(清面板+写+重画单次原子)/`alt`(write-through 宁污染勿丢失)/`inline`(CLEAR_LINE+写+重画 footer 防泄漏)/`none`(直写)/未注册(降级 stderr)。收编原两处旁路直写（`republish.ts` reentrant + `sinks/file.ts` error），`write` hook 绕 `rendering` 重入守卫（不吞「绝不能丢」的错误）。coordinator 纯叶子性由 layer-boundaries 守卫 + eslint 规则双钉死。
- **终端安全**：raw mode 下 `Ctrl-C`/`Ctrl-D`/`q` 统一请求 graceful shutdown；退出/崩溃/destroy/shutdown-draining 必经 `TerminalSession` 恢复 alternate screen、DECSTBM、光标与 cooked stdin，exit hook 可注销。`Ctrl-Z` 顺序为视觉恢复→`OutputArbiter.drain()`→detach/cooked→移除 listener→SIGTSTP 前台进程组；SIGCONT 后重装 listener→raw/attach→全量 repaint。Bun 1.3 的 `process.off` 不恢复 native default disposition，且 CLI launcher/JS worker 同属一个 job，故 Bun 路径经 `bun:ffi` 恢复 `SIG_DFL` 后对 libc process group 发 SIGTSTP；Python controlling-PTY oracle 以 `WIFSTOPPED` 连跑 8 次。Windows capability 明示无 job control并只提示一次。非 TTY、`TERM=dumb`、未注入 stdin或 CLI `--no-tui` 均退回 plain inline renderer，无 raw mode/DECSTBM/alternate screen。
- **诚实展示 retry**：每次被 retry strategy 接受的请求失败都打印一行 `[RETRY]`，重试序号由 duration 的 `last/total(N)` 中 N 承载。前缀黄色、状态码红色、`(retryable: ...)` dim；之后仍照常打印最终 `[ OK ]` / `[FAIL]` 行。L1/L2 重试均走同一 attempt event，终态 N 与末次 `[RETRY]` 对齐。

### History Web UI

- **显示实际请求内容**：如果最后一条消息是 `tool_result`，显示 `[tool_result: id]` 而非向前查找用户文本
- **文本优先于 tool_use**：对于同时包含 text 和 tool_use 的 assistant 消息，优先显示文本内容；仅在没有文本时显示 `[tool_use: ToolName]`
- **过滤系统标签**：从预览文本中移除 `<system-reminder>`、`<ide_opened_file>` 等系统标签

### 通用原则

- **减少噪音**：不显示冗余或不可用的信息
- **一致格式**：控制台输出使用固定宽度列对齐
- **信息丰富的预览**：历史预览应反映请求的实际性质
- **信息丰富的日志**：所有日志消息应包含足够的上下文（模块标签、模型名、具体值）以便采取行动
