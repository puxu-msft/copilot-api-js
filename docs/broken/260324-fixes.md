## 总体修复原则

后续所有改动必须遵守以下原则：

1. 修根因，不修表象。
2. producer 产出完整数据，consumer 不做上游裁剪决策。
3. 同一能力的不同 transport 必须共享同一生命周期与观测契约。
4. 类型系统必须表达真实业务边界，而不是为当前实现让路。
5. 运行时配置必须具备可预测性，不能让并发请求读到不断变化的全局状态。

## High-1: History 数据流被 consumer 裁剪，`attempts` / `truncation` 等 rich data 丢失

### 现象

`RequestContext` 已经能够产出完整的 `HistoryEntryData`，包含：

- `response`
- `pipelineInfo`
- `truncation`
- `attempts`
- `httpHeaders`
- `sseEvents`

但真正落入 history store 的数据不完整：

- `attempts` 没有进 store schema
- 顶层 `truncation` 没有在完成/失败时写入
- consumer 在 `completed` / `failed` 事件里手工挑字段更新 entry

### 证据

- [src/lib/context/request.ts](/home/xp/src/copilot-api-js/src/lib/context/request.ts)
  - `toHistoryEntry()` 已产出完整 entry
  - 关键位置：`456`、`493`
- [src/lib/context/consumers.ts](/home/xp/src/copilot-api-js/src/lib/context/consumers.ts)
  - `completed/failed` 时只更新部分字段
  - 关键位置：`68`
- [src/lib/history/store.ts](/home/xp/src/copilot-api-js/src/lib/history/store.ts)
  - `HistoryEntry` schema 缺 `attempts`
  - `updateEntry()` 允许更新的字段集过窄
  - 关键位置：`222`、`720`

### 根因

项目里同时存在两套相近但不一致的数据表示：

- `HistoryEntryData`，来自 `RequestContext`
- `HistoryEntry`，来自 store

二者没有建立单一事实来源，而是由 consumer 手工做字段搬运和裁剪。

### 为什么不是最佳方案

这直接违反了仓库的核心要求：

- 数据应该以最丰富形态流动
- producer 不应替 consumer 做裁剪决策

目前的实现会带来这些问题：

- History UI 无法完整看到 retry / truncation 过程
- 未来 metrics / webhook / telemetry 也拿不到 attempts
- 每增加一个新字段，都要同步修改 producer、consumer、store 三处

### 修改目标

建立单一、完整的 history entry schema，使 `RequestContext` 成为 rich data producer，history consumer 仅做持久化桥接。

### 详细修改思路

1. 收敛 schema。
   - 统一 `HistoryEntryData` 与 `HistoryEntry`
   - 明确 store 的 entry 就是“完整快照”，不再维护一个缩水版结构

2. 补齐 store schema。
   - 为 `HistoryEntry` 增加 `attempts`
   - 若保留顶层 `truncation`，则确保它始终可持久化
   - 明确 `pipelineInfo.truncation` 与顶层 `truncation` 的关系，避免双重来源

3. 调整 consumer。
   - `created` 仍可先插入最小 entry
   - `completed` / `failed` 时不要手工挑字段拼补丁
   - 改为用完整 `entryData` 做一次完整 upsert 或覆盖式 merge

4. 调整 store 接口。
   - `updateEntry()` 不应只允许局部、白名单式字段更新
   - 应提供更适合上下文消费者的接口，例如：
     - `replaceEntry(id, entry)`
     - 或 `mergeEntry(id, patch)`，但 patch 必须覆盖完整 schema

5. 明确 summary 层的职责。
   - summary 继续做投影
   - 但投影只能从完整 entry 读取，不能倒逼上游丢字段

### 需要补的测试

- `RequestContext` 生成的 `attempts` 能完整落入 history store
- `truncation` 在 history API 中可见
- `failed` 请求仍保留 attempts / status / headers
- history summary 不受 schema 丰富化影响
- WebSocket history 推送在 entry 丰富后不回归

### 验收标准

- history store 中能取到完整 attempts
- truncation 信息不再中途丢失
- consumer 中不再存在“挑字段搬运 rich data”的逻辑

### 进度

- 状态：`todo`
- 受未提交改动影响：`否`

## High-2: Responses WebSocket 路径没有接入完整 RequestContext 生命周期

### 现象

`Responses` HTTP 路径和 WebSocket 路径声称共享同一 pipeline，但实际只有 HTTP 路径把 `requestContext` 传给 `executeRequestPipeline()`。

这意味着 WS 路径缺失：

- attempt 记录
- queue wait 聚合
- retry / error 分类的上下文记录
- 与 history / TUI 的完整一致性

### 证据

- [src/routes/responses/handler.ts](/home/xp/src/copilot-api-js/src/routes/responses/handler.ts)
  - HTTP path 传入 `requestContext`
  - 关键位置：`112`
- [src/routes/responses/ws.ts](/home/xp/src/copilot-api-js/src/routes/responses/ws.ts)
  - WS path 没传 `requestContext`
  - 关键位置：`165`
- [src/lib/request/pipeline.ts](/home/xp/src/copilot-api-js/src/lib/request/pipeline.ts)
  - pipeline 已明确支持 `requestContext`
  - 关键位置：`67`

### 根因

共享 pipeline 只共享了“执行过程”，没有共享“生命周期契约”。

本质上，HTTP 和 WS 两条路径不是在复用同一个 request handling contract，而是在复用一部分实现。

### 为什么不是最佳方案

同一业务能力不应因 transport 不同而失去观测一致性。

现在的结果是：

- HTTP 路径有完整上下文
- WS 路径只有部分手工补的记录
- 后续有人修改 pipeline / tracking 时，极容易只修 HTTP 不修 WS

### 修改目标

让 Responses WS 与 HTTP 完全共享同一个 request lifecycle contract。

### 详细修改思路

1. 补上 `requestContext` 传递。
   - 在 [src/routes/responses/ws.ts](/home/xp/src/copilot-api-js/src/routes/responses/ws.ts) 的 `executeRequestPipeline()` 调用中传入 `requestContext: reqCtx`

2. 补齐 WS path 的上下文更新语义。
   - 确认 queue wait 最终进入 `reqCtx`
   - 确认 streaming 完成时 `reqCtx.complete()` 的数据与 HTTP path 等价
   - 确认异常分支 `reqCtx.fail()` 前后不会遗漏 headers / attempts

3. 收敛 HTTP / WS 差异。
   - 如果两条路径除了 transport bridge 外基本一致，应抽一个共享 helper
   - 该 helper 的输入应是：
     - payload
     - selected model
     - reqCtx
     - transport sink
   - 而不是复制一份相似逻辑

4. 把 WS 的“协议转换”与“request lifecycle”彻底拆开。
   - lifecycle：pipeline + context + history
   - transport：SSE event -> WS frame

### 需要补的测试

- WS path 也会记录 attempts
- WS path 的 pipeline error 能进入 history entry
- WS path 在 rate limit / retry 时能记录 queue wait
- WS path 完成后 history entry 与 HTTP path 字段完整度一致

### 验收标准

- `Responses` HTTP / WS 经过同一生命周期记录
- history 中能看见 WS 请求的 attempts / headers / failure metadata
- 不再出现 transport-specific 的观测缺口

### 进度

- 状态：`todo`
- 受未提交改动影响：`是`

## High-3: endpoint 能力模型与代理 transport 混杂，已导致类型边界失真

### 现象

当前 `ENDPOINT` 常量同时包含：

- 上游模型支持的 API endpoint
- 代理内部提供的 WebSocket transport 标记 `ws:/responses`

然后这套常量又被直接用于：

- model capability 判断
- 测试中的 known endpoint 集合
- 类型断言

最终导致 `typecheck` 失败。

### 证据

- [src/lib/models/client.ts](/home/xp/src/copilot-api-js/src/lib/models/client.ts)
  - `supported_endpoints?: Array<string>`
- [src/lib/models/endpoint.ts](/home/xp/src/copilot-api-js/src/lib/models/endpoint.ts)
  - `ENDPOINT.WS_RESPONSES = "ws:/responses"`
  - `isResponsesSupported()` 把 HTTP endpoint 与 WS transport 混算
- [tests/component/supported-endpoints.test.ts](/home/xp/src/copilot-api-js/tests/component/supported-endpoints.test.ts)
  - 关键位置：`52`
- [tests/e2e/model-endpoint-completeness.test.ts](/home/xp/src/copilot-api-js/tests/e2e/model-endpoint-completeness.test.ts)
  - known endpoint 集合包含 `WS_RESPONSES`
  - 关键位置：`120`

### 根因

“模型支持什么 upstream API”与“代理对客户端暴露什么 transport”没有拆成两层概念。

### 为什么不是最佳方案

这会不断制造以下问题：

- 类型系统无法稳定表达真实边界
- 测试必须知道代理内部 transport 细节
- 新 transport 加进来时会继续污染能力判断

### 修改目标

把模型能力和代理 transport 拆成两个清晰模型。

### 详细修改思路

建议至少拆成两层：

1. Upstream endpoint capability
   - 例如：
     - `/v1/messages`
     - `/chat/completions`
     - `/responses`
     - `/v1/embeddings`

2. Proxy transport capability
   - 例如：
     - `responses-sse`
     - `responses-ws`

更具体地：

1. 不要再把 `ws:/responses` 存进模型 `supported_endpoints` 语义里。
2. `Model.supported_endpoints` 应明确只表达上游 endpoint。
3. 若需要表示“本代理支持 WS transport”，应由代理路由层或 transport registry 决定，而不是写进 model endpoint 常量。
4. `isResponsesSupported()` 应改为只回答：
   - upstream 是否支持 `/responses`
5. 如确实需要一个“客户端是否能走 WS responses”的判断，应新增一个单独函数，名字要体现是 proxy transport，不是 model endpoint。

### 需要补的测试

- endpoint 类型恢复后 `typecheck` 通过
- `supported_endpoints` 测试只验证 upstream capability
- proxy WS transport 单独有自己的测试
- e2e completeness 不再知道 `ws:/responses`

### 验收标准

- `tsc` 恢复通过
- model capability 与 proxy transport 的命名和类型边界清晰
- 业务代码不再用一个字符串集合表达两层不同概念

### 进度

- 状态：`todo`
- 受未提交改动影响：`是`

## High-4: 全局可变 `state` 被按请求热更新，但请求执行没有配置快照

### 现象

当前每个请求开始前都会执行：

- `applyConfigToState()`
- `ensureValidCopilotToken()`

随后请求执行过程中，大量逻辑继续直接读取全局 `state`，包括：

- `autoTruncate`
- `streamIdleTimeout`
- `rewriteSystemReminders`
- `stripServerTools`
- `normalizeResponsesCallIds`
- 等等

### 证据

- [src/server.ts](/home/xp/src/copilot-api-js/src/server.ts)
  - 每请求执行 `applyConfigToState()`
  - 关键位置：`40`
- [src/lib/config/config.ts](/home/xp/src/copilot-api-js/src/lib/config/config.ts)
  - 文档明确“删除键保持当前运行时值”
  - 关键位置：`255`、`257`
- [src/routes/messages/handler.ts](/home/xp/src/copilot-api-js/src/routes/messages/handler.ts)
- [src/routes/chat-completions/handler.ts](/home/xp/src/copilot-api-js/src/routes/chat-completions/handler.ts)
- [src/routes/responses/handler.ts](/home/xp/src/copilot-api-js/src/routes/responses/handler.ts)
- [tests/component/config-hot-reload.test.ts](/home/xp/src/copilot-api-js/tests/component/config-hot-reload.test.ts)
  - 当前测试在验证“配置缺席时状态不重置”

### 根因

项目把以下三件事混在了一个全局可变对象里：

- 启动时基础状态
- 热更新配置
- 请求期行为决策

### 为什么不是最佳方案

这会带来几个隐藏问题：

- 并发请求可能读到不同阶段的配置
- 配置文件删掉某个键，不会恢复默认值，而是保留历史状态
- 测试容易固化“状态残留”行为

### 修改目标

让配置热更新和请求期决策解耦，请求开始时拿到只读快照。

### 详细修改思路

建议拆成三层：

1. Process state
   - token
   - models cache
   - runtime service singletons

2. Runtime config
   - 来自 `config.yaml`
   - 可热更新
   - 有完整默认值，不依赖上一次状态残留

3. Request config snapshot
   - 每个请求开始时从 runtime config 复制
   - handler / pipeline / sanitization / timeout 逻辑只读这个 snapshot

具体实施建议：

1. 先定义 `RuntimeConfig` 类型，收纳现有配置字段。
2. `applyConfigToState()` 重命名或拆分为：
   - `loadRuntimeConfig()`
   - `applyRuntimeConfig()`
3. 热更新时生成完整配置对象，不依赖“缺键保留旧值”。
4. 在 request context 或 middleware 上挂载 config snapshot。
5. 把核心 handler / pipeline 的 `state.xxx` 读取替换为 snapshot 读取。

### 需要补的测试

- 请求开始后，即使 config 热更新，中途行为不变
- 删除 config key 时恢复默认值，而不是沿用旧值
- 两个并发请求分别持有各自 config snapshot

### 验收标准

- 核心请求路径不再直接依赖热变动的全局配置字段
- config 语义可预测
- 热更新不影响正在执行的请求

## High-5: `ServerInstance.close()` 的跨运行时语义不一致，Bun 分支提前完成

### 现象

`ServerInstance` 接口承诺：

- `close(force?) => Promise<void>`

Node 分支会在 server 真正关闭后才 resolve。

Bun 分支当前实现是：

- 调 `bunServer.stop(force ?? false)`
- 立刻 `Promise.resolve()`

### 证据

- [src/lib/serve.ts](/home/xp/src/copilot-api-js/src/lib/serve.ts)
  - 接口定义：`15`
  - Bun 实现：`99`
- [src/lib/shutdown.ts](/home/xp/src/copilot-api-js/src/lib/shutdown.ts)
  - Phase 4 会 `await server.close(true)`
  - 关键位置：`264`

### 根因

抽象层统一了函数签名，但没有统一完成语义。

### 为什么不是最佳方案

shutdown 代码会基于接口契约做时序判断。

如果 `close()` 提前 resolve：

- Phase 4 的等待语义变得不可信
- Bun / Node 行为会出现隐蔽差异
- lint 报错也在提醒这个 Promise 没被正确处理

### 修改目标

让 `ServerInstance.close()` 在所有运行时都兑现相同语义。

### 详细修改思路

1. 优先查清 `Bun.serve().stop()` 的真实返回语义。
   - 如果它本身可等待，直接返回该 Promise
   - 如果它不可等待，则需要包装一个真实“关闭完成”条件

2. 明确 `close(false)` 与 `close(true)` 语义。
   - `false`: 停止接收新连接
   - `true`: 强制终止现有连接

3. 调整 shutdown 代码的调用假设。
   - 确保 `close(false)` 的 fire-and-forget 是有意行为
   - 确保 `close(true)` 的 await 确实表示完成

4. 修复 lint 报错时，不要只加 `void`。
   - `void` 只能消音，不解决契约不一致

### 需要补的测试

- `ServerInstance.close()` 在 Bun / Node 分支语义一致
- graceful shutdown Phase 4 真正等待关闭完成
- `close(false)` 的非阻塞行为有明确测试

### 验收标准

- `serve.ts` 中不再存在契约不一致
- shutdown 对 Bun / Node 的行为预期一致
- 相关 lint 报错自然消失

### 进度

- 状态：`todo`
- 受未提交改动影响：`是`

## Medium-1: `RequestContext` 创建时序导致 history 先插空 entry，再补 request

### 现象

现在 `manager.create()` 会立即触发 `created` 事件，而此时 `originalRequest` 还没写进去。

因此 history consumer 只能：

1. 先插入一条 request 基本为空的 entry
2. 再等 `setOriginalRequest()` 触发 `updated`
3. 再补 request 字段

### 证据

- [src/lib/context/manager.ts](/home/xp/src/copilot-api-js/src/lib/context/manager.ts)
  - `create()` 里立即 `emit({ type: "created" })`
- [src/lib/context/consumers.ts](/home/xp/src/copilot-api-js/src/lib/context/consumers.ts)
  - 对 `originalRequest` 特殊补丁
- [tests/component/history-summary.test.ts](/home/xp/src/copilot-api-js/tests/component/history-summary.test.ts)
  - 明确有“empty request then update”测试

### 根因

context manager 的 create API 只接 identity，不接初始化所需的数据。

### 为什么不是最佳方案

producer 没有一次性交付完整数据，consumer 被迫理解时序细节。

这会增加：

- history consumer 复杂度
- entry 一致性风险
- 测试中的实现耦合

### 修改思路

建议二选一，优先第一种：

1. 让 `manager.create()` 支持直接传 `originalRequest`
2. 或延后 history 插入时机，直到 request 基本信息准备好

推荐第一种，因为它保留了 RequestContext 作为 producer 的中心地位。

### 需要补的测试

- create 时即可生成完整 entry
- 不再需要 `originalRequest` 特殊补丁路径

### 验收标准

- consumer 中没有“为了修正 create 时机而额外补 request”的特殊逻辑

### 进度

## Medium-2: `error.ts` 中错误分类与错误格式化重复维护

### 现象

当前至少有两套相似逻辑：

- `forwardError()`
- `classifyHTTPError()` / `classifyError()`

文件顶部也已经显式标注了这项技术债。

### 证据

- [src/lib/error.ts](/home/xp/src/copilot-api-js/src/lib/error.ts)
  - 顶部 TODO
  - `forwardError()`
  - `classifyError()`
  - `classifyHTTPError()`

### 根因

pipeline retry decision 和 HTTP response formatting 没有共享同一个标准中间表示。

### 为什么不是最佳方案

未来新增一种错误类型时，极容易发生：

- pipeline 能识别
- 对外返回格式没同步

或者反过来。

### 修改思路

1. 先构建统一的 parsed / classified error model。
2. `forwardError()` 改为消费这个 model，而不是自己重复判断 status / body。
3. 解析 JSON body 的逻辑集中到一个入口，避免重复 `JSON.parse`。
4. 把对外协议格式化拆成独立 formatter：
   - anthropic-compatible formatter
   - generic formatter

### 需要补的测试

- 402 / 413 / 422 / 429 / 503 upstream rate limit 在 classify 与 forward 上结果一致
- 新增一个错误类型时，只需改一处分类逻辑

### 验收标准

- `error.ts` 里不再平行维护两套 status 分支树

### 进度

- 状态：`todo`

## Medium-3: `start.ts` 体积过大，启动装配职责混叠

### 现象

[src/start.ts](/home/xp/src/copilot-api-js/src/start.ts) 已接近 500 行，同时承担：

- CLI 参数解析
- 配置输出格式化
- state 初始化
- history / context / TUI 初始化
- token / model / proxy bootstrap
- WS 装配
- HTTP server 启动
- shutdown wiring

### 根因

启动流程没有按职责拆层。

### 为什么不是最佳方案

这类文件会导致：

- 任何启动相关修改都需要通读整个函数
- 复用和测试困难
- 依赖顺序只能靠注释维持

### 修改思路

建议拆分为 4 层：

1. 参数与 runtime option 归一化
2. 本地服务初始化
3. 外部依赖 bootstrap
4. network server 启动与 shutdown 绑定

可考虑拆出：

- `buildStartupSummary(...)`
- `initCoreServices(...)`
- `bootstrapExternalState(...)`
- `startHttpRuntime(...)`

### 需要补的测试

- 启动顺序关键约束有明确测试
- server 未成功启动时不会半初始化

### 验收标准

- `start.ts` 仅保留 orchestration，复杂逻辑下沉到具名 helper / module

### 进度

- 状态：`todo`
