# 三条工程规则的召回分组裁决

**裁决资格：**确认具备；我未参与 A、B 任一方，也未修改被争议规则或 skill。
**争议清单：**①三条是否同一读者问题；②`check-dependency-contract` 与 `batching-can-silently-remove-a-gate` 是否同一失效机理；③`new-checks-must-not-alter-existing-contracts` 是否必须拆半。
**裁决态：**①两者皆误；②支持 A 对 B 的否定；③支持 A 的“不拆半”，但不支持 A 把三条全并为一组。最终采用第三种分法。

## 每条规则对应的读者时刻
[1] `check-dependency-contract`：正在冻结／设计新不变量，并准备选一个既有 API 作为承载基础；问题是“这个依赖自身声明的合法用法，会不会反向许可我的禁态？”（`/home/xp/.claude/rules/agents/63-engineering-practice.md:49-50`）。
[2] `new-checks-must-not-alter-existing-contracts`：正在新增校验并决定插入点；问题是“放在哪里既生效，又不改变既有顺序与分层契约？”（同文件 `:42-43`）。
[3] `packaging-can-void-another-invariant`：正在改 import 可达性；问题是“这次改动的爆炸半径里，哪些既有隔离不变量会成为受害者？”（同文件 `:59-60`）。
[4] 对照项 `batching-can-silently-remove-a-gate`：正在把 check 与 action 编进同一次工具调用；问题是“check 失败是否通过真实控制流阻断 action？”（同文件 `:51-58`）。

## 召回测试
[R1] 带 A 的“相邻既有契约是否与设计冲突”检索：能宽泛召回 [1][2][3]，但把“依赖会破坏我的不变量”与“我的改动会破坏别人的契约”压成同一方向；召回全不等于同一问题。
[R2] 反向测试 A：读者只问“我选的 API 是否把禁态写成合法用法”时，[1] 精确命中，[2][3] 不回答；只问“这次 packaging 会破坏谁”时，[3] 精确命中，[1] 不回答，故合并 description 不能替代两个意图域。
[R3] 带 B 的“门在真正执行时还在吗”检索：精确召回 [4]；只能靠把“矛盾文档诱导出错误实现”改写成“门蒸发”才勉强带出 [1]，不是 [1] 读者当时的自然问题。
[R4] 带 B 的“我的改动会打破谁的不变量”检索：召回 [2][3]；二者同属改动向外的 contract-impact 域，分别是通用插入点与 packaging 特例。
[R5] 带 B 的“该插在哪一层”检索：只召回 [2]，但其落点选择与“不改变顺序／分层契约”是同一个决策的约束和目标，拆半会让任一半都失去完整处方。
[R6] 反向测试 B：按其分法，处于 [1] 时刻的读者不会自然检索“执行控制流／退出码传播”，因此 `check-dependency-contract` 有漏召回路径；[2][3] 则不会永久漏召回。

## 最终裁决与影响
[D1] 三条全并为一个 seam-compatibility 问题——**两者皆误中的 A 部分**；A 捕捉到共同上位概念，却抹平了稳定的因果方向。
[D2] `[1]` 与 `[4]` 同一失效机理——**支持 A、反对 B**；前者是两个规范来源语义冲突，修法是换 API／同步契约／声明不适用，后者是 shell 控制流 fail-open，修法是 `&&`、`pipefail` 或分开执行。对象、故障机制和修法均不同。
[D3] `[2]` 必须拆半——**支持 A、反对 B**；原文实例显示“插入层”正由“不得改变既有顺序与分层”决定，不存在两个可独立召回的动作。
[D4] 第三种分法：域甲 `[1]`＝“依赖／契约传播能否破坏我正在建立的不变量”；域乙 `[2]+[3]`＝“我的改动会否破坏既有契约／不变量”，其中 `[3]` 是 packaging 特化入口。后续若改 skill description，应让两个意图域都可召回，而非按三个名词或一个泛化 seam 词组组织。

**最弱一环：**召回测试是依据当前规则的动作、因果方向和可用修法做的反事实检索模拟，没有真实 selector 日志或多读者盲测；因此“哪种措辞实际触发模型”的经验强度最低，但不影响 `[1]` 与 `[4]` 在控制流事实和修法上的机制差异。
