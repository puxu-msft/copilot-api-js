写下任何**顺序前置**（「X 必须晚于 Y」「Y 未完成前不得 X」）之前，先追一遍它的**完整触发／放行链**，逐环问四件事：**谁产生 X 的触发事件、谁决定放行 X、哪一环读取或因果编码了 Y、检查与放行是否原子。** **只有整条链上没有任何一环读取或编码 Y 时**，这条才不是门，而只是愿望——它没有执行接缝，写得再郑重也拦不住任何东西。

⚠️ **判据是「整条链」，不是「X 的直接执行者」。** 直接执行者不读 Y，门仍可能成立：Y 完成后才产生 X 的触发事件（因果编码），或 scheduler／hold 机制在放行 X 前读取 Y。把判据收在直接执行者上会**误杀正确设计**（false-red），逼人放弃本来有效的因果门。

**本轮实例（2026-08-08，History Worker Batch 1b 收尾）**：我把「临时证据清理必须晚于收尾提交进入 `master` 祖先」写成清理前置。追链后确认整条链都没有一环读 Y——清理由 **Claude job 自动回收**触发，会话正常结束、崩溃或平台回收都会触发它，没有 scheduler 读 ancestry，也没有任何机制让「提交进 master」去产生清理事件。终审 reviewer 判 major。

**判定「不是门」之后有两条合法出路，别只记住第一条**：
1. **首选：让 X 提前发生也无害**（消门，而不是加固门）。本轮做法是把长期价值**先行**落进已提交的持久接收者，于是清理何时发生都不删唯一副本；`master` ancestry 只保留它真正管得住的职责——「可宣告集成完成、可清理 branch/worktree」。首选它是因为它不依赖任何外部机制持续正确。
2. **备选：建立并验证一个真正会读取／编码 Y 的外部 gate**（如可显式 hold 生命周期的机制）。这条是合法的，但**必须实测验证该 gate 确实生效**，不能凭它「应该会」就写进设计——否则只是把同一个愿望挪到了另一层。

**两个放大这个错误的形态**：
- **逐行复述**会让它看起来像已有 disposition。本轮那条失效的门被清单**逐行复述了 56 遍**，单看任一行都完整合规，只有回到「追触发链」这一步才暴露。
- 它是**判据之间留缝**而非某条判据写错：盯「产物有没有进提交」的检查（skill `session-closeout` 自验表 V7）**结构性地**看不到「我设的前置条件在物理上能不能被执行」。逐条核判据核不出来。

**Why:** 不可控的平台生命周期事件（job 回收、容器重建、缓存过期、CI 超时终止）被当成受控步骤来排序，是一类会静默失效的设计错误——它在纸面上完全自洽，只在真正发生时丢数据，而那时已经没人在看。

**How to apply:** 每写一条顺序前置，当场把**完整触发／放行链**标注出来（谁触发、谁放行、哪一环读或编码 Y、检查与放行是否原子）；整条链都没有那一环，就走上面两条出路之一，优先消门。此形态已记入 skill `session-closeout` 的 `verification-log.md` 2026-08-08 节，标为「新增负样本、建议入表」，待独立评审决定是否升为正式自验条目——**未经评审不得自行改写 SKILL.md 正文**（instruction text 必评）。
