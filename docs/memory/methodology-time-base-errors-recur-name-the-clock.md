**每次说「早 X / 晚 X / 写下时就已过期」，先写清是哪两个时刻之差、用的哪个时钟。** 2026-07-27~28 同一根因连错四次，每次都是数字算对了、**时间基换掉了**：

1. **`offsetMs` 是 commit 相对，不是请求开始相对** —— 据此做时间归因，把上游的空块认成我方 keepalive 锚点，写进了给用户的报告。
2. **「peer 早 6 小时」用的是 author date** —— 同一提交 commit date 只早 30 分钟。数字没错、结论敏感：若用来论证「本该有足够长的窗口发现它」，两个时钟给出相反答案。
3. **「写下它的 1 小时 40 分之前就已被 peer 修好」** —— 实际相反：那句**写下时是对的**（`de9ca1e8` 07-27 21:26），12 小时后才被 `1b8bdf2f`（07-28 09:30）作废；1h40m 是「修复 → 我自己那次经过该文件却没发现的提交（`ed455b9d` 11:10）」之间的距离。我把 reviewer 报告里 A→B 的间隔安到了 B→C 上。
4. **修正第 3 次的那个提交（`31e39d6f`），把被证伪的原话逐字写进了第四处。** 我在 skill 与 KICKOFF 两处把叙述改对了，却在同一提交的 HANDOVER 里新增了一行「那条在写下时就已过期」——于是「唯一事实源」与 KICKOFF 给出相反的时间叙述。由 reviewer 收口时抓出。

**Why:** 时间差是**两个端点的函数**，而句子通常只提一个端点（「早 6 小时」省略了「相对谁」，「写下时就已过期」省略了「哪次写下、被谁作废」）。省略的那一端会被读者、也会被三小时后的自己按最顺手的解释补全——于是同一个数字支撑了相反的结论。第 4 次最能说明它不挑场合：**当时我正在逐条修正前三次**，注意力全在这个错误上，仍然在同一个提交里复制了被自己判死的措辞——因为省略端点的句式读起来完全通顺，不触发任何警报。

**How to apply:** 引用时间差时把两个端点连同时钟一起写进句子——「`1b8bdf2f`（07-28 09:30 commit date）晚于那句写下的 `de9ca1e8`（07-27 21:26）12 小时」，而不是「早/晚 X」「写下时就已过期」。`git log` 默认显示 author date，做提交先后判断时显式取 `--format=%ci`（commit date）或 `%ai` 并标注取的哪个。**转述别人的时间口径前，回到原文确认它量的是哪两点**（第 3 次的成因）。**修完一处后全仓 grep 被判死的原措辞**（第 4 次的成因）——改对了主句不代表没在别处新写一遍。
