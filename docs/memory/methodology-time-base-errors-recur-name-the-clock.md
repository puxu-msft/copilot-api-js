**每次说「早 X / 晚 X」，先写清是哪两个时刻之差、用的哪个时钟。** 2026-07-27~28 同一根因连错三次，每次都是数字算对了、**时间基换掉了**：

1. **`offsetMs` 是 commit 相对，不是请求开始相对** —— 据此做时间归因，把上游的空块认成我方 keepalive 锚点，写进了给用户的报告。
2. **「peer 早 6 小时」用的是 author date** —— 同一提交 commit date 只早 30 分钟。数字没错、结论敏感：若用来论证「本该有足够长的窗口发现它」，两个时钟给出相反答案。
3. **「写下它的 1 小时 40 分之前就已被 peer 修好」** —— 实际相反：那句**写下时是对的**（07-27 21:26），12 小时后才被 `1b8bdf2f`（07-28 09:30）作废；1h40m 是「修复 → 我自己那次经过该文件却没发现的提交」之间的距离。我把 reviewer 报告里的口径压缩转述时，把 A→B 的间隔安到了 B→C 上。

**Why:** 时间差是**两个端点的函数**，而句子通常只提一个端点（「早 6 小时」省略了「相对谁」，「写下之前」省略了「哪次写下」）。省略的那一端会被读者、也会被三小时后的自己按最顺手的解释补全——于是同一个数字支撑了相反的结论。第 3 次尤其说明它不挑场合：那次既没有探针也没有代码，只是**转述一份正确的报告**。

**How to apply:** 引用时间差时把两个端点连同时钟一起写进句子——「`1b8bdf2f`（07-28 09:30 commit date）晚于那句写下的 `de9ca1e8`（07-27 21:26）12 小时」，而不是「早/晚 X」。`git log` 默认显示 author date，做提交先后判断时显式取 `--format=%ci`（commit date）或 `%ai` 并标注取的哪个。**转述别人的时间口径前，回到原文确认它量的是哪两点**——第 3 次错误正是转述时丢了端点。
