**收尾文档里凡是描述「接下来要做 X」的断言，在 X 真的发生之后就是错的**——而它恰恰是在 X 发生前写的，写的时候完全正确。2026-08-08 无损 shutdown 整改：终态报告、plan 状态头与两份评审记录共八处写着「整改尚未合回 master、待合并」，用户执行合并（`ad8128ad`）之后这八处同时变成假的，而没有任何东西会提醒我回来改。

**Why:** 这类错误有三个让它特别难被自己抓到的性质：

1. **它不是写错，是「写对之后世界变了」。** 通读全文查不出来——通读只能确认「我写出了我想写的」（`reread-docs-after-writing` 的边界），而这里我想写的当时就是对的。
2. **触发它的动作由别人执行**，所以我这边没有任何事件可挂。用户回一句「已合并」是唯一的信号，很容易被当成「那我可以收工了」而不是「有八处要改」。
3. **它伪装成完成态。** 文档通篇在讲「已完成、全绿、已闭合」，中间夹一句「待合并」，读者会自动把整份读成完成件，然后**不去执行那个 X**——本轮的独立评审正是据此判 blocker：读者据「已合入、可合并」不会再合并，而 master 上此刻仍带着两条 MAJOR。

**How to apply:**

- **写下任何「待/尚未/下一步是 X」时，当场把它登记为一条会过期的断言。** 收尾不是在报告发出时结束，而是在 X 的结果回来、且所有描述 X 的位置都被更新之后才结束。用户说「已合并」「已部署」「已发布」是**收尾的中段**，不是终点。
- **别只改叙述，要把判定翻面成正向可复跑命令。** 反例（改坏的形态）：把「待合并」删掉、写成「已合并」——读者仍然只能选择相信。正确形态是给出会随事实变化的命令：`git branch -a --contains <fix-sha>` 应当同时列出 `master`，`git show master:<file> | grep <invariant>` 应当看到修复后的形态。**判定命令的方向也要一起翻**——本轮我一度把「只输出本分支即未合并」原样留着，那句话在合并后自己就是错的。
- **grep 全部携带者，别只改主文档。** 本轮八处分布在四个文件：plan 状态头、plan 实施结果、两份评审记录的顶部状态行、终态报告的第 1 行／分支状态节／「未做的事」节。`grep -rn '待合并\|尚未\|未合并'` 一次扫干净，逐条处置。
- **合并后新写的东西同样要声明它自己的状态。** 这批更新本身仍在分支上未合并——所以报告里补了一节明说「本批仍待合并」，否则下一个人读到的又是一份自称已完成、实则有一半没进主干的文档。
