**任何聚合器，只要它的「零」既可能来自「真的没有」、也可能来自「没读到」，它就会在某一天报出一个绿色的假结论——而且是最显眼、最容易被摘走的那一行。** 属 verification 簇（[[feedback-pass-null-clean-not-self-validating]] 的「空≠负」在**聚合器**上的形态；对象是我方门禁而非 subagent 或文档，与 [[methodology-diagnostic-log-is-authoritative-voice-verify-against-ground-truth]] 并列——那条讲计数器只接了部分代码路径，本条讲证据通道本身会被截断）。

**实例（2026-08-09，合并 master 后的全后端门）**：`scripts/parallel-test.ts` 的汇总行从各 shard 的 stdout 解析 `N pass` / `N fail`。一个 shard 在打印 summary 的过程中死掉，那两行永远没落盘，于是它对汇总贡献 0。结果是 `3337 tests · 3337 pass · 0 fail · 1 shard(s) crashed`，而该 shard 的 junit XML 里躺着一条真实的 `<failure type="TimeoutError"/>`。同一次还把总数少报一半以上（3337 vs 7529 executed）。原件见 `exp/junit-tally-false-green/README.md`。

**三个具体形态，逐个都咬过人：**

1. **摘要在最后打印，事实随事件落盘。** 进程异常终止时，**先丢的恰恰是摘要**，而摘要正是所有人引用的东西。真相源要取**随事件写出的结构化产物**（junit XML、事件日志、DB 行），不取最后那份人类可读的 digest。
2. **两道判据读同一份证据时会互相掩盖。** crash 分类器的判据是「非零退出**且**没打出 `N fail`」，而 tally 的判据也是那行 `N fail`。同一份缺失的证据同时产生了「0 fail」和「crashed」标签——**而 crashed 标签让那个零看起来已经被解释过了**。设计两道判据时问一句：它们会不会由同一个缺失同时触发？
3. **换更可靠的源不消除这个错误，只把它挪进新源的盲区。** 改用 junit 之后，**测试文件在加载期抛错**根本不产生任何 junit 行，而 bun 照样打印自己的 `N fail`——于是这次是 crash 分类器失效（它等的那行来了），该文件的用例与失败静默蒸发。同一缺陷类，低一层。这正是 `fix-at-the-shared-base-not-where-you-noticed`：我修在了发现它的那一层。

**How to apply**：
① 看到聚合出来的 `0`／`空`／`none`，先问**「这是没有，还是没读到」**——两者在输出上长得一样，必须由不同机制区分。
② 判据设计上，**让「口径不完整」这件事本身出现在结论那一行**，不要只打在上面几行。实测教训：退出码当时已经是 fail-closed 的（文件身份比对会抓到缺行文件并退 1），但**警告打在上面、tally 打在最后**，交付报告摘走的永远是最后那行。修法是把 `⚠ INCOMPLETE`／`⚠ OUT-OF-SCOPE` 挂在 tally 行上。
③ 换证据源之后**重新问一遍新源的盲区**，别以为换了就完了。问法：什么情况下被测对象**存在**却在新源里**一行都不写**？
④ **别再枚举形态，去找一个能交叉检查的计数——但先想清楚它跨过了什么、没跨过什么。** 我连续三轮补新形态、三轮被更窄的形态推翻；第四轮改用「产出方自己声明的 `tests`/`failures`/`skipped` 与我的解析结果对账」才收敛。⚠️ **但我当时把它叫作「独立 oracle」，那是错的**：声明属性与行**同出一个 producer、同一份 artifact**，所以它只是 **producer 内部的自洽检查**——独立于**我方 parser 的计数实现**（能抓到我们丢行），**不独立于 producer**（producer 若把某文件从行与声明里一起省掉，两侧一致、门照过）。用它之前先实测这个关系是否成立（16/16 份真实产物三项精确相等），并**把「它跨过哪一侧、没跨过哪一侧」写进代码注释与测试名**。

⚠️ **「找一个独立来源」这件事本身，是我这轮栽得最惨的地方——同一形态连中三次。** 先是「同一 commit 连跑 N 次一致」（与 tally 同源）、再是「发现基线与 runtime 独立枚举」（实为同一份 `discover()` 结果一处两用，我把自己的代码写反了）、再是上面这条「声明计数是独立 oracle」。**三次都由独立评审证伪，而我的记忆库里早就有这条模式，有它在册也没拦住我。** 所以把可操作的动作写在这里：**要主张两侧独立，先交一张 provenance 图**——每侧的**生产者**是谁、**观测点**在哪、**上游**追到哪；**任一生产者同时控制两侧、或两侧最终追到同一上游，即不独立**。「换一种运行方式」「换一个 parser」「多跑几次」**都不改变上游**。→ [[feedback-pass-null-clean-not-self-validating]] 的独立 oracle 要求、`60-evidence-and-criteria` 的 provenance 图条款。

⑤ 这类断言的原件常在临时目录（`$CLAUDE_JOB_DIR/tmp`、`/tmp/*`）。**要在提交信息或文档里把某个数字当事实引用，就得把机器生成的原件固化进仓库**——独立评审复核时拿不到原件，只能标「无法核实」，哪怕断言是真的。**人工转录不算原件**：那样能确认的只是「作者在多个载体重复了同一说法」。

**⚠️ 被迫撤回的主张会换个措辞回流，这是本轮最贵的教训。** 同一个「充分性」主张（「满足 X 就能引用这些数字」）被独立评审推翻了**四次**，每次我都照改，然后它在**另一份文档**里以新措辞重新出现：先是「无 `INCOMPLETE` 标记即可」→ 改成「退出码 0 是唯一充分判据」→ 改成「退出码 0 是必要非充分」→ 结果又在进度文件里写成「判据是退出码与标记，不是某个具体数字」。**根因不是措辞不小心，是我在多个文档里各复述了一遍判据**。修法：**判据只在权威文档里定义一次，其余位置只留指针并明说「本行不复述该判据」**（→ user-rule `41-doc-mgmt` 的 `one-authority-allows-contextual-restatement`：可以复述解释，但**易变的判定条件**复述一次就多一个漂移点）。自查动作：被评审推翻一条断言后，**去 grep 它的所有同义表述**，别只改被点名那处。

**顺带一条判据标定的教训（同轮，独立评审证出）**：阈值别按「看起来安全」取整。那条 CAS 字节比判据设 `≥10`，实测两端是——健康 109.68 / 218.58，**去重完全失效** 9.51 / 10.79。于是 physical 只差 0.49 就放行，而 **live 在完全失效时都没有鉴别力**（10.79 > 10，照过）。正确做法是**把两端都测出来**（正常值与故障值），阈值取两端几何均值附近；现为 30 / 50。

⚠️ **这里我曾写成「任何部分退化按构造全绿」，被反例推翻，留作反例**：收尾评审构造了 47/48 个 operation 退化（保留一个仍复用共享内容）的**部分**退化，实测 `physicalRatio=9.516`，旧的 `≥10` 断言**仍然变红**。也就是说 physical 轴对严重的部分退化是有鉴别力的，我从两个端点外推到「整个退化区间」缺乏实验支撑。**能说的只有端点事实**：完全失效时 live 仍过门、physical 仅以 0.49 之差失败。要主张覆盖整个区间，必须参数化复用比例、实测曲线或证明单调边界。这是我自己记忆索引里那条「全称词没穷举范围」的又一次复发（→ [[methodology-closeout-summaries-overstate-their-evidence]]）。

**多臂判据要逐臂配负控。** 上面那道对账有三臂（`tests`／`failures`／`skipped`），我写的每条用例都**同时**带行数不符，于是另外两臂从未成为任何一次变红的原因——删掉它们测试照样全绿，是「看起来像覆盖」的装饰。判据：**为每一臂造一条「只有该臂不符」的用例，再逐臂变异确认各自恰好咬红一条**；顺带检查错误消息的匹配正则**互不交叉**，否则仍分不清是哪一臂咬的。→ `criteria-fail-two-ways`、[[methodology-new-oracle-discriminating-power-is-experimental]]。
