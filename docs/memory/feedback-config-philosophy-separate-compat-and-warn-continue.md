配置的哲学倾向与代码相反、**单独成条**：代码遵循 CLAUDE.md「无向后兼容负担」（可强制迁移旧→新、允许短期报错 / 功能不可用），但**配置不适用这条**——配置随用户想法不停改动、用户手上有存量 `config.yaml`，破坏性重命名 / 删键会让老配置**静默失效**。

两条铁律：
1. **兼容层必留。** 配置键重命名 / 迁移 / 收窄作用域时，提供向后兼容别名（旧键 → 新键读时映射），不直接砍掉旧键路径。存量配置要继续能用。
2. **警告并继续，不中止进程。** 配置加载 / 校验遇到已弃用 / 未知 / 无效键时，默认**警告并继续**（保留可用配置 / 走默认值），**唯一例外**是程序启动时（用户在场、能立即修）——启动期可以 fail-fast 中止。运行时热重载配置**绝不**因一处配置问题杀掉正在服务的进程。

**Why:** 配置是用户高频改动的活面板，破坏性变更的成本落在用户身上而非代码维护上；一个正在服务的进程被一次手滑的配置改动打挂是不可接受的。这与「代码破坏性重构长远正确」并不矛盾——两者作用对象不同（代码是维护者的债，配置是用户的活输入）。
**How to apply:** 重命名配置键（如本次 `system_prompt_{prepend,append,overrides}` → `anthropic.system_prompt_*`）时——schema 保留旧键接受 + 读时迁移映射到新键 + 弃用警告；配置加载器须区分「启动期 fail-fast」与「热重载 warn-continue」两档严重度。收尾时把此哲学正式下沉到 ADR + CLAUDE.md 工作哲学节（作为「无向后兼容负担」的配置侧例外）。
