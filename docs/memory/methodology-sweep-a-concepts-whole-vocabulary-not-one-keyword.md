删掉或改掉一个概念之后做文档／注释清扫时，**grep 的是词，不是概念**。同一个概念在文本里通常有好几个称呼，它们分属不同词性、不共享任何子串，所以扫净其中一个对其余毫无信息量——而「`rg <那个词>` 返回空」读起来却像是一句完备性结论。

**实证（2026-08-11，RequestEnvelope 三作用域重构）**：把 `requestState` 拆成 `request`/`candidate` 两个作用域、并把 copy-on-write 的 `with()` 改成就地写的 `writeAttempt` 之后，我按 `requestState` 扫了 src + tests + docs，逐处改完、命中归零、宣布完成。但同一次改动的另一半留在原地：

| 称呼 | 词性 | 在哪 |
|---|---|---|
| `requestState` | 属性名 | 我扫了 |
| `env.with()` / `RequestEnvelope.with` | 方法名 | 漏 |
| 「immutable」「NEW env」「pure transform」 | 描述该策略的形容词 | 漏 |
| 「defensive body clone / defense-in-depth」 | 描述被一并删掉的配套机制 | 漏 |

漏掉的这些**恰好落在最要紧的地方**：`hooks/types.ts` 的 `client.inbound` 契约仍写着「driver 交给 hook 一份防御性 body 克隆（immutable-return + defense-in-depth）」，而防御性克隆正是用户裁决删掉的；`RewriteResult.env` 仍文档为「Immutably-updated envelope」，而 `writeAttempt` 返回的是**同一个对象**——照这份契约写的作者会持有一个 pre-rewrite 引用并以为它还是旧 body。属性名散在实现注释里（改错了代价小），而形容词散在**面向作者的契约文档**里（改错了代价大）：清扫顺序与风险顺序恰好相反。

**How** —— **候选集合必须从「删除动作本身」机械导出，不能由作者回忆列举。** 这是本条经三次修订才找到的承重点：前两版都要求作者「列出称呼」，而作者列得全不全**只能由作者自己判定**，于是每一版都被同一种方式绕过（第一版：把某类填成抽象类别；第二版：每类只列一个 literal 就宣告该类已覆盖）。

1. **导出标识符候选集**：删除/重命名是一次 diff，`-` 侧包含你移走的每一个标识符。`git show <删除该概念的 commit> -- <路径>` 或 `git diff <改动前ref>..HEAD -- <路径>`，把 `-` 侧出现、`+` 侧不再出现的标识符抓出来——**这份集合是别人能重跑并逐字比对的**，不依赖任何人的记忆。
2. **导出非标识符候选集**：形容词与配套机制名（「immutable」「copy-on-write」「defensive clone」「不可变返回」）不是标识符，diff 抓不到。它们的机械来源是**被删声明自己的旧文档**：`git show <改动前ref>:<定义该概念的文件>`，读那段 docstring / 注释，把它用来描述该概念的**词**抄下来。旧文档就是当初教别人怎么称呼它的地方。
3. **逐项处置**：对①②合成的候选集，每一项写明「已扫，命中 N 处，处置为 X」或「不适用，因为 Y」。**不允许出现未处置项。**
4. 逐项扫描时**分别报数**，不要合并成一句「已清扫」——那会丢掉「哪个称呼扫过、哪个没扫」。
5. 完备性判据是「**候选集合由①②机械导出，且集合内每一项都有处置**」，**不是**「命中归零」（[[feedback-pass-null-clean-not-self-validating]] 的空命中陷阱），**也不是**「我列的那几个都扫了」。
6. 按后果排序先扫**契约文档**（给 hook/插件/rewrite 作者读的）与**可加载的示例代码**，再扫实现注释——踩过的实例见下。

第 1、2 条与前两版的区别是**谁来裁定完整性**：前两版是作者，现在是一条别人能重跑的命令。作者仍可能漏处置某一项，但那会在候选集合与处置清单的**差集**里显形，而不是消失在「我觉得列全了」里。

**这条规则被独立评审连判三次可绕过，每一次都是同一个结构病：完整性由作者自评。** 这段迭代史本身就是判据的证据，不要删。

| 版本 | 判据 | 被怎么绕过 | 实证 |
|---|---|---|---|
| v1 | 列四类称呼、分别报数 | 把某类填成抽象类别或自认无项 | 写下后**同一会话内又复发两次**：`DESIGN.md` 只扫 `requestState` 漏掉「防御性 body 克隆」那行；整个 `docs/` 侧 hook 规格没扫，其中**可加载的** `hooks/strip-todowrite.ts` 与生产示例都在承诺已不存在的契约 |
| v2 | 每类须给具体 literal + 旧契约 `file:line`，写「无」须附检索式 | **每类只列一个 literal**：方法类只列 `writeAttempt` 不列已删的 `env.with()`，四类都有 literal 与证据，判据照样满足 | 评审当场构造出这张能通过文字门的四行表 |
| v3（现行） | 候选集合由 diff 与旧 docstring **机械导出**，逐项处置，差集显形 | —— | 对本次删除实跑导出得到 `requestState`／`RequestState`／`with`／`Immutable`——**恰好包含 v1 漏掉的那两个**；并额外查出 `src/lib/request/retry-registry.ts` 一处三轮清扫与六名评审都没抓到的残留 |

三次都由**独立评审**逮到，没有一次是自查逮到——这正是为什么完整性不能交给作者判定。

**与 [[feedback-fix-all-comparison-sites]] 的分工**：那条问「**这件事在系统里被独立做了几次**」，按业务维度（腿／格式／端点）枚举入口，治的是「同一动作多个入口」；本条问「**这个概念在文本里被叫过几个名字**」，治的是「同一概念多套措辞」。两条都是「grep 的边界」，但枚举的维度不同，漏的东西也不同。

**触发提醒**：这次是用户一句「整体都做完了吗」才让我回头核的——我自己给出的「清扫完成」是自证结论。凡是宣称某类清扫完备，先把**机械导出的候选集合与逐项处置**交出来（`git show <删除 commit>` 的 `-` 侧标识符 + `git show <改动前ref>:<定义文件>` 的旧 docstring 用词），不是交一张自己列的称呼表。
