用户明确陈述（本会话多次）：

> **用户永远不在乎向后兼容性、回归风险，用户在乎架构健康、长期可维护性、可观测性**

> **如果一个问题真实存在，不要在乎风险，认真去做，再让 subagent 认真 review，如果真出问题说明测试覆盖不够到位**

**Why:** 给暂缓项分流时，我的默认偏向"ROI / 风险调整后的优先级"——把低严重度的可读性项、以及"没有真 bug、只是形状问题"的项当作暂缓。用户回怼：这个框架是错的。正确的轴是"问题到底存不存在"。若存在 → 修它，不管感知到的风险。回归风险靠测试 + subagent review 来缓解，而非靠回避。

**How to apply:**
- 给 backlog/review 分流时：只问"这是不是一个真实问题？"——而非"修起来有没有风险？"或"用户会不会注意到？"
- 区分两类"风格",别把前者误归后者而漏修:
  - **代码一致性 = 真问题,要修。** 同函数/同模块的相似逻辑用了不一致的写法(有客观锚点:**既有模式**),属 CLAUDE.md best-complete-solution"保持代码风格统一"——选定一种模式就贯彻到底。
  - **纯主观 A/B 偏好 = 跳过。** "这行换种写法更好看",无既有模式约束、不影响缺陷,才是 subjective preference,不算问题。
  - 判据是有没有**既有模式做客观参照**:有 → 一致性问题要修;没有、纯审美 → 跳过。
- 若潜在风险是真的（如资源泄漏、静默数据丢失、竞态、可观测盲点），别把项归类为"等触发再说"。
- 实现后，跑一次独立的 subagent review（`feature-dev:code-reviewer`）。若 review 发现新的真 bug，那证明测试覆盖不足——在修复里补测试。
- 用户**不要**每项一个授权门——自主走完整个清单。
- 架构健康 > 向后兼容：改 config 字段名、函数签名、返回类型都可接受。

Related: [[feedback_no_unilateral_action]] 仍适用于**范围歧义**（不确认就别扩大范围）——但在已确认的范围内，把所有真实问题都修掉。
