**一份 skill 里凡是「需要实战检验才能确认」的断言，验证机制就必须内置在这份 skill 里**，让未来的会话在**正常使用它的过程中**顺手验掉，而不是写成交接里的一条待办、或"留给新会话"的口头承诺。用户 2026-07-28 定：「如果 skill 有什么内容需要实战检验，理应在 skill 内置，并让未来的会话自我验证。」

落地形状（`session-closeout` 是范式）：skill 正文一节**自验表**（断言 / 怎么验 / 证伪长什么样），配一个同目录 `verification-log.md` 记录文件；验法必须是**在正常走流程时顺手能观察到的**，不是要另做实验；毕业与证伪规则写死（三次独立会话证实即毕业、**任何一次证伪当场改正文**）。作者本人**不能给自己的 skill 投证实票**——「我知道该用哪个 skill」「我填自己的模板不犹豫」都是被污染的观察，只能记「数据不足」。

**Why:** 指令文本的**静态自洽**（评审能查的）与**真实压力下会不会被照做**（只有实战能查的）是两回事，而后者恰恰是 skill 存在的理由。把待验项写进交接，等于把它托付给一个不会回来的上下文——那条备注会随交接文档一起沉底。内置进 skill 则每次使用都自动重新提起，且**验的人正好是最有条件验的人**。立表当场就有回报：`session-closeout` 的自验表刚建好、第一次真跑 V4，就**证伪了我自己写进 §6 的查-peer 配方**——`git log -S<符号>` 抓不到那次作废我结论的提交（它只加了一行守卫，我会去搜的模块名不在 diff 文本里，而 `-S`/`-G` 匹配的正是 diff 文本），路径口径才命中。若没有这张表，这条错配方会以"经两轮跨模型评审"的姿态一直躺在 skill 里。

**How to apply:** 写完任何 skill/rules，先问「这里面哪些条是我**没有实战证据**的？」——触发可靠性、压力下的可执行性、配方在本仓真的抓得到东西、规则会不会改变某个可测比例，这四类几乎必然属于未证。把它们从正文里挑出来单列自验表，**每条给出可被观察到的证伪形态**，并把基线数字连同**产生它的确切命令**一起写下（口径不同的两个数不可比——V5 的初版基线就是抄了 reviewer 一次范围与判据都不同的抽样，复测立刻对不上）。
