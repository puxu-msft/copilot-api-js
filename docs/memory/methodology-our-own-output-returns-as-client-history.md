**凡是我方会写进响应的形状，都要假设它会从请求回流。** 所以「上游/客户端原生不会产出 X，故不必修 X」这个论据在代理项目里天然不成立——**我方自己就是那个会产出 X 的来源**，而客户端会把收到的内容原样存进对话历史，此后每一轮都带着它重投。

**Why:** 代理位于「客户端历史」与「上游校验」之间，是一条**闭环**而非单向管道。判断某个非法形态「不会出现」时，人只盘点了上游/客户端两个来源，漏掉了第三个也是最容易出问题的来源：我方自己的改写/合成/恢复腿。而且这种回流是**自我延续**的——一旦写进客户端历史，客户端每轮都重投，于是「偶发一次的产出缺陷」变成「该对话每轮必败」。

**How to apply:** 写「明确未做/不必修」这类结论时，把判据从「客户端会不会发」换成「**我方会不会写出去**」：grep 自己的合成/改写/恢复路径（本项目如 recover-refusal、tool_recover_call_text、continuation 缝合、keepalive 合成帧、L1 布局矫正本身）是否可能产出该形状。相应地，**入站校验/修复要按「输入可能来自我们自己」来设计**——即修复腿要能修自己昨天造出来的东西（幂等 + 对既有非法形态主动矫正，而不只是"保证自己不制造"）。

实例（2026-07-27）：spec `docs/spec/2026-07-26-thinking-terminal-block-layout.md` 曾写「不主动修复 C3，因为客户端原生产出 `[T, tool, text]` 从未观测到」。一台陈旧实例把合法消息改写成 `[T, tool, T]` 发上游 → 客户端把它存进历史 → 之后每轮重投这条非法消息，而 L1 因为「只在 C1/C2 违规时才动手」对它视而不见、L2 又认不出那句 400 措辞，形成每轮必败且零兜底。修法是把 C3 升为独立触发条件（能修自己造的历史遗留），该条「明确未做」已划线订正。相关：[[methodology-verify-running-server-has-fix-before-diagnosing-from-log]]（先判是不是陈旧实例造的）、[[feedback-synthetic-data-must-be-distinguishable-from-real]]（合成物必须可辨识）。
