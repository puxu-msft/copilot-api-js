## 发现的问题（按严重度排序）

### P1: error.ts — JSON 反复解析

`classifyHTTPError` 中的辅助函数 `extractRetryAfterFromBody`、`isUpstreamRateLimited`、`tryExtractTokenLimit`、`isRateLimitedInBody` 各自独立 `JSON.parse(responseText)`。
`forwardError` 中也有独立的 `JSON.parse`。
同一个 `responseText` 可能被解析 4-5 次。

**建议**: 在 `classifyHTTPError` 入口解析一次，将 parsed object 传递给所有辅助函数。

### P2: error.ts — forwardError 与 classifyError 职责重叠

两者都在做错误类型判断（429、402、413 等），但走不同路径：
- `classifyError` → 供 pipeline 策略使用
- `forwardError` → 供最终 HTTP 响应使用

**建议**: 让 `forwardError` 内部复用 `classifyError` 的结果，而不是重新做一遍分类。

### P3: responses/handler.ts — 死 re-export

第 219 行: `export { responsesInputToMessages, responsesOutputToContent } from "~/lib/openai/responses-conversion"`
需要确认是否有消费者通过 handler 导入这些函数。

### P4: 三个 handler 的流式处理模式高度相似

所有三个 handler 都有几乎相同的流式处理骨架：
```typescript
const iterator = response[Symbol.asyncIterator]()
const abortSignal = combineAbortSignals(...)
for (;;) {
  const result = await raceIteratorNext(iterator.next(), { idleTimeoutMs, abortSignal })
  if (result === STREAM_ABORTED) break
  if (result.done) break
  // 解析、累积、转发
}
```
**建议**: 可以提取通用的流式迭代器骨架函数, 减少重复。但这是 API 格式不同导致的平行实现, 不是紧急问题。

### P5: auto-truncate 跨模块相似函数

`anthropic/auto-truncate.ts` 和 `openai/auto-truncate.ts` 有同名函数:
- `calculateTokenLimit` — 逻辑完全相同, 可提取为共享函数
- `createTruncationSystemContext` — 几乎相同, 模板文字微差
- 其他函数因类型差异不适合合并

**建议**: 将 `calculateTokenLimit` 提取到 `auto-truncate/index.ts`（已有的共享模块）。
注意: `request/truncation.ts` 已有一个共享的 `createTruncationMarker`, 说明共享化的方向是对的。

## 总体评价

### 优秀之处
1. **架构设计清晰**: 模块划分合理, 职责边界清楚 (client → handler → pipeline → strategy)
2. **策略模式**: request/pipeline.ts 的重试策略设计优雅
3. **类型系统**: 严格 TypeScript, 类型覆盖全面
4. **错误处理**: 分类精细 (10+ 错误类型), 每种都有对应策略
5. **可观测性**: 日志、history 存储、TUI 展示层层完善
6. **算法精巧**: KMP 重复检测、令牌桶速率限制、自适应 auto-truncate
7. **优雅关闭**: 三阶段关闭 + stale reaper, 生产级可靠性
8. **观察者模式**: context manager 的消费者注册设计
9. **config 热重载**: YAML 配置文件变更自动应用
10. **模型解析**: 链式解析 + 循环检测 + family 回退

### 需要改进的地方
1. **error.ts 的 JSON 反复解析** — 性能浪费, 应一次解析传递
2. **forwardError 与 classifyError 职责重叠** — 应统一分类逻辑
3. **responses/handler.ts 死 re-export** — 应清理
4. **handler 流式处理骨架重复** — 可提取但不紧急
5. **auto-truncate calculateTokenLimit 重复** — 可提取为共享

### 总评
项目整体质量**高于平均水平**。模块化、类型系统、错误处理、可观测性都做得很好。
主要问题集中在 error.ts（可修复，不影响正确性）和 auto-truncate 跨模块相似性（有意的设计权衡）。
代码量约 8000+ 行 TypeScript, 测试 1026+, 覆盖面广。
