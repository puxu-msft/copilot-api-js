# UI 重写注意事项检查清单 / UI Caution Check

> 来源：从 `docs/2603-vue3-best-practice/`（针对已废弃的 Vue 3 UI，v3 与 v4/Vuetify）的最佳实践审查里，提炼出**与前端框架无关**的产品行为规格与方法论教训。原目录里 Vue/Vuetify 特定的整改建议（typed injection key、composable 化、`watch`/`watchEffect`、Pinia、Vuetify 页面 mount helper 等）在换框架后一律作废，**不在本文件范围内**。
>
> 本文件是一份可勾选的检查清单，供新 UI（无论用何框架）在设计、实现、评审阶段逐条核对。清单里引用的具体代码位置均为**旧 Vue UI 的反面战例**（截至提炼时仍存在），只作"这个坑真实发生过且会复发"的证据，不代表新实现要照搬那套代码。

## 一、副作用与 DOM 定位（最重要，v3→v4 原样复发的坑）

旧 UI 里"消息定位 / 搜索高亮滚动 / 目录树跳转"这类能力，一直用**全局 `document.querySelector` + 裸 `setTimeout` 赌渲染时序**实现。这是 v3 审查判定必须收口的问题，结果 v4 不但没修、还扩散到了更多文件（[useKeyboard.ts](../../ui/src/composables/useKeyboard.ts)、[useDetailOrchestration.ts](../../ui/src/composables/useDetailOrchestration.ts)、[useTocTree.ts](../../ui/src/composables/useTocTree.ts)、[DetailToolbar.vue](../../ui/src/components/detail/DetailToolbar.vue)、[DetailPanel.vue](../../ui/src/components/detail/DetailPanel.vue) 的 `.search-highlight` 全局查询 + `setTimeout`）。这类模式极易复制扩散，是最值得在新 UI 里从一开始就堵死的坑。

- [ ] **查询范围收敛到局部容器**，不对全局 `document` 做选择器查询。定位一个消息 / 工具结果 / 目录节点时，从组件自己持有的容器根（框架的元素 ref / DOM 引用）向下查，或维护一张"id → 元素"的注册表，而不是全局按 class/属性 选择器扫。
- [ ] **不用裸 `setTimeout(…, 50)` 等待 DOM 稳定**。滚动 / 高亮定位要挂在"渲染完成"的明确信号上（框架的渲染完成回调 / 布局副作用钩子 / `requestAnimationFrame` / `ResizeObserver` 等），不靠猜一个魔法延迟。魔法延迟在慢机器、大列表、异步内容下会"滚错位置或滚不到"。
- [ ] **同类节点存在多个时选择器不能撞车**。搜索高亮、消息锚点这类可能同时出现多个的目标，定位逻辑要能明确指向"第几个 / 哪一个"，而不是 `querySelector` 拿第一个。
- [ ] **副作用要有清理**。去抖 timer、observer、事件监听在组件卸载 / 输入变化时要停掉，避免挂起的回调打到已销毁的视图上。

## 二、测试策略（只测纯函数会漏掉真正脆弱的地方）

旧 UI 测试长期只覆盖 util / 类型守卫 / 纯函数 / store / ws-client，**页面挂载与交互层几乎没有**——而最脆弱的恰恰是页面副作用和交互边界。这条教训与框架无关。

- [ ] **要有交互层 / 页面挂载测试**，不能只有纯函数单测。至少覆盖：注入 / 依赖缺失、路由上下文、UI 容器缺失这类"装配级"失败。
- [ ] **按行为清单补测**（见第四节的产品行为），而不是按文件补测。搜索去抖是否在延迟后真的触发、筛选是否真的联动数据源、详情定位是否只在内容渲染后触发，这些是交互契约，值得各有一条测试钉死。
- [ ] **状态机分支要测全**：loading / empty / error / 依赖缺失 / 连接断开，每个态都要有验证，别只测 happy path。

## 三、组件粒度与分层

- [ ] **大组件按职责分层**（数据装配 / 展示结构 / 交互控制 / 副作用），不是按行数机械切块。旧 UI 里几个 400~700 行的页面同时扛这四件事，阅读和测试成本都高。
- [ ] **重复的有状态逻辑提炼为单一实现**（去抖、定位、筛选联动等），不要在多个组件里各复制一份——旧 UI 的搜索去抖就跨页面复制过，行为契约靠复制维持，迟早在延迟时间 / 清理时机上分叉。

## 四、必须重新实现的产品行为清单（换框架也要保留的用户能力）

这些是与框架无关的**产品行为规格**，新 UI 无论用什么技术都要重新实现，可直接当验收清单：

- [ ] **详情面板消息定位 / 搜索高亮滚动**：能跳到指定消息、跳到工具调用 / 工具结果、滚动到第一个搜索匹配项并高亮（这是第一节那个坑的正当需求，需求保留、实现方式换掉）。
- [ ] **目录树 / 大纲跳转**：从大纲节点跳到对应内容块（含父子层级回退定位）。
- [ ] **列表搜索去抖**：输入后延迟一段时间才真正触发搜索，而非每次按键都打。
- [ ] **筛选联动**：endpoint / status 等筛选条件正确联动数据源与列表。
- [ ] **实时态**：WebSocket 断线 / 重连的可见反馈，Live 与 History 的区分。
- [ ] **键盘操作**：模态开启时拦截、导出菜单等快捷键路径（旧实现同样用全局 DOM 查询判断模态是否打开，见第一节，新实现应改为显式状态）。

## 五、明确不用带走的（框架特定，防止照搬）

以下是旧目录的建议里**绑死 Vue/Vuetify 的部分**，换框架后无意义，列出以免新 UI 又把它们当"最佳实践"照抄：

- typed `InjectionKey` / `provide`-`inject` 收口（Vue 依赖注入特有）
- `<script setup>` / composable 化 / `watch` vs `watchEffect` 选型
- 是否迁移 Pinia、store 的 provide 位置
- Vuetify `v-app` 容器 / Vuetify 专用 mount helper

## 六、与后端 API 的关系

原审查目录对**后端 API 无可取之处、无未完成任务**——全部内容是前端框架层审查，未触及任何后端端点 / 契约 / 数据模型。唯一沾边的"Models 数据弱类型（`Record<string, any>`）应在 API 边界定义清晰类型"在旧 v4 里已收敛，且后端类型的单一真相在后端（见项目 `single-source-of-truth-types` 原则，前端从 `~backend/*` re-export）。新 UI 消费后端数据时沿用此原则即可，不需要从旧 UI 目录搬任何类型定义。
