## P2.4 任务（建 codec + 切 responses/route.ts + responses/ws.ts，behind flag）

### 1. `src/lib/codec/openai-responses.ts`（per-request 工厂 `createOpenAiResponsesCodec`）
实现 FormatCodec（参 codec.md §3 openai-responses）：
- `parse`：同步建 env（resolveModelName + modelIndex + manager.create + setOriginalRequest snapshot + tool-name mapper(responses 版 `buildResponsesToolNameMapper`/`applyResponsesToolNameSanitization`) + sanitize）。复用 CC 的 **preResolved**（route 在 system-prompt reload 前解析 model 传入）+ **originalBodyForHistory** + **getContext()**（失败 settle）范式。
- `decideRoute`（codec.md §2，**3 非一致默认写进注释**）：`vendor==="Google"(force)` 或 `!isResponsesSupported` → （`isEndpointSupported("/chat/completions")` ? translate `/chat/completions` : `vendor==="Google"` ? translate（**force 豁免 CC 检查**）: reject 400）；else passthrough `/responses`。
- `translateOut`：identity（直连）或 **Responses→CC**（`translateResponsesToChatCompletions`，fallback 到 CC 时）。**注意 CC 的教训**：翻译放 translateOut(S2) vs prepareWire(S4) 取决于 S3 改写/策略对 body 形态的假设——Responses 无 auto-truncate（retry-transport §2.2：`openai-responses: network → token-refresh`），故约束比 CC 弱，但仍要核对 fallback 路径的 body 形态一致性。
- `prepareWire`：直连 → `prepareResponsesRequest`；fallback → CC prepare。`normalizeCallIds`（call_→fc_）是**请求侧 S3 改写**（不在 codec，见 rewrite-registry），但 CC 把它放进了 prepareWire——**核对 Responses 直连路径 normalizeCallIds 该在哪**（现状 responses handler 怎么做的，照齐）。
- `renderResponse`：identity（直连；**stream-id-sync 由 S5 响应改写处理**，`fixStreamEventIds`）或 **CC→Responses**（fallback 回程 `translateCCStreamToResponsesStream`，stateful translator 闭包持有）。
- `renderResponseNonStreaming` / `formatError`（`streamErrorToOpenAIErrorType`）/ `createResponseAccumulator`（`createResponsesStreamAccumulator`）。
- `sampleRequest`：请求侧双轨（effective=Responses 直连 body 或 CC fallback body；wire=实际上游 + format 标签 `openai-responses`/`openai-chat-completions`；messages 用 `extractInputItems`）。

### 2. `src/lib/codec/openai-responses-strategies.ts`
`buildOpenAiResponsesStrategies` 复用 `adaptLegacyStrategy` 包 network-retry + token-refresh（**无 auto-truncate**，retry-transport §2.2）。

### 3. transport 上游 WS 二次选择（retry-transport §4.1，**P2.4 核心难点**）
`state.upstreamWebSocket && isWsResponsesSupported(model)` → 走上游 WS（`src/lib/openai/upstream-ws*.ts` manager：半开熔断/连接池/复用），失败回退 HTTP（`recordFallback`）。**这是 transport 内部细节、非路由决策**——扩展/包一层 transport 让它据 wire+model 选 HTTP vs WS，对 driver/codec 透明。`onTransport` 上报 http/upstream-ws/upstream-ws-fallback。运行时状态在 `/api/status.upstream_ws`。

### 4. route + handler-v4 + 客户端 WS
- `src/routes/responses/route.ts`：`if (isV4DriverEnabled("openai-responses")) handleResponsesV4 else legacy`（照 CC route 范式）。
- `src/routes/responses/handler-v4.ts`：route→driver→消费（照 `chat-completions/handler-v4.ts`：D3 parse 前 await system-prompt + preResolved；ctx 全失败路径 settle + c.set；流式消费记 forwardedSseEvents + complete；非流式 renderResponseNonStreaming）。
- **客户端侧 WS**（`src/routes/responses/ws.ts`）：Responses 的 GET WebSocket 端点（`client_ws_keep_open`/`max_ws_frame_bytes`/`max_client_ws_connections`）——让它**复用同一 driver**（runRequest/runResponse），WS 帧读写替代 streamSSE。这是 Responses 独有、CC 没有的一路，仔细对照现状。

### 5. flag + 等价测试 + 翻 ON
- driver-flags：`V4DriverFormat` +`"openai-responses"`，默认 false。
- `tests/responses/responses-v4.http.test.ts`：v4↔legacy 等价（**照 CC 测试范式**：直连流式/非流式、fallback(Responses→CC)、Google force-fallback、stream-id-sync、normalizeCallIds、unsupported reject；**+ L2 双轨等价**；**+ 上游 WS / 客户端 WS** 关键路径）。**测试隔离：afterEach 还原 flag 默认值，绝不硬编码 false**（CC 踩过的坑：泄漏给后续文件致主套件跑 legacy）。**测试环境 `disabled_models` 陷阱**：每请求前 `setDisabledModels([])` + 重 `setModels`（system-prompt 的 config reload 会重过滤掉注入模型）。

- **流式/时序测试连跑 10-25× 确认确定性**（fake timers + mock 随机/时钟）。

## 翻 flag ON 的硬 gate（逐格式）
**L1 行为等价 ∧ L2 记录等价**。L1 主要由「翻 ON 后现有 Responses 全套件经 v4 绿」满足（含 ws/fallback/force-fallback 既有测试）；L2 由「补 v4↔legacy history 双轨等价测试（effectiveRequest/outboundRequest/queueWaitMs）」满足——**当前定向测试不比 history 字段，必须补**，否则用未验证采样做 canary 基线。

## 关键坑 / 教训（CC 踩过的，照搬）
- **O10 双轨语义**：wire-trim（裁剪类）只落 wire 轨、不落 effective 轨（effective=未裁剪逻辑请求）；测试**钉死有意差异**，别复制 legacy 把裁剪泄漏进 effective 的旧行为。
- **失败终态 settle**：driver 抛错时 ctx 可能悬挂——codec 暴露 `getContext()`，handler 在**所有失败分支**（parse 期抛错/exchange 失败/reject）settle + `c.set("requestContext")`（让 observability 中间件兜底）。
- **queueWaitMs**：transport 记限流等待 + driver 记重试退避 `action.waitMs`（已通用，Responses 复用，但测试要覆盖重试路径）。
- **上游 WS 别泄漏到 codec/driver**：纯 transport 内部细节。
- **非流式路径走同 codec 的 NonStreaming 分支，别只迁流式**。
- **S5（改写 targetEndpoint 帧）vs S6（翻译到 clientFormat）边界严格**：stream-id-sync 是 S5 改写（操作 Responses 帧），fallback 的 CC→Responses 是 S6 render——别混层。
